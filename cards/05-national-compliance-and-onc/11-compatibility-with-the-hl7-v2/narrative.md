This section provides historical and technical context for why this guide diverges from the base HL7 v2 standard in certain areas. It is not required reading to use this guide operationally, but it may be useful for understanding the rationale behind specific field reinterpretations described elsewhere in this document.

HL7 v2 has been extraordinarily successful because it was designed around concrete, operational hospital workflows of the 1980s and 1990s. The VXU message inherited this lineage: it was adapted from medication-administration and ADT communication patterns intended for use within coordinated hospital environments. Those original patterns assumed a central orchestrating system, strict ordering semantics, and a clear distinction between orders, administrations, and acknowledgements.

Today's immunization reporting environment does not resemble those assumptions. VXU is no longer an offshoot of internal clinical messaging; it is a dedicated reporting interface implemented almost exclusively for sending immunization data to IIS. The HL7 v2 community is also no longer actively developing new VXU or QBP/RSP functionality. The work groups that originally defined these segments, constraints, and interaction patterns have largely moved to maintenance mode, and new interoperability work is occurring in FHIR, not in v2. As a result, there is no longer a shared user community evolving VXU semantics in parallel with IIS requirements.

Over the past two decades, IIS implementers and submitters have adapted the base message organically to fit the realities of public-health reporting. These adaptations were rarely intentional deviations; they emerged because the base v2 constructs did not cleanly match IIS workflows. Examples include the hard-coded values for PID-1, RXA-1, and RXA-2; the reinterpretation of RXA-9 from "administration notes" to "administered vs historical indicator"; and the reorientation of RXA-11 from bedside location to administering organization. These usages are now universal within the IIS ecosystem and fundamental to how systems interoperate.

The existing national guide historically preserved base-standard cardinalities and requirements even when IIS and submitters did not, and could not, use them consistently. This produced a situation where a field marked R could range from mission-critical to operationally meaningless. It also produced conformance issues in NIST validation: IIS that correctly documented relaxed local constraints appeared "off-standard," while IIS that quietly ignored base-standard requirements appeared "conformant."

The goal of this revision is to correct that long-standing mismatch. The immunization guide must describe actual implemented behavior, not maintain the fiction of full compatibility with a base standard that no longer serves this use case. This approach allows us to restore the meaningful distinction between R, RE, O, and X; to bring national and local guides into alignment; and to support consistent testing with NIST tools. The cost is reduced generic reuse of this specification outside immunizations. The benefit is predictable, testable, and operationally accurate guidance for the only domain still using VXU/RSP at scale.
