Immunization Information Systems (IIS) are required to consolidate vaccination information submitted from many independent sources into a single, coherent immunization history for each patient. To do this, IIS rely on key attributes of a vaccination event to distinguish one vaccination from another and to determine whether an incoming report represents a new event, a correction to an existing event, or a duplicate of information already received.

Submitting systems should understand that update and delete actions are interpreted in the context of this consolidation process. When a submitting system reports a change to a previously submitted vaccination, it is responsible for signaling whether the change alters the identity of the vaccination event itself or only modifies descriptive details. This ensures the IIS can correctly apply the update or delete to the intended vaccination record and avoid ambiguity or unintended data loss.

The fields listed in this section represent a minimum set of vaccination attributes that, if changed, can reasonably cause confusion about which vaccination event is being referenced. When an identifying field changes, an IIS may be unable to reliably determine whether the incoming information represents a correction to an existing vaccination or a newly administered dose. To avoid this ambiguity, a submitting system SHALL use **rechart** (delete-and-add) behavior, rather than a simple update, when reporting a change to any of these fields: sending a VXU delete for the original vaccination event, followed by a VXU add containing the corrected information. This guidance is not intended to define the complete set of data elements used by IIS for deduplication or record matching.

IIS should not assume that all submitting systems will follow this guidance consistently or in every operational scenario. IIS are expected to implement more nuanced and robust matching, reconciliation, and deduplication logic that considers equivalence and proximity, such as vaccination dates that are close but not identical, vaccine codes that differ but are known equivalents, or situations where identifying fields change without an explicit delete-and-add sequence. IIS SHOULD be capable of recognizing likely matches even when submitted data is not an exact match. The purpose of this field classification is to establish clear, predictable signaling behavior for submitting systems, not to constrain IIS matching or merging algorithms.

Together, these expectations establish a complementary standard: submitting systems are responsible for signaling changes in a way that minimizes ambiguity, while IIS are responsible for managing real-world variability in submissions so that the patient's immunization history ultimately remains complete, accurate, and coherent.

  - Followed by a VXU add containing the corrected information.
