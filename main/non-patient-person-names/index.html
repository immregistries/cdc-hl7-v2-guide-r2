4.5.2.11 Non-Patient Person Names

Quality review 3 warnings · 4 notes

Findings from automated and editorial checks, for the authors. Not part of the guide.

  • Warning ORC-12 (Ordering Provider) has usage C with no predicate. In ORC_IZ01 (Z22, Z32), ORC-12 is conditional, but there is no predicate, so neither readers nor validators know when it is required. Z42's ORC_IZ02 has it as O.
    IGAMT export defectAction: IGAMT
    IGAMT export
    • ORC_IZ01 ORC-12: C [0..1] XCN_IZ01, no predicate.
    Recommendation Add the intended predicate, or set a fixed usage.
    qf-igamt-ordering-provider
  • Warning Statement s4 Statement combines SHALL, SHOULD. Each statement should carry one requirement so it can be tested and referenced on its own.qf-multi-verb-statement-659e0ccf
  • Warning TAB Messaging Non-patient Person Names in HL7 (Scope (Table 1)): Conflict. The guide's list has "ORC-1 Entered By". ORC-1 is the Order Control code; Entered By is ORC-10. The other four fields are right. The guide does not say which message types each field applies to.
    ConflictAction: Narrative
    TAB The fields covered: PID-6 Mother's Maiden Name (VXU, QBP as QPD-5, RSP), NK1-2 Responsible Person Name, ORC-10 Entered By, ORC-12 Ordering Provider, and RXA-10 Administering Provider (VXU and RSP).
    Recommendation Change "ORC-1" to "ORC-10", and add the TAB's Table 1 (field by VXU, QBP, RSP).

    See the TAB comparison

    qf-tab-npn-01
  • Note MIROW guide Data Quality Assurance in Immunization Information Systems (BR138 - Vaccine administrator and prescriber): Partly covered. The guide carries both people (RXA-10 administering provider, RE for administered doses; ORC-12 ordering provider, conditional) and says how to format their names, but not which identifier goes with them (license number, NPI, or a local ID), so the license number MIROW asks for has no stated home.
    Partly coveredAction: CDC decision
    Best practice A vaccination event submission should include the full name and license number of the provider who prescribed the vaccine and of the provider who administered it.
    Recommendation CDC to decide whether the guide names an identifier for RXA-10 and ORC-12 (for example, NPI, with a license number as an alternative) or leaves it to local guides, and to say which.

    See the MIROW comparison

    qf-mirow-dqa-30
  • Note MIROW guide Data Quality Assurance in Immunization Information Systems (BR148 - Patient first and last name two characters): Partly covered. The guide deliberately sets no minimum length ("typically defined by the IIS"), and says guidance may be added in a future version after community discussion.
    Partly covered
    Best practice A patient's first and last names should each be at least two characters long, with possible exceptions.
    Recommendation When minimum name length is discussed, start from MIROW BR148.

  • Note In the draft, explanatory text continues after the conformance statements. Cards show statements after the narrative, so check that the order still reads well.qf-statements-mid-section-382f2d7c

Accurate representation of names for other people associated with the vaccination, parents, guardians, and providers, supports auditing, accountability, and linkage of immunization events to responsible organizations or individuals.

Applicable fields:

  • PID-6/QPD-5 Mother's Maiden Name
  • NK1-2 Responsible Person (Guardian) Name
  • ORC-1 Entered By
  • ORC-12 Ordering Provider
  • RXA-10 Administering Provider

Same formatting principles used for patient names apply here. These names must be transmitted consistently and with correct classification. Minimum supported length for name components is typically defined by the IIS and therefore varies; this guide does not set a universal lower bound, though guidance on minimum lengths may be added in a future version of the IG following discussion with the community.

  • The previous requirement that 'L' appear in the first repetition has been retired; order is not enforced.

Conformance statements

  1. SHALLSystems SHALL preserve spaces and hyphens.s1
  2. SHALLSystems SHALL support commonly used diacritics or transliterations.s2
  3. SHOULDSystems SHOULD preserve case and support up to 64 characters per component.s3
  4. SHALLFor NK1-2, submitting systems SHALL populate the name type code (NK1-2.7) and SHOULD use the official registry ('L') name when known.⚑s4
