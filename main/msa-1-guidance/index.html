3.3.4.1 MSA-1 Guidance

Quality review 1 warning · 4 notes

Findings from automated and editorial checks, for the authors. Not part of the guide.

  • Warning TA question (MSH Message Header, MSH-9 Message Type): Partly answers. The MSA-1 guidance says 'AR' was "previously" used for an unsupported message type, event code or processing ID, and removes only the fourth reason. It never says, in the present tense, that these conditions still get 'AR', or that "message type" covers all of MSH-9 (code, trigger event, structure). AIRA promised this clarification in 2024.
    Partly answers
    Asked The IG says to return AR for an unsupported message type. Does "message type" refer to the whole MSG data type in MSH-9, so that an unsupported trigger event (MSH-9.2) and message structure (MSH-9.3) are also covered?
    Recommendation Add a statement: an IIS SHALL return 'AR' when any component of MSH-9, MSH-11 or MSH-12 is not supported, with an ERR segment naming the field.

    See the TA question

  • Note TA question (MSH Message Header, MSH-11 Processing ID): Partly answers. MSH-11 is required and bound to HL70103, and the MSA-1 guidance mentions an unsupported processing ID. The guide does not say what an IIS does with 'T' or 'D' arriving at a production endpoint.

    Recommendation State that production interfaces SHALL send 'P', and how an IIS treats other values (see ta-q33-020).

  • Note TAB Acknowledgment (ACK) Messaging: Updated Specifications and Guidance (Successful, Qualified Successful, and Unsuccessful Transmissions): Partly covered. The guide uses "qualified successful" and "unsuccessful" in 3.3.4 and 3.3.4.1 but never defines the three terms. Key Terms (1.3) define Core Intent and Rejection, but not Accept or these three outcomes.
    Partly coveredAction: Narrative
    TAB Defines Successful (core intent fulfilled, no action), Qualified Successful (core intent fulfilled, issues need correction), and Unsuccessful (core intent not fulfilled, correct and resubmit); successful and qualified successful are accepted, unsuccessful is rejected (Table 2).
    Recommendation Add Successful, Qualified Successful, and Unsuccessful to Key Terms, or define them in 3.3.1.

    See the TAB comparison

    qf-tab-ack-08

Per these specifications, an MSA-1 value of 'AE' indicates the VXU was accepted as a qualified successful transmission. Previously, interpretation of 'AE' was ambiguous, requiring additional inspection of ERR-4 values in ERR segments to determine whether the VXU was accepted or rejected; this guidance resolves that ambiguity by limiting use of 'AE' to cases with severity 'W' errors but no severity 'E' errors.

An MSA-1 value of 'AR' indicates the VXU was unsuccessful, that is, rejected. Previously, 'AR' was reserved for four use cases: an unsupported message type, an unsupported event code, an unsupported processing ID, and an inability to process the message for reasons unrelated to format or content. This guidance removes the last of these as a valid reason to return 'AR', since it describes a transport or connectivity issue rather than an application-level outcome. As with ACKs more generally, MSA-1 cannot be used to convey transport or connectivity issues.
