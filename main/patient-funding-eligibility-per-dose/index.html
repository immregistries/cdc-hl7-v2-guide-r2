4.6.5.1 Patient Funding Eligibility (Per Dose)

Quality review 6 notes

Findings from automated and editorial checks, for the authors. Not part of the guide.

  • Note Statement s1 MIROW guide Immunization Information System Inventory Management Operations (BR705 - Patient eligibility for every administered dose): Reworded. Eligibility is reported for each administered dose. A jurisdiction may enforce it for participants in public programs, but the guide prefers accepting the vaccination and following up. The 2016 decrementing guide (S701) and ERR-5 code 2500 take the same approach.
    Reworded
    Best practice Patient eligibility must be documented and reported for every administered dose, and a report without it is rejected. Eligibility is needed to know whether to decrement public or private stock when both hold the same lot. It does not apply to historical doses.

    See the MIROW comparison

    qf-mirow-im-06
  • Note Statement s3 MIROW guide MIROW Principles and Business Rules Reports (DLE2011 - BR614, BR615 - Which eligibility to report when several apply): Conflict. The national value set (V01 to V05 and V22 to V25) has one code per category, and the guide allows at most one value per dose. That supports MIROW's minimum set but not its best practice. The guide does not give the hierarchy for choosing among codes, so a patient who is both on Medicaid and AI/AN may be reported either way.
    ConflictAction: CDC decision
    Best practice The minimum is a single item: Medicaid, AI/AN, uninsured, underinsured (at FQHC, RHC, or deputized providers only), grantee-eligible, or private coverage. When the patient meets more than one VFC criterion, the hierarchy is Medicaid, then AI/AN, then uninsured, then underinsured. The best practice is to report every applicable item in a valid combination (for example, AI/AN and uninsured), with rules for which combinations are valid and how to interpret them.
    Recommendation CDC to confirm that only one eligibility value is sent per dose, which departs from MIROW's best practice (DLE2011 BR615). If so, add to Patient Funding Eligibility (Per Dose) that when more than one applies, the submitter reports the first in MIROW's order: V02 (Medicaid), V04 (AI/AN), V03 (uninsured), V05 (underinsured).

    See the MIROW comparison

  • Note 4 requirements were written as paragraphs in the draft and are shown here as conformance statements (wording unchanged): s1, s2, s3, s4.qf-statement-from-paragraph-b938ed5e

Funding eligibility indicates whether the patient was eligible for a publicly funded vaccination program for a specific administered dose. Although some funding programs apply eligibility rules that are effectively patient-level (for example, all VFC-eligible vaccines at an encounter), implementations must record and message eligibility at the vaccination level to support accurate program reporting and MIROW-aligned practices.

Legacy workflows may capture eligibility only at the visit-level. The OBX-17 observation method allows systems and IIS to distinguish per-visit from per-dose capture and to troubleshoot older interfaces, but current implementations are expected to support per-dose reporting.

See Chapter 7, Message Infrastructure, and the OBX co-constraint tables, Section 7.2.18, for the normative HL7/LOINC field-level specifications, including OBX-3, OBX-5, and OBX-17 usage and exact code bindings.

Conformance statements

  1. SHALLSubmitting systems SHALL support capture and messaging of funding eligibility at the vaccination (per-dose) level.⚑s1
  2. SHALLIf a submitting system only captures eligibility at the visit-level, it SHALL associate that eligibility with each administered vaccination from that visit when constructing the message.⚑s2
  3. SHALLFor each administered vaccination, at most one funding eligibility value SHALL be sent.⚑s3
  4. MAYIIS MAY use OBX-17 to diagnose legacy or misconfigured interfaces but are not required to use OBX-17 to drive program logic.s4
