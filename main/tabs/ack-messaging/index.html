Acknowledgment (ACK) Messaging: Updated Specifications and Guidance

Defines core intent and what acceptance and rejection mean, ties MSA-1 to the most severe ERR-4 value, and sets requirements for ERR-2, ERR-4, ERR-5 (the national set of application error codes, with implementation priorities) and ERR-8.

Summary

The guide has folded in this TAB closely. Almost every requirement is in the ACK sections (3.3), often word for word, and figures 11 and 13 reproduce the TAB's tables. The main gaps are the national ERR-5 code set (named and published by the TAB, but neither named nor included in the guide, and mostly missing from the IGAMT value set), the rule that a rejected message is corrected and resent in full, and the core-intent scenarios in Appendix B. The guide also adds several requirements of its own, and recasts core intent in terms of "Critical Data", a term the TAB does not use.

3.3.4.1 MSA-1 Guidance

Summary: What Can Be Inferred from the ACK? (Key Takeaways) p. 6

shall not For a rejected (unsuccessful) VXU, the submitter corrects the issue(s) and resubmits the full message. Submitters shall not attempt to ascertain whether certain elements of the patient's IIS record were updated; there is no standardized way for an IIS to say which elements were stored.		Partly covered Warning

The guide says rejection does not imply that nothing was stored (s4), and that resubmission means a corrected message. It never says the whole message is resent, or that submitters should not try to work out what was stored, which is the practical consequence the TAB draws from s4.

Recommendation: Add to 3.3.1: "After a rejection, the submitting system SHALL correct and resubmit the complete message and SHALL NOT attempt to determine which parts of it were stored."

3.3.4 MSA-1: Derivation of Message-Level Disposition, Figure 11, Figure 13

Acceptance and Processing Terms: IIS Core Intent p. 7

Accept: the IIS received the message; the patient was associated or created and their shot(s), if submitted, were recorded. Reject: the patient was not associated or created and/or one or more submitted shots were not recorded; a corrected message must be resubmitted.		Reworded Note

The guide's narrative repeats the TAB's definition, but its statements define acceptance and rejection through "Critical Data", a term the TAB does not use: accepted when the patient is associated "and all submitted Critical Data is processed and stored". The two agree if Critical Data means the patient's identity plus each submitted vaccination; the TAB's examples (one of three immunizations stored: reject; TB result not stored: accept) fit that reading. Because Critical Data is otherwise left to local policy (see tab-ack-g03), the statements can be read more broadly than the TAB.

Recommendation: Confirm that Critical Data is meant to equal the TAB's core intent, and say so in the Critical Data key term, or phrase s1 and s2 in the TAB's terms (patient associated or created, each submitted vaccination recorded).

Action: CDC decision

Correction and Resubmission for Rejected (Unsuccessful) VXUs p. 15

Resubmission is not retransmission: correct and resend. Resending an uncorrected message can overload the IIS. The ACK does not say which side is at fault; operators on either side investigate.		Covered3.3.3.3 Required Follow-Up Actions

ERR-5 Values p. 16

ERR-5 carries a code from the national code set "as provided in the National Set of ERR-5 Application Error Codes for Immunization ACK Messaging".		Missing Issue

The narrative refers to "a national code set" but never names it, links to it, or includes it. The guide's own SHALL, SHOULD, and MAY (implement High, Medium, and Low priority codes) cannot be followed without it, because the narrative does not say which codes have which priority. The value set bound to ERR-5 in chapter 7 (HL70533_IZ01) is the 2017 code list plus 5044 and has no priorities. This site now shows the set (version 2026-07-06, pending publication by AIRA) as Appendix D, linked from 3.3.3.4; the narrative still needs to name and cite it.

Recommendation: Name and cite the national set in 3.3.3.4 and Resources (once AIRA posts it), and carry Appendix D, the codes with their priorities, into the guide.

Action: Narrative and IGAMT

3.3.3.4 ERR-5: Application Error Code

ERR-5 Values (code ranges) p. 16

Codes are organized into ranges: 1-7 legacy (use only when nothing more specific exists), 2000-2099 conflicting, 2100-2199 inappropriate, 2200-2299 invalid, 2300-2399 lookup failures, 2400-2499 message construction, 2500-2599 missing data, 2600-2699 processing errors, 2700-2799 data sharing or consent, 3001-3499 missing endorsed data elements, 3501-3999 invalid endorsed data elements, 5000-5999 processing results.		Partly covered Warning

The guide lists the categories in a sentence, without their number ranges, leaves out "processing results" (5000-5999) ("among others"), and does not say to use the legacy codes 1-7 only when no more specific code exists.

Recommendation: Give the ranges as a table in 3.3.3.4, including 5000-5999 and the rule for codes 1-7.

Action: Narrative

3.3.3.4 ERR-5: Application Error Code

ERR-5 Specifications p. 16

SHALL, SHOULD, MAY IIS SHALL implement High priority codes, SHOULD implement Medium priority codes, and MAY implement Low priority codes.		Conflict Issue

The narrative matches the TAB, but the profiles do not allow it. HL70533_IZ01 is marked closed and has 67 codes (1-7, 2000-2701, and 5044). The national set (Appendix D) has 280: 213 of them, including 16 of the 20 High priority codes (such as 2018, vaccination date before birth, and 3019, date of birth missing), are not in the value set, so an IIS that meets the SHALL sends ERR-5 values the profile does not allow. The value set also still lists 2202, 2203, and 2502, which the national set has deprecated.

Recommendation: Update HL70533_IZ01 in IGAMT to the national set (or make it open and point to the national set), and record the version of the set that the guide adopts.

Action: IGAMT
