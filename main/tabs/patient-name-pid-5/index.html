Patient Name (PID-5) Updates to Support Patient Matching

Name type codes (L required; M, NB, and N recommended), data type rules by name type, and preservation of spaces, hyphens, and special characters in patient names.

Summary

Section 4.5.2 (Patient and Other Names) is built on this TAB: the 'L' name rules, 'M', 'N', and 'NB' as SHOULD, the newborn scenario, spaces, hyphens, special characters with the same transliteration table, case, and 64 characters are all there, mostly as statements. The gaps are in the details. The guide forbids IIS from detecting placeholder names by pattern, where the TAB lets IIS reject them; it weakens the TAB's SHALL NOT for the Father's, Licensing, Business, and Partner name types to a SHOULD NOT; it leaves out the SHOULD NOT list (NAV, TEMP, BAD, D), the data type requirements by name type (as statements), and the IIS's duty to offer another way to correct a rejected accurate name. In IGAMT, the name type value set lacks REL, MSK, and NOUSE, and allows D.

Findings: 4 warnings 5 notes
Results: Conflict 3 · Missing 1 · Partly covered 2 · Reworded 1 · Covered 10 · Guide adds 2

Name type code (HL70200) Value Set usage for PID-5 p. 4

SHALL Systems SHALL support name type code 'L'. "Support" means submitting and querying systems can store and send names with the code in VXU and QBP, and IIS recognize it as valid (no severity 'E' because of the code).		Covered

The guide does not define "support" as the TAB does.

4.5.2.2 s1, 4.5.2.2 s4, 4.5.2.3 s4

Name type code (HL70200) Value Set usage for PID-5 p. 4

SHOULD Systems SHOULD support name type codes 'M', 'NB', and 'N'.		Reworded Note

Systems SHOULD support them (s1), as in the TAB, but receiving systems SHALL recognize and process them without error (4.5.2.3 s4), and IIS SHALL recognize 'NB' (4.5.2.6 s2). The TAB makes recognition by the IIS part of a SHOULD.

Recommendation: Confirm that the guide means to make recognition of M, N, and NB a SHALL for IIS.

Action: CDC decision

4.5.2.3 s1, 4.5.2.3 s4, 4.5.2.6 s2

Name type code (HL70200) Value Set usage for PID-5 p. 4-5

MAY Systems MAY support 'A', 'B', 'C', 'T', 'REL', 'MSK', 'NOUSE', and 'U'.		Covered

The guide names Assigned, Birth, Adopted, Indigenous/Tribal, and Religious as examples, not the full list. Its s4, "IIS SHALL NOT process unsupported name types if received", is unclear: it can be read as rejecting the message, where the TAB's point is only that unsupported names need not be stored.

4.5.2.4 s1, 4.5.2.4 s2

Name type code (HL70200) Value Set usage for PID-5 (Table 1) p. 4-5

SHOULD NOT, SHALL NOT 'NAV' (temporarily unavailable), 'TEMP', 'BAD', and 'D' (customary) SHOULD NOT be supported. 'F' (Father's name), 'I' (Licensing), 'K' (Business), and 'P' (Partner/Spouse) SHALL NOT be supported.		Conflict Warning

The guide says "Systems SHOULD NOT send names with ambiguous or administrative meaning such as Business, Partner/Spouse, or Licensing names", a SHOULD NOT where the TAB says SHALL NOT, and it does not mention Father's name or the SHOULD NOT codes.

Recommendation: Replace s3 with the TAB's two lists: SHOULD NOT NAV, TEMP, BAD, D; SHALL NOT F, I, K, P. Better, add Table 1 to 4.5.2.1.

Action: Narrative

4.5.2.4 s3

Table 1 compared with the IGAMT value set p. 4-5

Table 1 gives the usage of each HL70200 code for PID-5 (R for L; P for the others allowed; E for F, I, K, P).		Conflict Warning

HL70200_IZ01 (closed) does not include REL, MSK, or NOUSE, which the TAB allows (MAY), so they cannot be sent. It allows D (P), which the TAB says SHOULD NOT be supported, and leaves out NAV, TEMP, BAD, F, and K. It also has R and S (both E), which are not in the TAB's table.

Recommendation: Align HL70200_IZ01 with Table 1, including its usage for each code.

Action: IGAMT

4.5.2.1 Patient Names

Data type specifications by name type code (Table 2) p. 5-6

SHALL Systems SHALL follow the data type for the name type. 'L' and 'NB' names are XPN: given R, middle RE, family R, type R. 'M', 'N', 'A', and 'U' names are XPN_[Flavor]: given RE, middle RE, family R when given is not valued (otherwise RE), type R. The flavor is to be named in the next national guide.		Partly covered Warning

The guide describes this in narrative ("official registry and newborn names must contain both a family and given name, while other types ... may have only one component") and says two flavors "will be defined", but this is the guide that was to define them. There is no statement, no component table, and no flavor names. In IGAMT, the two XPN flavors exist but are applied by slicing the whole PID segment, so 'NB' names are not held to the family-and-given rule (see the IGAMT review, qf-igamt-c36-name-flavors).

Recommendation: Name the flavors (XPN_IZ01, XPN_IZ02), add Table 2 and a SHALL statement to 4.5.2.5, and resolve the IGAMT slicing finding so the rule applies per repetition.

Action: Narrative and IGAMT

4.5.2.5 Data Type and Structure

Scenarios: when the patient's name is known p. 7

SHALL, SHOULD, SHALL NOT Systems SHALL send the closest representation of the legal name with 'L'. Submitting and querying systems SHOULD send it in the first repetition; receiving and responding systems SHALL accept it in any repetition, process the message, and return the 'L' name in a response. Systems SHALL NOT send a name that is not the official registry name with 'L'.		Covered

The guide adds that systems SHOULD NOT send an empty first repetition to hold a place for 'L' (s3), and that IIS SHOULD match on the 'L' name when it is available (s5).

4.5.2.2 s1, 4.5.2.2 s2, 4.5.2.2 s3, 4.5.2.2 s4, 4.5.2.10 s1

Scenarios: maiden name and nickname p. 7

SHOULD When known, submitting and querying systems SHOULD send the maiden name ('M') and a nickname or preferred name ('N') in separate PID-5 repetitions; receiving systems SHOULD accept and process them.		Covered4.5.2.3 s1, 4.5.2.3 s2, 4.5.2.3 s3

Scenarios: unnamed newborn p. 7-8

SHALL NOT, SHALL, MAY Submitting systems SHALL NOT send a placeholder newborn name with 'L'. If 'NB' is used, they SHALL send the placeholder name with 'NB'; once the baby is named, SHALL send the legal name ('L') and the newborn name ('NB') in the same PID-5 field (which, per the Scenarios TAB, triggers a VXU with the complete history); and MAY continue sending the 'NB' name with the legal name.		Covered4.5.2.7 s2, 4.5.2.7 s3, 4.5.2.7 s5, 4.5.2.7 s6, 4.5.2.6 s1, 3.2.5.7 Official Registry Name Recorded for a Newborn

Examples: temporary newborn names p. 10-11

Recommended placeholder format: family name, and in XPN.2 'Girl', 'Boy', or 'Baby', the birth order for multiple births, and the mother's first name (Smith^GirlKatherine, Smith^Girl1Katherine).		Partly covered Note

The guide refers to Joint Commission and AHIMA conventions but says it "does not prescribe" a format, and gives none of the TAB's examples. The TAB's format is a recommendation, so this is a gap in guidance rather than a conflict.

Recommendation: Add the TAB's recommended format and the PID-5 examples to 4.5.2.7 or appendix A.

Action: Narrative

4.5.2.7 Unnamed Newborns, 4.5.2.6 s4

Name requirements p. 8

SHALL Systems SHALL preserve spaces and hyphens, and name components (for example, two first names in the first name field).		Covered4.5.2.9 s1

Name requirements (Table 3) p. 8-9

SHALL, MAY Systems SHALL support the commonly used special characters in Table 3 by preserving them or by transliterating them as Table 3 recommends; MAY support others. An IIS that cannot store them SHALL downgrade them following the transliterations (FAQ).		Covered

The guide adds that IIS SHALL NOT reject a message only because one of these characters appears (s4).

4.5.2.8 s1, 4.5.2.8 s2, 4.5.2.8 s3, 4.5.2.8 s5, 4.5.2.10 s4

Name requirements p. 8

SHOULD Systems SHOULD preserve case, and SHOULD support up to 64 characters in the first, middle, and last name components.		Covered

The guide adds that an IIS "SHALL NOT alter the capitalization in transmitted data" (s3), stronger than the TAB's SHOULD preserve case. The TAB's note that consistently long names warrant data quality follow-up is not carried over.

4.5.2.9 s2, 4.5.2.9 s4, 4.5.2.9 s3

Name requirements (IIS validation) p. 8

MAY, SHALL IIS MAY have additional validation, for example rejecting what appear to be placeholder or inaccurate names, or requiring at least two characters. If an accurate name is rejected for data quality reasons, the IIS SHALL offer submitters another (non-HL7) way to make sure the record is accurate in the IIS.		Conflict Warning

The guide says "IIS SHALL NOT rely on textual pattern detection (e.g., "Baby Boy") to infer that a record represents a newborn", which rules out the placeholder check the TAB allows (and that the national ERR-5 code 2201, Invalid Name (Baby), exists for). The IIS's SHALL to offer an alternate process when an accurate name is rejected is not in the guide.

Recommendation: Narrow 4.5.2.6 s3 to "IIS SHALL NOT treat a name as a newborn placeholder only because of its text when it is submitted with name type 'L'", or remove it; and add the TAB's alternate-process SHALL to 4.5.2.12 or 4.5.2.10.

Action: CDC decision

4.5.2.6 s3, 4.5.2.10 s3

FAQ: accepting records without 'L'; storing other names p. 12-13

Accepting a patient without an 'L' name is a local decision; an IIS may wait for the legal name. IIS are not required to store names other than 'L', but are encouraged to, for matching and consolidation. 'L' may be absent from PID-5 (for an unnamed newborn).		Covered

The guide makes storing or evaluating the other names a SHOULD (4.5.2.3 s5), stronger than the TAB's encouragement.

4.5.2.2 Official Registry Name, 4.5.2.3 s5

FAQ: how can IIS tell if a name is accurate? p. 13

SHALL Systems SHALL strive to accurately record and transmit names. IIS assume the submitted name is accurate unless other sources or submission patterns suggest otherwise.		Covered4.5.2.12 s2, 4.5.2.12 s1, 4.5.2.10 Name Consistency and Matching Expectations

Examples p. 9-11

PID-5 examples: 'L' alone; 'L' with a preferred first, last, or full name ('N'); 'L' with a maiden name ('M'); all three; newborn names for single and twin births, alone and with the legal name; and José González sent with accents and returned with or without them.		Missing Note

The guide has figure 22 of the name types but none of these PID-5 examples.

Recommendation: Add the TAB's examples to appendix A, linked from 4.5.2.
