Usage designations in this guide describe whether data is expected to be populated and whether the IIS attempts to process it, not whether the entire message will succeed or fail. When issues arise, they are communicated through ERR segments in the ACK, with severity determined later in Section 3.3, Acknowledgement Message Profile.

The following interpretations apply:

R (Required) The element is expected to be populated during normal operation, and the receiving system attempts to process it when present. If the element is missing or unusable, the receiving system SHALL indicate the issue using an ERR segment. For example, when a submitting system sends a VXU, the IIS, as the receiving system, SHALL indicate the issue via ERR.

RE (Required but may be empty) The element should be populated when data are known. If present, the receiving system processes the element meaningfully. If omitted, the receiving system continues processing and may indicate the omission via an ERR segment, depending on local policy and data importance. For example, when a submitting system sends a VXU, the IIS, as the receiving system, may indicate the omission via ERR.

O (Optional) The element may be populated by the sender at its discretion. If present, the receiving system processes the element; if absent, no further action is expected. For example, when a submitting system sends a VXU, the IIS, as the receiving system, may process the element and an ERR may be included if the data was invalid.

C (Conditional) Conditional usage indicates that the applicability of the element depends on a defined condition. Once the condition is evaluated for a specific data instance, the conditional resolves to a concrete usage (e.g., R or O). For example, a lot number may be required for administered vaccinations but optional for historical ones. Conditional usage is a documentation mechanism; at runtime, the element always has a specific usage. This guide intentionally limits its reliance on conditional expressions, using separate message profiles and segment flavors instead where appropriate. This approach simplifies implementation and reflects feedback that complex conditional logic can be difficult for implementers to interpret.

X (Not Supported) The element shall not be populated by the sender. If present, the receiving system shall not process, store, or use the data. For example, when a submitting system sends a VXU containing an unsupported element, the IIS, as the receiving system, does not process, store, or use that data.

IX (Ignored) The element may be populated by the sender, but the IIS does not read, validate, or store the data. IX is not defined in the national guide. The designation is defined here as a convention that local implementation guides may use to document elements that are unsupported by a receiving system, without treating their presence as an error. Unlike X, it is not an error for data to be sent in an IX element, but senders should expect the data to be ignored entirely. For example, a local jurisdiction's guide may designate a specific element as IX if its IIS does not support that data element; a submitting system may include data in that element, but the IIS will not process it and not generate an ERR segment.
