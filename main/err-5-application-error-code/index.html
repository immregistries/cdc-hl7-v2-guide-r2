3.3.3.4 ERR-5: Application Error Code

Quality review 2 issues · 3 warnings · 1 note

Findings from automated and editorial checks, for the authors and reviewers. Not part of the guide.

  • Issue TAB Acknowledgment (ACK) Messaging: Updated Specifications and Guidance (ERR-5 Values): Missing. The narrative refers to "a national code set" but never names it, links to it, or includes it. The guide's own SHALL, SHOULD, and MAY (implement High, Medium, and Low priority codes) cannot be followed without it, because the narrative does not say which codes have which priority. The value set bound to ERR-5 in chapter 7 (HL70533_IZ01) is the 2017 code list plus 5044 and has no priorities. This site now shows the set (version 2026-07-06, pending publication by AIRA) as Appendix D, linked from 3.3.3.4; the narrative still needs to name and cite it.
    MissingAction: Narrative and IGAMT
    TAB ERR-5 carries a code from the national code set "as provided in the National Set of ERR-5 Application Error Codes for Immunization ACK Messaging".
    Recommendation Name and cite the national set in 3.3.3.4 and Resources (once AIRA posts it), and carry Appendix D, the codes with their priorities, into the guide.

  • Issue Statement s1 TAB Acknowledgment (ACK) Messaging: Updated Specifications and Guidance (ERR-5 Specifications): Conflict. The narrative matches the TAB, but the profiles do not allow it. HL70533_IZ01 is marked closed and has 67 codes (1-7, 2000-2701, and 5044). The national set (Appendix D) has 280: 213 of them, including 16 of the 20 High priority codes (such as 2018, vaccination date before birth, and 3019, date of birth missing), are not in the value set, so an IIS that meets the SHALL sends ERR-5 values the profile does not allow. The value set also still lists 2202, 2203, and 2502, which the national set has deprecated.
    ConflictAction: IGAMT
    TAB IIS SHALL implement High priority codes, SHOULD implement Medium priority codes, and MAY implement Low priority codes.
    Recommendation Update HL70533_IZ01 in IGAMT to the national set (or make it open and point to the national set), and record the version of the set that the guide adopts.

  • Warning MIROW guide Data Quality Assurance in Immunization Information Systems (Comparison of past MIROW data quality best practices (published with the guide)): Conflict. The national ERR-5 code set cites MIROW rules by their old numbers. Seven codes cite numbers that now mean something else: 2001 (BR 118, now BR115), 2010 (BR 116, now BR126), 2016 and 2017 (BR 119, now BR128), 2018 (BR 101, now BR111), 2019 (BR 103, now BR113), and 2022 (BR102, now BR114). Three more cite numbers that do not match the code's content: 2214 cites BR 114 for the provider-type check (old BR113, now BR168), 2215 cites BR 130 for the license date range (old BR120, now BR133), and 2217 cites BR 113 for the patient name type. Code 2023 keeps the retired 14-day submission rule, which MIROW and this guide now put at 24 hours. Code 2024 cites a rule (medical contraindication) that MIROW retired.
    ConflictAction: CDC decision
    Best practice The 2022 guide renumbered the business rules of the retired 2008 and 2013 data quality guides; its companion comparison maps each old rule to its replacement or marks it retired. For example, old BR118 (date after lot expiration) is now BR115, BR119 (route and site) is BR128, and BR115 (submission within 14 days) became BR106 (within 24 hours).
    Recommendation Ask AIRA, which maintains the code set, to cite the 2022 rule numbers (written "DQA2022 BRnnn"), to align code 2023 with the 24-hour expectation, and to decide whether code 2024 is still needed.

ERR-5 communicates the specific nature of an issue using a code from a national code set, supplementing ERR-2 (location) and ERR-4 (severity) by answering the question of what the problem was. Codes are organized into ranges by issue type, including legacy HL7 v2 codes, conflicting data, inappropriate data, invalid data, lookup failures, message construction issues, missing data, processing errors, data sharing or consent restrictions, and missing or invalid endorsed data elements, among others. Codes in the missing- and invalid-data ranges use matching endings to pair each data element across both ranges.

Implementing a code means that when the IIS detects the corresponding condition, it returns that code in ERR-5. This does not, by itself, determine how the underlying data is treated (e.g., whether it is accepted or rejected) or what ERR-4 severity is assigned; those determinations remain governed by local policy and are conveyed independently through ERR-4.

If a concept needed by an IIS is not already represented in the national code set, implementers should coordinate with the guide's maintaining organization to have a new code added, rather than defining a local code. Locally invented codes are discouraged, as they increase burden and inconsistency across interfaces. Submitters should expect that the national ERR-5 code set will continue to expand as new data quality concepts are identified.
