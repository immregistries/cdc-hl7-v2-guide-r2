Query/response interactions require additional safeguards beyond basic authentication and encrypted transport used in submission workflows: queries expose patient data directly and can be repeated at scale if not properly constrained. Security controls must therefore focus on limiting misuse, detecting abnormal behavior, and preventing unintended disclosure.

To prevent unauthorized or unintended record retrieval, IIS SHALL NOT return patient records based solely on a single identifier. Even when strong identifiers such as a registry identifier (State Registry ID, SR, or Local Registry ID, LR) or Medical Record Number are supplied, the IIS SHALL verify that additional patient attributes, such as name and date of birth, are sufficiently consistent to support a valid match.

Conformance statements

  1. SHOULDIIS SHOULD implement rate-limiting controls to manage query volume and protect system availability. These limits should be configurable and proportional to expected usage patterns, allowing IIS to balance responsiveness for clinical queries with protection against excessive or inefficient access.s1
  2. SHALLIIS SHALL log all query activity in sufficient detail to support investigation, monitoring, and compliance. Logs should enable detection of unusual query volume, repeated access patterns, or other indicators of inappropriate use.s2
  3. SHOULDIIS SHOULD implement active monitoring and alerting to identify anomalous query behavior, including sustained high-frequency querying or access patterns inconsistent with normal clinical workflows.s3
  4. SHOULDIIS SHOULD carefully consider the security properties of externally exposed patient identifiers. Sequential or otherwise predictable identifiers increase the risk of enumeration and misuse. IIS SHOULD use randomly generated, non-guessable identifiers for state registry IDs exposed through query responses or other external interfaces.⚑s4
