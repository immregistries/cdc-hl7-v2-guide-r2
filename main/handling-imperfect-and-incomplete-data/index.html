This guide does not prohibit the exchange of incomplete, implausible, or low-quality data. Messages may be syntactically conformant yet clinically implausible, or clinically valid yet missing required elements due to data unavailability. These scenarios are expected and must be handled through appropriate programmatic processes rather than rigid message rejection.

The purpose of this guide is to define the boundary between conformant and non-conformant implementations, not to prevent data exchange.

Conformance statements

  1. SHOULDReceiving systems SHOULD accept and store data that is incomplete but operationally useful, unless prohibited by local policy.s1
  2. SHALL NOTReceiving systems SHALL NOT use this guide as the sole basis for rejecting data when doing so would result in unnecessary data loss.s2
  3. SHOULDReceiving systems SHOULD distinguish between message structure compliance, system capability, and data correctness when assessing conformance.s3
