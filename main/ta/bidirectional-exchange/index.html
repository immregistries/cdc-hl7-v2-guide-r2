Bidirectional Exchange

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

6 questions. Findings: none
Not yet assessed

What was asked

Questions in this section ask what "bidirectional" exchange means, how an IIS should start returning data to providers (HL7 v2 QBP/RSP versus CCD push or other mechanisms), where query capability should live (IIS or HIE), and how data flowing back to EHRs interacts with reconciliation and with patient-supplied updates. A recurring theme is that the HL7 v2 QBP/RSP query model is the nationally certified, recommended path, and that EHR-side reconciliation should not depend on optional response elements such as lot number.

Definition and Scope

What is the definition of bidirectional exchange?

Asked 1× · 2017 · VXU/QBP · Answered

Answer given

There is no official definition. Meaningful Use Stage 3 (MU3) considers it to be an EHR's capability to both submit (VXU) and query (QBP).

Choosing an Approach: HL7 v2 Query vs CCD and Other Options

Should an IIS return immunization data to practices using CCDs (pushed to sites, or returned from a query) instead of implementing true HL7 v2 QBP/RSP bidirectional exchange?

Asked 2× · 2021 · QBP/RSP · Answered · Related: Query & Response Behavior

Answer given

AIRA recommends going directly to a true bidirectional, immediate-response HL7 v2 QBP/RSP interface, the current national guide. EHRs have been certified to do this, so they should be able to use it immediately. AIRA was not aware of any IIS sending back CCDs and had not seen questions or experience with them. AIRA can help with documentation on the standards, testing tools, a reference implementation, example code and measurement reports.

Technically an IIS could create a CCD containing immunization information and send it to an EHR. However, this is not a typical way to share immunization data across the community, and it would mean onboarding with a new, atypical standard. Questions to answer first: - Can the EHRs actually accept and use a CCD? Their ability to read and use CCD content is limited, and often they only display it. - How standardized does the CCD need to be? - How would it be transported, for example through an existing HIE conduit? - What would trigger sending one?

The HL7 v2 query model is a "pull": any authorized EHR can query any patient. A CCD is a "push", so the IIS would have to decide which EHR gets each update (probably only those that submitted a vaccination) or build a request mechanism. CCD is an HL7 v3 standard. v3 interfaces typically take about three times longer to implement than v2, and the community has largely moved away from it. Implementing the HL7 v2 query interface would probably be faster. Even a query interface that only supports querying by MRN would be quick to set up and very valuable to providers. Sending flat files back to clinics is another, simpler option.

An IIS has two HIEs (a statewide HIE and an in-house HIE created for COVID). Where should bidirectional query capability be implemented: in either one, or both?

Asked 1× · 2021 · QBP/RSP · Answered · Related: Transport/Connectivity

Answer given

From the outside, either would work, as long as the one used provides a real-time view of the patient's immunization record and evaluation/forecast. Nearly all IIS have implemented query directly, but at least one uses its HIE to handle query requests.

Reconciliation and Data Flowing Back to Providers

Is there guidance on how an EHR should automatically deduplicate/reconcile vaccines (e.g., COVID) received from the IIS, when the EHR's logic relies heavily on lot number?

Asked 1× · 2021 · RSP · Answered · Related: RXA-15, Patient Matching & Deduplication

Answer given

IIS must auto-reconcile everything. They should use the best practice guide "Vaccination Level Deduplication in Immunization Information Systems" (2006; the methodology is still sound), in whole or in part, for every transaction. It is unclear how much of it applies directly to an EHR.

A caution about logic that hinges on lot number: the query response profile used for Meaningful Use does not require the IIS to return lot number even when it has it. Lot number is optional. Nearly all IIS return it, but not all do, so EHR reconciliation should not depend on it.

Providers resending older demographic or vaccination data are overwriting patient-portal updates in the IIS. Could the IIS push updated patient information to providers in an HL7 message, has any jurisdiction done this, and is there another way to keep patient-supplied updates from being overwritten?

Asked 1× · 2022 · VXU · Answered · Related: Patient Matching & Deduplication, Data Quality & Validation

Answer given

It helps to separate patient-level data from immunization-level data. One jurisdiction is known to push updates for vaccination events. Providers may be interested in immunization-level updates. They are much less interested in demographic updates, because they rarely rely on the IIS for current demographics, so pushing demographic updates may have little value.

The other option is to adjust the IIS business rules for accepting demographic data. If the IIS believes the consumer-supplied data on file is better than provider data, it is well within its rights to keep it. No HL7 rule requires an IIS to overwrite existing data with newly received data.
