Transport & Connectivity

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

53 questions. Findings: none
Not yet assessed

What was asked

Questions in this section are about how HL7 v2 immunization messages move between submitters (EHRs, HIEs, middleware, gateways) and IIS. Most of them concern the CDC SOAP Web Service (the "CDC WSDL"): where the specification lives, whether it is required, how to implement it exactly (operation names, namespace, faults), how to encode the HL7 payload inside SOAP XML, and how to handle segment terminators.

IG clarifications suggested when the TA records were consolidated (6)
  • Publish the CDC WSDL as a directly downloadable file, and state the expected SOAP version and Content-Type header explicitly.
  • Clarify segment terminator handling inside the SOAP hl7Message element (CR versus LF), require receivers to accept CR, LF or CR+LF, and state that intermediaries must not alter the HL7 content.
  • Define the meaning of the WSDL username/facilityID (submitting organization/system, not an individual user) and tie WSDL credentials to MSH-4, with MSH-22 for responsible organizations, as in the draft next-IG language.
  • Allow authentication by any system before the IIS acts on a message, give guidance for HIE/intermediary scenarios, and require intermediaries to relay the IIS ACK unchanged to the original submitter.
  • Document alternatives to username/password (OAuth, client certificates/mTLS, multi-factor), which the current transport guidance does not address.
  • Add retry guidance that separates transport failures (backoff, limits, suspend/throttle) from application-level rejections (no automatic resend of unchanged messages).

Which specification and documentation cover web service (SOAP) transport of HL7 immunization messages to an IIS, and does the CDC WSDL support immunization messaging?

Asked 4× · 2018–2023 · general · Answered · Related: Conformance Testing & Validation Tools; Acknowledgement & Error Handling; Query & Response Behavior

Answer given

IIS use a community standard: the CDC SOAP web service transport specification (https://www.cdc.gov/vaccines/programs/iis/technical-guidance/soap/services.html). The CDC WSDL defines the SOAP web service transport used to exchange HL7 v2 immunization messages between EHRs and IIS. It is in the appendix of the Formal Specification. Endpoints, credentials and onboarding come from each IIS.

NIST has a SOAP connectivity tester (https://hl7v2-iz-r1-5-testing.nist.gov/iztool/#/soapConn) that implementers can use to verify they support the CDC WSDL correctly. It is part of the Immunization Test Suite, but the SOAP test works for any HL7 v2 message because it only checks that the payload is HL7 v2. Immunization content is checked in the suite's Context-Free and Context-Based sections. Passing these tests means a client should be in good shape to connect at the transport layer.

Other reference documents shared in response to this question: Guidance for HL7 Acknowledgement Messages to Support Interoperability; IIS Functional Guide, Vol. 1: Query and Response; and SOAP Web Services Guidance and Specifications.

People talk about "SOAP" and "HTTP" connections when moving providers from an intermediary to point-to-point connections with the IIS. Are these two separate methods, or related?

Asked 1× · 2023 · general · Answered

Answer given

They are related. SOAP sends its information over an HTTPS connection, so a SOAP connection uses both SOAP and HTTPS. An "HTTP" connection means HTTP is used directly, with no additional standard defining the request. SOAP adds a standard framework for formatting the request and data, which makes connections smoother for submitting systems. Middleware users (e.g., Rhapsody) use these terms as shorthand for connection types. For the IIS, they should use a SOAP connection (the CDC WSDL), not a plain HTTPS connection.

Implementing and Verifying a CDC WSDL Endpoint

Must the operation names and parameters in an IIS's WSDL match the CDC WSDL exactly?

Asked 1× · 2020 · general · Answered

Answer given

Yes. Operation names and parameters must be exactly as defined in the CDC WSDL. Otherwise EHRs must build special operations just for that IIS. For example, the connectivity test operation must be named connectivityTest (lowercase c) with a single parameter echoBack, and names must match exactly, including case. AIRA tests three things: connectivityTest, submitSingleMessage, and the SecurityFault. Publicly available, validated endpoints (e.g., some IIS test WSDLs) can be used as references.

How can an IIS add a new operation (e.g., submitMultipleMessages()) to the CDC WSDL as an extension, given compile problems caused by references to the CDC namespace?

Asked 1× · 2021 · general · Answered

Answer given

Extensions are generally left to implementers, as long as the CDC-defined operations, faults, etc. are not changed and the WSDL stays backwards compatible. The simplest approach is to add the new operation to the IIS's copy of the CDC WSDL and present it to the tooling stack as if it were part of the CDC WSDL base. Anyone retrieving the WSDL would see an extra operation, but this does not affect the other operations. AART testing checks the operations, not the WSDL itself, and would not notice the extra operation. Alternatively, a second WSDL could be created that leaves the CDC WSDL as is, though this would mean two different endpoints.

An IIS updating its CDC web service will drop Base64 encoding of the HL7 payload and wants to require senders to wrap the message in a CDATA section. Is that okay?

Asked 1× · 2019 · general · Answered

Answer given

CDATA and XML escaping are part of the XML encoding standard that SOAP is built on, not part of the CDC WSDL or SOAP standards, which is why the CDC WSDL documentation does not detail them. It is fine to recommend CDATA for encoding the HL7 data, but the IIS should still support either method: CDATA, or escaping characters with XML entities (e.g., `&` as `&amp;`).

How should HL7 reserved characters be escaped when an IIS returns RSP/ACK messages inside the CDC WSDL submitSingleMessageResponse? (One IIS was double-escaping, e.g., `MSH|^~\&amp;amp;|` and O'Brien as `O&amp;#39;Brien`.)

Asked 1× · 2024 · RSP, ACK · Answered · Related: MSH-2, PID-5

Answer given

Only a single XML escape is needed. The ampersand in MSH-2 should appear as `&amp;` in the XML, not `&amp;amp;`. The extra "amp;" causes some parsers to misread the HL7. Escaping the apostrophe as `&amp;#39;` also parsed poorly (AIRA's test tooling could not interpret it). A simpler, broad approach is to wrap the whole HL7 message in a CDATA section, e.g. `<return><![CDATA[MSH|^~\&|...rest of message...]]></return>`. CDATA removes the need for character-specific escaping, so values such as "&" and O'Brien can be returned as-is without complicated escaping logic for HL7 embedded in XML.

Is the CDC WSDL submitSingleMessage operation only for one message (one patient)? Should an IIS accept multiple HL7 messages, possibly of different types (e.g., VXU, QBP, VXU), or batches in one payload?

Asked 2× · 2021–2024 · VXU, QBP, general · Answered · Related: Message Structure & Cardinality (FHS/BHS batch)

Answer given

The operation is "submit single message", so senders should send only one message per call. An IIS may choose to process more than one message per call if it wants. An IIS that wants only one may return an error such as "too many messages" or the MessageTooLargeFault exception. A payload can be too large by number of characters or by number of messages, i.e., anything too big for the IIS to process.

The standard does not rule out batch submissions. "Batch" can mean two or more messages in the same request, messages wrapped in BHS/BTS, or a series of single messages sent individually over the same period. Batch has not been standardized, largely because submitSingleMessage works efficiently: with multi-channel connections and connections held open, sending one message at a time can be very efficient.

Segment Terminators in SOAP Payloads

In CDC WSDL testing, HL7 segments were sometimes separated by line feeds instead of carriage returns, and the IIS returned a very generic error. Which end-of-line characters should separate HL7 segments in a SOAP payload, and how should an IIS handle the alternative?

Asked 1× · 2024 · general · Answered · Related: Message Structure & Cardinality (segment terminators)

Answer given

The HL7 standard requires each segment to end with a carriage return (ASCII 13, \r, #xD). The XML standard that SOAP is built on normalizes end-of-line characters to a line feed (ASCII 10, \n, #xA). In practice the two get mixed up, and HL7 sometimes arrives separated by XML line feeds. An IIS that accepts only carriage returns is not off-standard, but it should either give clearer error messages when this happens or, as most IIS have done (based on AIRA testing), be more forgiving and accept the other line-ending characters. See Appendix B of the CDC WSDL transport specification. This is not required to pass AART tests. The IIS in this case later fixed it.

An IIS returns ACK and RSP messages over the CDC WSDL without segment terminators, so all segments appear on one line. Is this acceptable?

What does the CDC WSDL "username" represent? Should an IIS issue a unique SOAP username/password per site or organization, or one per submitting system (e.g., one for an HIE or a multi-tenant EHR)?

Asked 2× · 2022–2025 · QBP, VXU · Answered · Related: MSH-4, MSH-22, RXA-11

Answer given

Earlier guidance (2022): The CDC WSDL uses the term "username", but it is meant to be a unique ID given to the site doing the query (the hospital, clinic, or physician practice group), not to an individual user. The IIS would want to assign a "username" to each unique system that connects to it. The IIS's technical team appeared to be on the right track.

Later guidance (2025), on an IIS proposing to require unique SOAP credentials per organization (with unique MSH-4 per site, and RXA-11.4 for inpatient departments) instead of one global credential per EHR: AIRA did not believe separate credentials per site would give more protection, and they may cause operational problems and pushback from EHRs that increasingly use multi-tenant hosting. In a cyber incident involving one site, you would most likely want to cut off all communication from that EHR system (which may serve many organizations), and a single connection makes that easier to find and switch off. Realistically, an incident would be handled with non-IIS measures such as network blocking, because disabled credentials at the IIS still let traffic reach the IIS and database for authentication checks. Managing many username/password pairs on what is effectively one client system is also a burden and increases risk by storing many credentials in one place.

Draft material for the next HL7 v2 IG defines a submitting organization as one software system instance (EHR, gateway, or service bureau node) sending over one authenticated connection, possibly on behalf of other responsible organizations when authorized during onboarding. Authentication happens at the transport layer (CDC WSDL username/facility ID, client certificate, or whitelisted IP), and MSH-4 carries the same organizational identity. Draft rules: systems SHALL populate MSH-4 in all VXU and QBP messages to identify the submitting organization. The IIS SHALL authenticate via CDC WSDL credentials and confirm they correspond to MSH-4. A single MSH-4 MAY be authorized to submit for multiple responsible organizations identified in MSH-22. WSDL credential values MAY differ from the MSH-4 string, but the IIS SHALL document the mapping and SHALL NOT rely only on transport headers to infer other roles such as MSH-22 or RXA-11.

Flagged when consolidated: The 2022 answer ties the username to the "site" (hospital, clinic, practice group) and also to "each unique system". The 2025 answer and draft IG language tie it to the submitting software system instance. Reconcile the wording in the FAQ.

Messages pass through a state HIE before reaching the IIS. Where should the CDC WSDL identification fields (username, password, facility ID) be validated: in the IIS or in the HIE? Is it acceptable to pass IIS-assigned credentials back to the HIE for validation?

Asked 1× · 2020 · general · Answered · Related: MSH-4, MSH-22

Answer given

The CDC WSDL transport specification does not define how these fields are implemented. It only says there are three identification/authentication fields that may be used, and the IIS can assign the values submitters should send. The security requirement is that the credentials are checked at some point before the IIS acts on the message. They do not have to be checked by the first system in the network path (the Internet and internal networks also carry the messages unauthenticated). So if the HIE exposes a CDC WSDL endpoint that accepts the values and forwards them directly to the IIS, it is perfectly acceptable for the IIS to be fully responsible for verifying identity (like airport security checking identity at the gate rather than in the parking lot).

If management requires the HIE layer to authenticate, there are two options. (1) The HIE is fully responsible for managing and assigning credentials. Once it authorizes a sender, it passes the right tokens to the IIS so the IIS knows who the authorized party is (some IIS do this by putting the facility ID in MSH-4/MSH-22 or in the CDC WSDL fields). This requires the HIE to manage all credentials and coordinate facility identification with the IIS. (2) Synchronize credentials from the IIS back to the HIE. This is not ideal and actually reduces security: credentials are stored in more than one place and transmitted regularly, they are hard to keep in sync, and troubleshooting authentication faults becomes harder (did it fail at the HIE or the IIS?).

SOAP Faults and Transport-Level Errors

CDC WSDL transport testing reported that the SecurityFault child elements are not in the SecurityFault namespace. How should the SecurityFault be structured?

Asked 1× · 2024 · general · Answered · Related: Conformance Testing & Validation Tools

Answer given

AIRA checked the result in SoapUI and in the NIST tooling directly. Both showed the same returned structure: the soap: prefix was present, but the SecurityFault child elements were not in the SecurityFault namespace (urn:cdc:iisb:2011). Connectivity Test and Submit Single Message pass because they lack the nested structure that SecurityFault needs. The child elements (Code, Reason, Detail) must be qualified in the urn:cdc:iisb:2011 namespace, either by giving them the same prefix as SecurityFault (e.g., ns2:Code, ns2:Reason, ns2:Detail) or by using default namespace declarations instead of prefixes. For example, declare xmlns="urn:cdc:iisb:2011" on SecurityFault so unprefixed Code/Reason/Detail inherit it, inside a SOAP 1.2 Fault with Code/Value = Sender, Reason/Text, and Detail. Example: SecurityFault Code 10 with Detail "Invalid Username or Password". The NIST IZ tool (hl7v2-iz-r1-5-testing.nist.gov/iztool, SOAP connectivity tests) can test an endpoint directly against the CDC WSDL specification.

If a backend API used by the IIS SOAP service fails (e.g., timeout, too many requests, HTTP 4XX-5XX), should the IIS return a Z23 ACK or a SOAP fault?

Asked 1× · 2022 · ACK · Answered · Related: MSA-1, ERR, Acknowledgement & Error Handling

Answer given

Rule of thumb: if the problem is in processing the HL7 message, return an HL7 response. If the problem is with transport, authentication, or the SOAP envelope, return a SOAP Fault. These errors mean the IIS cannot process the message for reasons unrelated to its content, so this is probably a Z23 ACK with MSA-1 = AR (one of the rare appropriate uses of AR), with as much detail as possible in ERR segments so the sender knows what to do. The IIS has a lot of discretion here, and AIRA cannot test these conditions. Either approach is acceptable as long as the message is clear and the receiver knows what to do.

An EHR vendor or provider cannot connect to the IIS CDC WSDL web service because of problems with its SOAP request. What does a correct request look like, and how should the IIS troubleshoot it?

Asked 2× · 2021–2023 · VXU, general · Answered · Related: Conformance Testing & Validation Tools; Onboarding & Interface Testing

Answer given

In the cases recorded, the SOAP request was malformed (in one case probably an older SOAP version). A SOAP request that sends a VXU via the CDC WSDL consists of: (1) the start of the SOAP Envelope (and Body); (2) the operation element, submitSingleMessage; (3) the operation's parameters: username, password, facilityID, and hl7Message (the VXU content); (4) the end of the operation element; and (5) the end of the SOAP Body/Envelope. Credentials go in the SOAP body as parameters of submitSingleMessage, with placeholders such as insert_your_username / insert_your_password / insert_your_facility_ID.

To troubleshoot, ask the provider for the redacted SOAP wrapper and the exact error/response returned, compare them against the CDC WSDL specification, and point the provider and vendor to the NIST IZ test tool (which can test SOAP envelope structure), the CDC SOAP specification, and AIRA's transport training videos. AIRA has also sent vendors an example of a correctly formatted request.

Is there a standard for how many HL7 messages per time period an IIS should be able to process without performance degradation? Should capacity be based on current volume or a set standard?

Asked 1× · 2025 · VXU, QBP, general · Answered

Answer given

There is no official national standard for IIS message volume capacity. In the Measurement & Improvement initiative, the performance standard is that 95% of responses return within 5 seconds. This is a low bar meant to catch systemic underperformance, and it is tested in pre-production with controlled traffic. Production systems should aim to be faster; about 1 second is typical in normal use. Rather than basing targets strictly on current volume, build a baseline performance profile: monitor average and percentile response times for updates and queries, track performance over time and at peak hours, and watch for degradation as volume grows. Degradation usually means better provisioning is needed (compute, database, or interface engine changes). AIRA's Security Guidance recommends capping query volumes per site, especially for low-security endpoints, so one provider cannot degrade performance. The TAB on Scenarios for Updates and Queries encourages coordination with high-volume partners (e.g., a hospital querying its whole population at once). Acceptable performance is ultimately up to each IIS, but most will want to exceed the national minimums.

Mass vaccination sites may administer 50,000+ doses a day. Have IIS raised concerns about VXU and query volume, and how should submitters reduce the impact?

Asked 1× · 2021 · VXU, QBP · Answered · Related: Query & Response Behavior

Answer given

AIRA asked IIS vendors and a few states with standalone IIS. None raised specific concerns, though volume increases are always a concern and they appreciated the warning. Recommendations: (1) Keep communicating with IIS as usual. (2) 50,000 doses a day is not a show-stopper by itself, but queuing all 50,000 and sending them in one batch at the end of the day is a problem, so spread submissions across the day. (3) Control query patterns to avoid repeat queries for the same patient. Sending 50,000 queries at once the night before can cause problems, especially with multithreaded clients. (4) Tell the IIS program staff ahead of time when high-volume sites will start and what volumes to expect. (5) Impact is relative: a very large IIS may barely notice the increase, while smaller IIS will feel it more. IIS had been preparing for higher loads, but actual loads are hard to predict.

EHR vendors vary widely in retry behavior when submitting to an IIS, from a few retries before giving up to resending the same message 10,000-20,000 times, including messages the IIS already rejected for data quality reasons. Is there guidance on appropriate HL7 retry logic?

Asked 1× · 2026 · VXU, ACK · Answered · Related: Acknowledgement & Error Handling; MSA-1; ERR-4

Answer given

There is no detailed broad-exchange standard yet, and AIRA is considering adding one. Suggested language: manage automatic retransmission at the destination/interface level rather than per queued message. When a transport/connectivity failure prevents receipt of an application ACK, the sender should keep the message, temporarily suspend or throttle submissions to that destination, and retry transient failures at progressively longer intervals (exponential backoff) within reasonable limits. Configuration, authentication or certificate failures should be treated as needing investigation, not continued retry. Queued messages may resume once connectivity is restored.

The IZ Gateway has its own retry strategy guidance. AIRA's updated IIS Security Guidance includes a business-continuity recommendation that partners queue submissions (e.g., VXUs) until an application-level ACK is received, optionally with exponential backoff. That guidance covers outages, not data quality rejections.

Resending a message that was already rejected only produces the same ACK. AIRA's 2015 ACK guidance and the 2026 ACK TAB cover this: if the IIS returns at least one ERR segment with severity "E", the sender must fix the problem before resubmitting. The IIS can point vendors to those documents.
