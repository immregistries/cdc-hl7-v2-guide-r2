What was asked

Questions about the PID segment center on patient identity data used for matching and deduplication: patient identifiers and assigning authorities (PID-3), name handling including placeholder newborn names, aliases and special characters (PID-5), administrative sex vs. gender identity (PID-8), and race/ethnicity coding including unknown values and the OMB SPD 15 revision (PID-10/PID-22). Other recurring themes are phone number use/equipment codes (PID-13), address edge cases (PID-11), multiple birth fields (PID-24/25), and how strictly an IIS may enforce RE fields and what ERR-4 severity to use. Much of the guidance evolved over time, moving from ad hoc answers to SISC-approved Technical Advisory Bulletins (TABs).

IG clarifications suggested when the TA records were consolidated (10)
  • **PID-3:** Document how identifiers and assigning authorities are exchanged, including the common practice of qualifying MRNs by submitter, recommended PID-3.4 values for MRNs (facility vs jurisdiction), and MRN handling in bidirectional query/RSP.
  • **PID-5:** Define allowable character sets and handling of diacritics/punctuation; define an approach for patients with no first name; define name type definitions (L vs C) and their use in QBP vs VXU; add a distinct designation for temporary/newborn names (e.g., NB) and timing expectations for sending VXUs before a legal name exists.
  • **PID-8:** Allow HL70001 value X; correct the Table 0001 description ("self-reported gender") that conflicts with Administrative Sex; define a patient-level OBX approach (e.g., LOINC 76690-7) and value sets for gender identity/sexual orientation; define how value sets may evolve.
  • **PID-10 / PID-22:** Clarify the comment that race and ethnicity share a table (not interchangeable placement); formally document CDCREC extension codes UNK, ASKU, PHC1175 and the CE.3 coding system for them; restate that unrecognized race/ethnicity codes are treated as empty, not rejected; address OMB SPD 15 (MENA 2118-8 as top-level, combined collection vs separate PID-10/PID-22 messaging); define how local codes may be added to user-defined tables; align NIST validation.
  • **PID-11:** Guidance for non-US addresses (country code from HL70399, optional state) and international phone numbers; where apartment/unit belongs (XAD.1 vs XAD.2, per USPS Pub 28 / Project US@); prohibit placeholder text for unknown/no address and discourage rejecting messages lacking PID-11; prohibit formatting characters (CR/LF escape sequences) in address components; resolve the Birth State inconsistency (core data elements point to PID-11 BR/BDL while an example uses PID-23) and state IIS may ignore birth addresses.
  • **PID-13 / PID-14:** Update HL70201/HL70202 guidance: PRN is the primary contact number and may be paired with any equipment type including CP; PH/CP are not reliable; clarify validator treatment of legacy XTN.1 kept for v2.3 compatibility.
  • **PID-15:** State clearly that the CWE.3 coding system is ISO6392 (not HL70296), that ISO 639-2 codes are lower case and case sensitive with case-insensitive acceptance recommended, and whether ISO 639-3 codes (e.g., 'cmn') are allowed.
  • **PID-23:** Clarify whether Birth Location has a defined message location.
  • **PID-24 / PID-25:** Clarify PID-25/QPD-11 usage when PID-24 = 'N', correct the appendix where the PID-24/PID-25 descriptions are reportedly swapped, and explain the RE expectation and importance for matching multiples.
  • **PID-29 / PID-30 / PD1-16:** Centralize guidance on deceased status across these fields.

PID-1 Set ID - PID

Why is PID-1 (Set ID) required, and is it a concern if an IIS does not require or enforce it on incoming VXUs?

Asked 2× · 2019–2026 · VXU/RSP · Answered · Fields: PID-1 · Related: Data Quality & Validation

Answer given

PID-1 is required because the base HL7 standard requires it; it is not important for IIS (2019).

Later guidance (2026) elaborated: PID-1 has very little operational value. A VXU can contain only one PID segment, so PID-1 is almost always 1; even in an HL7 batch each VXU has a single PID. PID-1 matters mainly in RSPs that return multiple candidate patients. Many IIS do not require or validate PID-1 without causing interoperability problems, so it is fine to ignore a missing PID-1 on incoming VXUs. Systems must still populate it in RSPs per the standard.

What value belongs in PID-3.4 (assigning authority) for a medical record number? One IIS asks submitters to use their IIS-assigned facility code, while another asks for a fixed state code (e.g., 'NYA'). Which is correct?

Asked 1× · 2021 · VXU · Answered · Fields: PID-3 · Related: PID-3.4, PID-3.5, RXA-11

Answer given

PID-3.4 identifies the organization that assigned the ID. For example, if PID-3 carried a driver's license number (identifier type DL in PID-3.5), the number is useless without knowing the issuing state, so the state would go in PID-3.4. For an MRN (type MR), the assigning authority would not be the state unless the state assigned the ID; it would normally identify the hospital, clinic or pharmacy that assigned the MRN. The national standard does not define the specific value, but requiring in a local guide that it be the ID the IIS assigned to the facility makes sense and is consistent with other IIS. A fixed state code might make sense for a state registry ID (SR) but not for an MRN.

How should an IIS manage MRNs and assigning authorities in PID-3 when assigning authorities vary widely and submitters send multiple MRNs per patient? Should it keep a preapproved list of assigning authorities, use its own submitter/provider ID as the MRN qualifier, and what strategies help standardize MRNs and sending-facility identification for bidirectional exchange?

Asked 3× · 2021 · VXU/QBP · Partly answered · Fields: PID-3 · Related: PID-3.4, PID-3.5, Patient Matching & Deduplication, Bidirectional Exchange, MSH-4

Answer given

There are two models.

  1. ID type + assigning authority. HL7 defines identifiers by type and assigning authority, designed for hospital networks where an ADT system and administrator define the recognized ID types and assigning authorities. Applying this to IIS is hard because IIS generally lack authority to define ID types and assigning authorities statewide, so each submitter and the IIS must negotiate values, which is the problem the asking IIS encountered.
  2. Submitter ID method (how most IIS work in practice). The MRN is only considered valid within the context of a single submitter. The IIS stores a unique MRN for each patient per submitting organization, using the identity of the submitter rather than the HL7 assigning authority as the qualifier. Submitters are not expected to know or coordinate each other's MRNs, so an organization can query using MRNs it previously submitted but not another organization's MRNs.

IIS ask submitters to identify the MRN with type MR and, with a few exceptions (state registry ID, Medicaid number, SSN), ignore other ID types; nearly all IIS require at least one ID to be the MRN.

How should PID-3 (Patient Identifier List) be populated in an RSP?

Asked 1× · 2017 · RSP/VXU · Answered · Fields: PID-3 · Related: Query & Response Behavior, MSH-22, RXA-11

Answer given

Best practice starts with submission (VXU): the IIS should be able to recreate (store, map, etc.) the values submitted in PID-3.1, PID-3.4 and PID-3.5, associated with the provider as the EHR knows them, so that in the response it can recreate all of PID-3, not just PID-3.1. ('Recreate' is used rather than 'store' to avoid being too prescriptive.)

As a secondary option until the best practice can be implemented, or when the data cannot be recreated (legacy data, not submitted), the IIS should return the ID submitted in PID-3.1 but may need to substitute values in 3.4 and 3.5. For PID-3.4 (assigning authority), ideally determine with the provider or EHR vendor which value to use; otherwise use something similar to the organization ID sent in MSH-3, MSH-22 or RXA-11.4 on submission. For PID-3.5 (identifier type), again ideally agree with the provider or vendor; otherwise the most commonly used value across the U.S. is MR, though others such as PI or PT are seen.

Which MRN should an IIS return in RSP PID-3? If an EHR queries with an MRN (QPD-3) that the IIS has not linked to the matched patient, should the IIS echo the queried MRN back?

Asked 2× · 2020–2022 · RSP/QBP · Answered · Fields: PID-3 · Related: Query & Response Behavior, QPD-3, Patient Matching & Deduplication

Answer given

Only return identifiers in PID-3 that the IIS actually associates with this patient. Returning an MRN asserts the IIS has determined the record matches that MRN, and that should only be done if the IIS believes it is true; finding the patient via other query parameters (e.g., after a merge, or a patient new to that provider) does not mean the IIS has decided to link them, so the MRN should not be echoed. The IIS is only required to return at least one identifier, which for an IIS should include the state registry (SR) ID. Do not send an empty MRN repetition if the MRN is unknown; e.g., instead of `PID|1||^^^99993^MR~<IIS ID>^^^<IIS>^SR|`, send only the SR identifier: `PID|1||<IIS ID>^^^<IIS>^SR|`. In the reported case the EHR rejected the response because PID-3 did not match its stored identifier; this is a common situation for all IIS. (The earlier 2020 question, Q04-043, had no answer recorded.)

What PID-3 identifier type code should be used to indicate that an identifier is a Master Patient Index (MPI) ID?

Asked 1× · 2021 · VXU/QBP · Answered · Fields: PID-3 · Related: Patient Matching & Deduplication

MPI is a generic concept implemented differently by organizations; IDs it produces are usually labeled by their specific type (e.g., a hospital MPI that assigns MRNs). The IZ community has settled meanings for MR and SR; beyond that you must learn the other system's needs and negotiate a solution.

Some submitters (notably pharmacies) appear to generate a new MRN for each encounter. Have other IIS encountered this, and is there national guidance on how to handle it?

Asked 1× · 2021 · VXU/QBP · Answered · Fields: PID-3 · Related: Patient Matching & Deduplication

Answer given

Some partners, particularly pharmacy systems that had not previously integrated with IIS, have been reported to assign a new MRN for every visit. This is mainly a problem for IIS without a robust matching algorithm that depend on submitters to supply a consistent MRN to avoid duplicates. Most IIS use a robust patient matching process in which a matching MRN is a strong sign of a high-confidence match, but which will still match patients (even from the same submitter) on other criteria. Ideally the same patient has the same MRN every visit, which reduces matching problems inside the IIS and when the EHR queries the IIS, but a good matching process should readily merge records with different MRNs when other evidence shows they are the same patient.

The more serious concern is a submitter that reuses MRNs, i.e., reports one patient under an ID and later a completely different patient under the same ID. IIS should not accept data from systems that do this and should never merge records where the MRN matches but demographics are significantly different. Every MRN match should be double-checked against a minimum threshold; for example, one IIS required that at least the first name, last name, or birth date also match before an MRN match was accepted, which allowed updates while preventing bad MRN matches.

A clinic sent 25,000 patients with the same MRN and many were merged incorrectly because the IIS updates patients with the same MRN from the same clinic even if name or DOB differ. Should the IIS reject records with the same MRN but different name/DOB from the same site, and what is best practice?

Asked 1× · 2023 · VXU · Answered · Fields: PID-3 · Related: Patient Matching & Deduplication, Data Quality & Validation

Answer given

Treat MRNs (and other patient identifiers) as 'trust with verification'. They are heavily weighted demographic data, not mistake-proof keys. EHRs can also have the opposite problem: one person split into two records with two MRNs, and trusting the MRN would then create a duplicate in the IIS. An MRN match is a useful shortcut past costly deduplication logic, but it should be followed by a sanity check on other demographics.

Rejecting is up to the IIS, but it loses data that might never be resent. A better approach is to build this into processes: for example, create a separate patient when the same MRN seems to be two people and flag them for manual review. The right strategy depends on internal resources and how easily the IIS can merge and unmerge, since unmerging wrongly merged records is often much harder than linking or unlinking possible matches. In AIRA premeasurement of patient matching with 52 IIS, one rejected the message when it suspected the same MRN belonged to two patients; the other 51 created two separate patients.

PID-5 Patient Name

How should alias names and nicknames be sent in PID-5, and is there a standard nickname list for matching?

Asked 2× · 2020–2022 · VXU/QBP · Answered · Fields: PID-5 · Related: Patient Matching & Deduplication

Answer given

Alias names are sent as an additional repetition of PID-5; it is permissible to send only the first or only the last name if that is all that is available (2020).

The CDC IG requires the patient's legal name in the first repetition of PID-5; this should not be a nickname or alias (e.g., do not send 'Jon' for a patient legally named Jonathan). Additional repetitions are allowed, including an alias with name type code 'A', which is where a nickname may properly be sent, e.g. `|Lastname^Jonathan^^^^^L~^Jon^^^^^A|`. In practice nicknames are sometimes sent as the legal name, so matching systems should be ready to handle that. AIRA does not know which states store alias names separately, since testing cannot reveal whether an IIS saves or ignores this data. There is no official national nickname list; the 2013 CDC/AIRA 'IIS Patient-Level De-duplication Best Practices' (p. 35) says IIS should match on nicknames but gives no list. An IIS could build one from its own manual merge decisions (preserving names from both merged records) and feed common nickname pairs into automated matching; comparing lists across IIS would also help (2022).

How should a patient's own maiden name be sent (as distinct from mother's maiden name)?

Asked 2× · 2020–2021 · VXU · Answered · Fields: PID-5 · Related: PID-6, PID-9, Patient Matching & Deduplication

Answer given

Send it as an additional repetition of PID-5 with name type M (maiden), with the maiden last name in the family name component, e.g. `LAST^FIRST^^^^^L~MAIDENLAST^FIRST^^^^^M`. This differs from the mother's maiden name, which goes in PID-6. A maiden name is a person's name before marriage and includes both first and last names, and the data type requires both, so expect both. It cannot be sent in PID-9 (alias), which has usage X (Not Supported) in the current guide.

Few if any IIS collect patient maiden name and most would likely ignore it, and it is not a core data element; it is unclear how often EHRs collect it. It may help patient matching (the first name could help as well), and anything that improves matching is a good idea. An IIS considering adding support should first find a couple of large partners who actually record and send maiden name to confirm it is worth it.

How should a patient who truly has no first name be messaged in PID-5.2? Is there a standard filler value (e.g., 'NFN', '-')?

Asked 2× · 2020–2022 · VXU · Answered · Fields: PID-5 · Related: Patient Matching & Deduplication, Data Quality & Validation

Answer given

Earlier guidance (2020, IIS-specific): based on knowledge of one IIS's system, it was recommended to use the first name "Baby", as this signals to that IIS's matching system that the person does not have a real first name.

Later general guidance (2022): national standards require the patient's first name always be valued, and there is no guidance on submitting patients with no first name or on standard filler names; using a filler is probably not correct under the current standard, although it happens in practice. It is appropriate for an IIS to reject such records. Generally, if a legal name fails basic validation (missing first name, unacceptable characters), the IIS may reject it and require the provider to use an alternative process (manual entry or entry by IIS staff). The IIS must then set a policy for recording such names, considering the effect of filler names on searching and patient matching; in some cases the IIS may not be able to record the information properly without clarification of the legal name.

An AART data quality measure (DQI 1.1, missing patient first name) failed even though the IIS returned NF to the query. What did the IIS do wrong?

Asked 1× · 2023 · VXU/ACK/QBP/RSP · Answered · Fields: PID-5 · Related: ERR-2, Data Quality & Validation, Conformance Testing & Validation Tools

Answer given

The measure checks that the IIS recognizes the missing first name. It can pass in two ways: (1) return an ERR segment in the ACK pointing to PID-5 (this IIS flagged a problem but only pointed to the PID segment in general); or (2) when queried, return the patient record without a first name. Accepting patients with no first name is allowed, but AIRA knows of no IIS that does it.

Many DQI tests work the same way: either detect the problem on submission or show on query that it was handled. The recommended and easiest route is to flag it on submission. The tests do not require accepting or rejecting any data; they only look for evidence the problem was recognized, usually an ERR segment pointing to the field. Its severity can be error, warning or information, matching the IIS's acceptance policy. The simplest fix is to add an ERR pointing to PID-5 (ERR-2), or change the existing ERR to point there; the number of ERR segments doesn't matter as long as one references PID-5.

How should newborns with temporary or placeholder names (e.g., 'Baby Boy', 'BABYGIRL, SALLY') be messaged and handled? Should the EHR hold the VXU until a legal name is assigned, and how should it update the name later?

Asked 4× · 2023–2026 · VXU · Answered · Fields: PID-5 · Related: Patient Matching & Deduplication, Data Quality & Validation, PID-5.7

Answer given

No community standard existed as of 2023. IIS generally take one of two approaches: (1) reject VXUs with placeholder names, each IIS or product keeping a list of names it rejects; or (2) accept them but have processes to match the placeholder-name record to a properly named record later. Interim resources included a 2020 AIRA information request on accepting temporary newborn names, the September 2022 HL7 User Group presentation and discussion on reporting unnamed children, a 2021 HIMSS Immunization Integration Project 'legal baby names' backgrounder (the project had the topic on its short list but had not prioritized it), and a 2023 AIRA Discovery Session on improving IIS data quality in which a jurisdiction presented its strategies (including an exception queue) for unknown baby names.

In 2025, AIRA shared with an EHR vendor a draft Technical Advisory Bulletin (TAB) on patient names that addresses patients without legal names, including a proposed 'NB' (newborn) name type code in PID-5 (PID-5.7) so receiving systems can identify temporary names; name type codes could help IIS that have exception processes for such names. A jurisdiction's published paper on handling temporary baby names was shared, and AIRA offered to connect the vendor with jurisdictions to pilot the 'NB' name type. The specific questions of whether to hold the VXU until a legal name exists, and whether to later resend the vaccination or send a demographics-only VXU (no RXA), were not directly answered. By 2026 AIRA referred IIS to the TAB on name types at https://repository.immregistries.org/resource/tab-resources/.

Many IIS expect name type code 'L' (legal) in the patient name of a QBP, but an EHR cannot guarantee that the name it holds is the legal name. Should IIS permit 'C' (current) in queries rather than rejecting anything other than 'L'?

Asked 1× · 2024 · QBP · Partly answered · Fields: PID-5 · Related: QPD-4, Patient Matching & Deduplication

Answer given

The current IG requires that the legal name be sent first because some IIS read only the first repetition and the legal name gives the IIS the best chance of finding a match. In practice there is a lot of variation in how names are typed, and IIS are expected to have matching systems that can cope with this. PID-30 Patient Death Indicator

How should deceased status be determined when PID-30 (Patient Death Indicator), PID-29 (Death Date/Time) and PD1-16 (Immunization Registry Status) conflict or are incomplete? Can a patient be marked deceased without a date of death, and does PID-30 = Y take priority over PD1-16 = active?

Asked 3× · 2016–2022 · VXU · Answered · Fields: PID-30 · Related: PD1-16, PID-29

Answer given

Yes, a patient can be marked deceased without a date of death (e.g., PID-30 = 'Y', PD1-16 = 'P', PID-29 empty). Documentation is in two places in the CDC IG, not directly correlated because they report different information that overlaps when a patient is deceased. PID-29 and PID-30 are standard PID fields shared with ADT: PID-30 is RE and must be valued if known, and PID-29 is used only when PID-30 is true, in which case it is RE. PD1-16 uses user-defined table 0441 (Appendix A); it is RE in an RE segment, so if known it must be reported, and one could argue a sender that knows the patient is deceased must send 'P'. In practice not all systems convert a deceased flag into the registry status. Pragmatically, the IIS should mark a patient deceased if PID-30 indicates it, even if PD1-16 is not 'P'.

Earlier questions (2016) had no answer recorded; one noted that MIROW patient status guidance says that when PD1-16 = deceased and PID-30 = N or empty, the registry status should be ignored, but does not cover PD1-16 = active with PID-30 = Y.
