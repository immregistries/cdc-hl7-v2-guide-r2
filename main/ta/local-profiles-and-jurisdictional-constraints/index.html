Local Profiles & Jurisdictional Constraints

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

18 questions. Findings: none
Not yet assessed

What was asked

Questions in this section concern how far an IIS may go in adding local requirements on top of the national HL7 v2.5.1 Immunization IG, how local guides should be written and documented, and how EHR vendors serving many jurisdictions should cope with the variation. A large cluster arose during the 2020-2021 COVID-19 vaccine rollout, when jurisdictions added data elements (priority group, playbook elements) and vendors asked whether national specifications existed. Recurring themes are the difference between "legal" local constraints and helpful ones, the preference for RE over R for policy-driven requirements, and state laws (consent, SOGI) that force local deviations.

IG clarifications suggested when the TA records were consolidated (7)
  • Document the rules for constraining usage codes in local profiles (which transitions are allowed, e.g., RE to R, O to X, X to O).
  • Limit the scope of local constraints and encourage RE over R for policy-driven requirements.
  • Jurisdictional requirement tables should use HL7 usage codes precisely and state the consequence of a missing value (rejection vs. warning).
  • Address consent/registry status resending: the IG assumes it can be sent with every update, conflicting with send-once consent policies.
  • Add guidance on submitting on behalf of another organization, including identification of the responsible organization when one sender transmits for multiple organizations.
  • Consider national race/ethnicity codes for unknown values so EHRs can build one solution for all IIS.
  • Clarify the IG's position on Z-segments in local guides.

COVID-19 Reporting Requirements

Is there a plan to define a minimum data set that EHRs should support for COVID vaccine reporting to IIS, and is anyone tracking state-specific COVID requirements?

Asked 1× · 2020 · VXU · Answered

Answer given

No national plan to define a minimum data set for EHR reporting was known. Some IIS were defining requirements for EHRs, e.g., asking for priority group or encouraging currently optional fields such as multiple race codes. There is no formal process requiring IIS to clear such requirements with CDC or another national body; AIRA can coordinate through SISC when IIS ask.

The CDC COVID playbook lists data elements such as administered-at location type, dose number, vaccination series complete, comorbidity status (Y/N) and recipient missed vaccination appointment (Y/N). Are EHRs expected to send these to the IIS, and where in the VXU?

Asked 2× · 2020 · VXU · Answered · Related: RXA, OBX

Answer given

Most do not need to be submitted by EHRs. - Administered-at location type should be metadata the IIS captures during onboarding; there is no need to send it with each VXU, and the IIS reports it to CDC. - Dose number and series complete are calculated by the IIS with its CDS engine when reporting to CDC. - Missed vaccination appointment was removed as a CDC requirement. - Comorbidity status was still under discussion; as defined by CDC, most IIS could not accept it and there is no standardized way to send it in HL7 Z22.

An IIS publishes a table of "required" COVID-19 data elements for HL7 connections. Is there anything in the table that should be changed?

Asked 1× · 2020 · VXU · Answered · Related: Data Quality & Validation

Answer given

The requirements outlined looked good overall. The main concern is the use of the word "required". It needs to be clear whether "required" means a message will be rejected if any of those fields are missing. The table itself only nominally distinguished a few optional fields, a couple of RE fields and a few conditionally required fields. Setting the bar that high risks getting bad data: if submitters read "required" as meaning they must put something in the field or nothing will be accepted, they may fill the fields with junk values just to get the message accepted.

Can an IIS local implementation guide mark most national IG optional (O) fields as X (Not Supported) to tell providers it won't use them? Is there any expectation that an IIS accepts and stores optional fields?

Asked 1× · 2021 · VXU · Answered · Related: Version & IG Interpretation

Answer given

Yes, that is acceptable, and IIS are not expected to accept or store optional fields. What matters is how the interface behaves when a submitter populates one of these fields. It should be forgiving, not strict: a field that is X in one IIS may be RE in another, and EHRs struggle when both IIS are extremely strict.

The IG says local implementers may further constrain the guide (e.g., make optional fields required). Is that license to impose any local rule, such as requiring ZIP code on every patient, and how should a multi-state vendor handle such requirements without maintaining many HL7 variants?

Asked 1× · 2025 · VXU/ACK · Answered · Related: PID-11, Data Quality & Validation, Version & IG Interpretation

Answer given

Adding a local requirement is technically legal under the IG, but that does not mean it solves problems, and it can create others. IIS must retain some flexibility for inherently local values (e.g., MSH-4, RXA-11.4) and jurisdictional policy choices. AIRA's Measurement & Improvement (M&I) process distinguishes expected from unexpected local differences: IIS that add requirements like patient address can still be validated, but only as "Complete Minor Difference".

Talking points: - Most policy requirements should be RE (required if known) rather than R, allowing legitimate unknowns. - Staying close to the national standard lowers integration and maintenance burden. - "Always required" policies do not produce better data; they convert missing data into bad placeholder data that is harder to detect. - The HL7 interface is an automated data feed, not a data-entry screen; rejecting messages for missing data rarely leads to correction and loses vaccination data. - Manage completeness through data quality monitoring and outreach (e.g., one missing ZIP in 150,000 records is noise; 95% missing from one provider indicates a process problem). - Vendors should implement configurable validation severity (error/warning/informational per jurisdiction) in a single interface rather than multiple message variants. - The IIS may already have the ZIP for the patient or could derive it via address services, so rejecting for a missing ZIP should be revisited.

An IIS accepts VXU messages with an empty patient phone number (PID-13) and an empty dose amount (RXA-6). Staff listed these as gaps against national standards. Should the IIS start rejecting messages missing these values to align with national standards?

Asked 1× · 2023 · VXU · Answered · Related: PID-13, RXA-6, Conformance Testing & Validation Tools

Answer given

AART Assessment and Validation does not ask for this change. Accepting messages without the patient phone number or dose amount is not a deviation the national standard requires the IIS to fix. If the IIS makes these fields mandatory anyway, it adds local requirements beyond the national standard, and those must be documented for trading partners.

Does a state's local implementation guide take precedence over the national CDC IG? A provider's vendor refuses to change race/ethnicity handling to meet the state's requirements, citing the CDC guide.

Asked 1× · 2022 · VXU · Answered · Related: PID-10, PID-22, Version & IG Interpretation

Answer given

It is more complicated. A jurisdiction can set additional expectations locally, such as making RE/O fields required or adding values to code sets, but it must communicate and negotiate with its community during implementation. A certified system cannot be expected to meet arbitrary state requirements without modification and cost; seemingly simple changes can be expensive and complicate the EHR's deployments in other states. AIRA hopes CDC will add race/ethnicity codes for unknown values nationally, which would let EHRs build one solution for all IIS. Meanwhile, the IIS should accommodate EHR partners that meet the national standard but cannot yet meet local requirements.

State Law, Policy & Multi-Jurisdiction Reporting

Why does one state IIS have unique registry consent requirements that EHRs must build specifically, and how have others handled them? This seems to be a barrier to bidirectional functionality across states.

Asked 1× · 2020 · VXU · Answered · Related: Bidirectional Exchange, PD1 (registry status/consent)

Answer given

Some IIS variation exists because state laws and regulations require things the national standard does not support. This state requires more consent detail than yes/no; AIRA worked with the IIS to put this in the message in a way consistent with the standard, but it still requires EHR changes, and changing it would likely require legislative action.

An additional hurdle: the IIS lacks an effective process for handling withdrawn patients. Withdrawal removes the person entirely from the database, so resubmitting the patient with a positive consent, even old information, would re-consent them. To prevent this, the IIS's policy is that submitters may not use the real-time bidirectional interface unless they can send consent once for a patient and never again. This is very difficult to implement and technically breaks the national standard, which expects this information to be sent whenever the patient record is updated. The IIS is aware and looking for workarounds that would allow EHRs to report consent whenever they like, but until then its policy is to submit consent using its state-specific codes and only once.

Are other jurisdictions requiring sexual orientation and gender identity (SOGI) data in HL7 submissions, and is there data on how many IIS collect it even if not required?

Asked 1× · 2024 · VXU · Partly answered · Related: PID-8

Answer given

AIRA does not have firm numbers on SOGI requirements or collection across IIS and suggested an AIRA Information Request to the community. AIRA has received SOGI questions from several jurisdictions about supporting it in HL7 processing; one state has legislation (HB22-1157) with additional data collection requirements. AIRA is not aware of any IIS requiring SOGI and sees no evidence of it in Measurement & Improvement submission assessment. Testing for SOGI support is limited: a VXU with SOGI data can be submitted and the patient queried, but at best this shows whether the IIS rejects the data; acceptance does not show it was stored, and IIS are unlikely to return SOGI in an RSP.

Asked 1× · 2026 · VXU · Partly answered · Related: MSH-4, Onboarding & Interface Testing

Answer given

AIRA has no published guidance on this; it is primarily a policy question for the IIS. The upcoming IG is adding guidance on how a system submits on behalf of another organization, so this kind of arrangement is known and technically supported. At a technical level, using a configurable lookup to populate the new owner's IIS organization identifiers looks sensible, and there is no national-level reason not to solve it this way.
