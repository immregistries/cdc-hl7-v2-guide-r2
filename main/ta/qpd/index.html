What was asked

QPD questions cover the query name in QPD-1 (Z34 vs Z44 and the correct coding system), how patient identifiers in QPD-3 should be used and matched (submitter MRNs, IIS IDs, re-querying after a Z31 selection), demographic matching on name and address (QPD-4, QPD-8), and how an IIS should echo the QPD in its RSP even when the query contained invalid or non-conformant values. A recurring theme is that query demographic fields are RE in the national IG and that IIS should not let unknown or missing values block a match unnecessarily.

IG clarifications suggested when the TA records were consolidated (4)
  • Consistently show CDCPHINVS as the QPD-1 coding system.
  • State that the RSP echoes the QPD exactly as received, even with invalid values, and validators should not fail it.
  • Describe how to populate QPD-3 when re-querying after a Z31 candidate selection, including the local MRN.
  • Explain that query demographic fields are RE and give guidance on IIS minimum-match requirements versus local R constraints.

When the IIS echoes the query's QPD in its RSP, NIST flags conformance errors in the echoed content (e.g., an invalid date, or "The required Component QPD-8.7 (Address Type) is missing"). Does this affect results, and should the IIS flag such values instead of, say, returning NF?

Asked 2× · 2021–2024 · QBP/RSP · Answered · Related: QPD-8, MSA-1, Query & Response Behavior, Conformance Testing & Validation Tools

Answer given

The IIS should echo the QPD back as received, even if it contains invalid values. AART shows QPD conformance errors but doesn't score them, because the QPD in the RSP is an echo of what the tester sent; some test cases intentionally send poor HL7, so echoed errors sometimes can't be avoided. In one case AIRA fixed the test case so the QPD-8.7 issue wouldn't recur (2021). For a query containing an invalid date (2024): NIST will see the echoed date as a problem in the response, but AIRA does not consider it something the IIS should fix, and it should not cause a failure. The test case (probably Query measure 6) is most likely checking that the IIS recognizes the error and returns AE with an ERR segment instead of AA, so returning an error is preferable to only reporting not found.

QPD-1 Message Query Name

What are the correct QPD-1 values? The 2.5.1 IG uses both HL70471 and CDCPHINVS as the coding system; for a history request, send `Z34^Request Immunization History^HL70471` or `Z34^Request Complete Immunization History^CDCPHINVS`?

Asked 2× · 2016–2022 · QBP · Answered · Fields: QPD-1 · Related: MSH-21, Code Sets & Vocabulary, Version & IG Interpretation

Answer given

Use CDCPHINVS. The NIST Immunization Test Suite, which follows the current CDC IG and is used for EHR certification, does not allow HL70471 in QPD-1 for QBP Z34 messages, so for certification always use CDCPHINVS. It works with all IIS. HL70471 may work with some IIS, but it has not been tested and is not seen in practice. The HL7-balloted version of the IG also uses CDCPHINVS (2022). An earlier (2016) question noting that the IG's QPD-1 values appear incorrect has no separate answer recorded.

QPD-3 Patient List

When a querying provider includes its own MRN in QPD-3 for a patient the IIS has never associated with that provider, the IIS returns no match, but removing the MRN returns the patient. Should an unknown provider MRN prevent a match?

Asked 1× · 2025 · QBP/RSP · Answered · Fields: QPD-3 · Related: QPD-4, QPD-6

Answer given

No. Including the MRN with every query is a customary and encouraged practice, and it is common for a submitter to have no prior relationship with a patient in the IIS (e.g., a patient registers at a pharmacy that then queries the IIS for history). A known provider MRN can help the IIS find a match, but if the IIS does not know that provider's MRN this should not prevent the IIS from finding the patient using the other demographics; the IIS search logic should be reconsidered.

After a Z31 candidate list, when the clinician selects the correct patient, how should the follow-up query populate QPD-3: (a) echo the identifier list received in the selected PID, (b) send only the local MRN with the registry's demographics, or (c) send both?

Asked 1× · 2023 · QBP/RSP · Partly answered · Fields: QPD-3 · Related: PID-3, Query & Response Behavior

Answer given

The IG does not single out PID-3 identifiers as different from the other PID fields when re-querying from a Z31 selection, so the follow-up query should echo the identifier list (and demographics) returned for the selected candidate, i.e., option (a), which helps the IIS make a single exact match.

How can a submitter retrieve the complete immunization history for a patient it just reported, when QPD doesn't seem to have a unique identifier?

Asked 1× · 2021 · QBP · Answered · Fields: QPD-3 · Related: PID-3, Query & Response Behavior

Answer given

QPD-3 (PatientList) is the equivalent of PID-3 (Patient Identifier List). Put your MRN in QPD-3 just as you would in PID-3. Most IIS require this field and treat the submitter's MRN as a strong indicator of which patient to return.

QPD-4 Patient Name

A consumer portal queries with the identity-proofed legal name (e.g., David) while the IIS record has a nickname (Dave), causing no match. Should the IIS match nicknames, and if so from a pre-generated nickname table or aliases stored on the record, or require an exact name match?

Asked 1× · 2021 · QBP/RSP · Answered · Fields: QPD-4 · Related: Patient Matching & Deduplication, PID-5

Answer given

Most patient matching algorithms handle this through a nickname lookup that links known names as common replacements, typically curated from name resources. If all other data elements agree, matching TIMOTHY to TIM using a pre-generated list (or another technique) is reasonable. Many algorithms compute a confidence score across all demographic elements that must meet a threshold; each IIS needs to decide where that threshold is, and it may be the same or different for VXU and QBP. String comparison techniques such as Soundex, Jaro-Winkler and edit distance also help with nicknames, spelling variants (Sara/Sarah) and city names. Requiring an exact name match from external systems, whose demographics may change without notifying the IIS, will lead to a low match rate. The CDC de-duplication best practices document also covers many matching nuances that remain applicable.

QPD-8 Patient Address

In IIS-to-IIS query, one IIS may hold a different address for a patient than another. Would sending a different address cause many "not found" responses?

Asked 1× · 2022 · QBP/RSP · Partly answered · Fields: QPD-8 · Related: Patient Matching & Deduplication

Answer given

This has come up before and most IIS reported that address differences would not have a large impact on found vs. not-found results, since matching relies on other demographics as well. Allowing a user to send an address not saved in the IIS via a manual query was considered a good feature to add.

A jurisdiction changed QPD-8 (patient address) from RE to R in its local guide, and providers querying for transient clients with unknown or outdated addresses now get many "Not Found" responses. The national guide lists QPD-8 as RE. What is recommended?

Asked 1× · 2023 · QBP · Answered · Fields: QPD-8 · Related: QPD-3, QPD-4, QPD-6, Local Profiles & Jurisdictional Constraints

Answer given

The patient address in QPD-8 is RE in the national IG, as are all the patient-identifying query fields. In practice nearly all IIS require some minimum patient information before running a query. Testing commonly shows IIS requiring the patient ID, name and date of birth. Those fields are normally required for VXU submission and present on the patient record, so requiring them is not usually a problem.

The AIRA IIS Functional Guide for query (section 6.1, p. 28) says "The Querying System SHALL include all known data from the Querying System at the time of the query." This supports keeping the query data fields RE, as the national IG has them.

General recommendations when an IIS wants to move a field from RE to R locally: - IIS may tighten requirements in their local guides. These are constraints on the national standard. - Make the change only to support a specific local policy, after weighing what happens when the data is truly missing. Document why the constraint exists so partners understand the impact on their systems. - It can affect AART assessment and validation. Moving RE to R can produce a "Deviates From Standard" result instead of "Meets", which flags the local constraint for partners. - Overall, IIS are encouraged to follow the national standard as closely as possible and minimize local constraints. This shortens onboarding and keeps the most capability available.

For this case it depends on policy. If a patient record truly cannot be retrieved without an address, the IIS has to keep QPD-8 as R. Patients without an address then cannot be found through the HL7 query interface, and the IIS should document that limitation and the workarounds (such as requesting the record by other means). If the IIS wants to support queries for patients without an address, it should move QPD-8 back to RE, in line with the national standard.
