ERR Error Segment

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

30 questions. Findings: none
Not yet assessed

What was asked

ERR questions cluster around four issues: how many ERR segments an RSP may carry and where they may appear; how to encode the error location in ERR-2; which HL7 table 0357 codes belong in ERR-3 (207 vs 999, 200-203, 100); and, most frequently, how to choose ERR-4 severity (E, W, I) and what each severity means for the sender. ERR-5 questions reflect a long-running need for a national, expanded set of application error codes. Many of the questions arise from AART/NIST assessment findings, and the answers lean heavily on AIRA's "Guidance for HL7 Acknowledgement Messages to Support Interoperability".

IG clarifications suggested when the TA records were consolidated (6)
  • Allow multiple ERR segments in RSP profiles (currently limited to one); note the base-standard origin of the limit.
  • State explicitly that ERR-4 = E means the data was not accepted and must be corrected and resubmitted.
  • State that HL70357 codes 200-203 pair with ERR-4 = E and MSA-1 = AR; clarify 207 vs 999 and when ERR-5 (table 0533) should be populated, fixing inconsistent Appendix B examples.
  • Publish a national, expanded ERR-5 application error code set, including codes for data quality situations.
  • Address partial acceptance and "accepted but not stored by local policy" through Advanced ACK guidance.
  • Local profiles should not loosen the RSP ERR segment from RE to O.

ERR (segment-level)

The IG allows only one ERR segment in the RSP (0..1, including the Z33 response), but providers would benefit from seeing all errors at once. Why is it limited, and should an IIS that returns multiple ERR segments change?

Asked 3× · 2020–2024 · RSP · Answered · Related: Message Structure & Cardinality

Answer given

Guidance has changed over time.

Earlier guidance (2020): This is a known limitation of the base standard / HL7 version in use. AIRA convinced HL7 International of it and it will be corrected, but only in a later HL7 version that the community is not yet using; HL7 cannot go back and correct older versions. Until then, the one-ERR constraint in the Z33 response stands. Guidance was given on how to pick the one error to return when multiple errors exist (details not recorded).

Later guidance (2024): No change was needed on the IIS side. The current IG profile allows only one ERR segment in the RSP, but returning multiple ERR segments in this rare scenario is considered the better practice, so AART was updated to exclude this from assessment reporting. The NIST tool will still flag it if messages are run directly there; IIS should keep using NIST during development but ignore the multiple-ERR finding. The multiple-ERR scenario was identified for the next IG revision, with AIRA recommending that IIS be allowed to send multiple ERR segments in RSP messages.

When a query is rejected with AR, the response gives no explanation (e.g., MSH-2 too long, QPD-9 badly formatted), while AE and TM responses do. Shouldn't the IIS explain AR rejections?

Asked 1× · 2017 · ACK/RSP/QBP · Answered · Related: MSA-1, Query & Response Behavior

Answer given

Yes. If an IIS cannot process a query it should return one of two messages, both of which must include at least one ERR segment indicating the issue. Not returning details is inconsistent with current IIS standards. See IG Release 1.5 pages 139-140 (Figure 41), which diagrams how a QBP should be processed.

If the QBP fails for one of the reasons at the top of Figure 41 (unsupported message type, unsupported event code, unsupported processing ID, or unable to process for reasons unrelated to format or content), an ACK must be returned. Per the AIRA ACK Guidance document, an ACK with AR should include at least one ERR segment indicating the issue.

If none of those apply but a fatal error still prevents the query from being processed, the diagram shows an RSP should be returned. The RSP definition allows an ERR segment, and for practical purposes it should be included to indicate the reason so the submitter can fix and resubmit. Either way, the response should indicate the problem in an ERR segment; this is fully supported by the current standard.

ERR-2 Error Location

What is the correct format for ERR-2 (Error Location)? An IIS encoded locations as `PID^7` or `PID^^5.2`.

Asked 2× · 2023–2025 · ACK · Answered · Fields: ERR-2 · Related: PID-7, Acknowledgement & Error Handling

Answer given

Each part of the location belongs in its own component rather than using dotted notation: segment ID ^ segment sequence ^ field position ^ field repetition ^ component number. For example, an error in PID-7 is written `PID^1^7` (segment ID, then segment sequence where 1 = first PID, then field position), and an error in PID-5.2 is `PID^1^5^1^2`. The sequence matters little for PID but is critical for segments that can repeat, such as RXA. Changing `PID^7` to `PID^1^7` passed the AART test, which checks that the error is reported in PID-7 (2023). For `PID^^5.2`, the extra ^ was not the real problem; the issue was the dotted notation (2025). The question of whether ERR-2 can repeat was not specifically addressed; the TA offered to review the original ACK to confirm all needed changes.

How specific should ERR-2 locations be? Is segment and field enough (e.g., `PID^1^13`), or should repetition and component be included (e.g., `PID^1^13^2^4` for a second email address, `PID^1^5^1^1` for missing given name)? Are subcomponents needed?

Asked 1× · 2022 · ACK · Answered · Fields: ERR-2 · Related: Acknowledgement & Error Handling, PID-13, PID-5

Answer given

Identifying the issue down to the field (e.g., PID-13 or PID-5) is very good and is what matters if AIRA measures whether the IIS detects an issue. Indicating the repetition is even better, especially if submitters regularly send multiple email addresses, but if not the impact is small since the list is usually short and problems can be found quickly. The same applies to components: they may be indicated but are not required, particularly when the ERR-8 description clearly states the problem.

ERR-3 HL7 Error Code

An EHR receives an ACK with error code 207 indicating the account is locked, but the IIS sees no connection attempts in its logs. Why?

Asked 1× · 2023 · ACK · Answered · Fields: ERR-3 · Related: MSA-1, Acknowledgement & Error Handling

Answer given

It appears the interface the EHR is pointing to is reporting too many attempts with a bad password and has locked the account. If the EHR is using the correct connection parameters, the IIS's system (e.g., its HL7 hub) is generating the message. Such a message would likely not be logged under the account because the system treats it as a bad-faith request. Check documentation on how the system handles account locking after repeated bad credentials, confirm with the vendor that it generates this error, and most likely follow the account unlock process and issue new credentials before the EHR retries.

How should ERR-3 999 (Application error) be distinguished from 207 (Application internal error)? Do table 0533 codes in ERR-5 apply only when ERR-3 is 207 or 999, and should ERR-5 be blank for other ERR-3 values (100, 101, etc.)?

Asked 1× · 2016 · ACK · Answered · Fields: ERR-3 · Related: ERR-5

Answer given

207 is for internal errors, such as the database being down. 999 is for business rule failures. ERR-5 has usage RE and is technically independent of whether ERR-3 is 207 or 999, but it is more likely to be populated with 100-class or 999 errors. Discussion continued as the new IG was being developed, and implementers might wait for final clarification. (The questioner noted that IG Appendix B examples and the AIRA ACK guidance populate ERR-5 inconsistently.)

ERR-4 Severity

How should an IIS decide which issues are errors (E) versus warnings (W) in ERR-4, and is there a resource defining the criteria? (e.g., if one of three immunizations in a VXU has an invalid vaccination date, should that be E?)

Asked 4× · 2016–2024 · ACK · Answered · Fields: ERR-4 · Related: MSA-1, ERR-5, RXA-3, Acknowledgement & Error Handling, Conformance Testing & Validation Tools

Answer given

Per the AIRA ACK guidance ("Guidance for HL7 Acknowledgement Messages to Support Interoperability", repository.immregistries.org), error severity is determined by the system creating the ACK based on its local requirements and business rules, but the severity chosen should reflect what the receiving system is expected to do. The guidance includes a table translating each severity into expectations that the other system correct an issue in its system and/or resend the data. Different systems may therefore assign different severities to the same issue depending on how they want the other system to react, which reflects how important that information is to them (2016). The severity for a given issue depends on the IIS's data quality rules and policy for that field, not on HL7 conformance rules; an HL7 conformance problem can be reported, but its severity is an IIS policy decision (2021).

Severity is at the IIS's discretion: if the IIS cannot save data it deems critical and wants the sender to correct and resubmit the entire VXU, use E; otherwise use W or no error at all (e.g., a missing zip code might produce nothing, a W, or an E depending on the IIS's needs). For an invalid vaccination date on one of three doses, E is the universally accepted approach because IIS never want to lose vaccination events. Since HL7 cannot easily message partial rejections, the submitter resubmits the entire message, including the doses the IIS probably accepted. For a less critical problem, such as one bad NK1 among several, each IIS makes its own business decision: E if it needs a correction and resubmission, W to notify of a data quality problem, or possibly nothing (2024).

For ERR-5, the national set of error codes (2017 publication) provides additional guidance, and a working group drafted additional codes (an "ERR-5 minimum error set" with High/Medium/Low implementation priority) listing data quality situations an IIS might want to signal; an IIS does not have to send these codes but can use the list to decide which issues to detect. Also include the NIST IZ validation tool in ACK development and testing: many IIS that complain about submitters' HL7 conformance return ACKs that are themselves non-conformant, often because they were built before a robust testing tool existed (2021).

In one review (2018), AIRA confirmed an IIS's described usage of W and E was correct (details not recorded).

Does an ERR-4 = E cause AART to treat a message as not accepted, and where is it stated that E means the message was not accepted (is it from NIST)?

Asked 2× · 2024 · ACK/RSP · Answered · Fields: ERR-4 · Related: MSA-1

Answer given

Yes. Any ERR segment with ERR-4 = E causes AART to interpret the message as not accepted (rejected, fully or partially), so the test case fails (e.g., an ACK with AE, one W and one E "VIS Identifier submitted value is not a valid option. Data rejected."). The AART testing log shows how each test case is assessed. The interpretation comes from AIRA/SISC guidance documents rather than NIST: "Guidance for HL7 Acknowledgement Messages to Support Interoperability" and "Guidance for HL7 RSP Messages to Support Interoperability" explain ERR-4 = E and describe how AART evaluates test cases.

Does ERR-4 = E mean the entire message was rejected, or can E be returned when only one piece of data (e.g., a field-level validation failure such as code 207) was rejected?

Asked 1× · 2026 · ACK · Answered · Fields: ERR-4 · Related: MSA-1, ERR-5, Acknowledgement & Error Handling

Answer given

ERR-4 = E does not indicate whether the IIS processed the message; it indicates whether the sending system needs to fix the issue and resubmit. If the IIS could not save the patient or vaccination because of the problem, it should send E in ERR-4. Even when ERR-4 = E is sent, the IIS may still choose to process and accept some of the data in the message; it may, but is not required to, reject the entire message. More detail is in AIRA's latest ACK TAB (https://repository.immregistries.org/resource/tab-resources/).

The ACK guidance says W means the sender must correct the issue but does not have to resend. How is it corrected if it is not resent?

Asked 1× · 2024 · ACK · Answered · Fields: ERR-4 · Related: Data Quality & Validation

Answer given

W is used for systemic problems, placeholder data and similar issues, such as a phone number of 555-1212. These are usually best reviewed in aggregate over a week, month or quarter to find data quality improvement opportunities. A W on an individual message is not concerning, but if the same W shows up in every message the sender should fix its system or process going forward; the correction applies to future submissions rather than resending that message.

How can an IIS indicate that it rejected one vaccination in a VXU but accepted the others, if AE with W means accepted and AE with E means failed?

Asked 1× · 2024 · ACK · Answered · Fields: ERR-4 · Related: MSA-1

Answer given

This is not possible in the base HL7 v2 standard, which has no concept of a partially accepted message. An ERR segment with ERR-4 = E is interpreted as a rejection, full or partial, telling the EHR that some data was not saved and the submission must be fixed and resubmitted. If the IIS is satisfied with the message and does not expect resubmission, the highest ERR-4 severity it should use is W. AIRA's short ACK guidance document describes the logic AART uses. The partial-acceptance concept was raised with the SISC ACK improvement group; it is out of scope for the current improvements but on the radar, and SISC is developing an "Advanced ACK".

Is it appropriate for an IIS to return MSA-1 = AE with ERR-4 = E (e.g., `ERR||RXA^1^9^1|207^Application internal error^HL70357|E||||Immunization source must be 00 to deduct inventory`) for every valid historical vaccination (RXA-9 = 01)? How should the EHR handle this?

Asked 1× · 2025 · VXU/ACK · Answered · Fields: ERR-4 · Related: RXA-9, MSA-1, ERR-2

Answer given

No. Returning an "E" for a good historical vaccination does not follow the national standard; such an IIS would fail Basic Validation for Submission and Acknowledgement (measure #2). Per AIRA guidance published in 2018, ERR-4 = E means the submitter must correct and resubmit, whereas ERR-4 = I indicates information that can be reviewed with no follow-up action required. EHR vendors reasonably assume IIS follow this. In the most recent M&I measurement, 92% of measured IIS did not return an E-level error for historical vaccinations. The standard way to send an informational message such as "this immunization is historical / not deducted from inventory" is ERR-4 = I.

Two ways forward: (1) preferred - the IIS changes the severity to I so it aligns with national standards; (2) not ideal - the EHR adapts locally, e.g., treating a message as rejected only when the word "reject" appears in the ACK text (an approach common in early IIS interface testing). Each IIS sets its own onboarding standards, but when its interface deviates from the national standard it should clearly communicate that to trading partners. (The IIS in this case explained the message appears only for providers set up for automated inventory deduction and could be avoided by turning off the inventory module for that provider.) See Submission and Acknowledgement Validation: Basic Level in the AIRA repository.

A jurisdiction's local guidance says refusals should not be sent to the IIS, so the IIS returns ERR-4 = E when a refusal is submitted. Is this a local deviation, and what is the right ACK behavior?

Asked 1× · 2025 · VXU/ACK · Answered · Fields: ERR-4 · Related: Local Profiles & Jurisdictional Constraints, Immunization Evidence (refusals, immunity, contraindications)

Answer given

Current guidance, given the existing ACK structure, is to return ERR-4 = I or W with the same error message rather than E. Returning E means the submitter should fix an issue and resubmit; since the IIS does not accept refusals, resubmission makes no sense. Returning I or W with a clear message that refusals are not stored is the best current approach. SISC technical small groups are working on an "Advanced ACK" TAB to let IIS communicate such situations in a more structured way.

An IIS wants to return an informational ERR when it accepts an RXA update (RXA-21 = U), using ERR-3 = 0 (Message accepted). Is ERR-5 then mandatory? Table 0533 has no success code - can the IIS create its own, or will that fail AART testing?

Asked 1× · 2025 · ACK · Answered · Fields: ERR-5 · Related: ERR-3, ERR-4, RXA-21

Answer given

New ACK formats should always be checked with the NIST IZ Tool; if the ACK passes, its structure will not cause problems in Measurement & Improvement (M&I) testing. ERR-3 is not a critical field and provides little value; M&I only verifies the code comes from the correct table. `0^Message Accepted` is appropriate and means the issue did not prevent the message from being accepted or the update action from being taken. ERR-5 is RE, so if there is no applicable application error code it can be left blank; NIST and M&I both accept this. Alternatively, a local internal application error code can be placed in ERR-5, which is what the field was originally defined for. The recommendation is to leave it blank for now and adopt the expanded, coordinated set of application error codes AIRA was preparing for release (around March 2025), along with forthcoming Advanced ACK guidance.
