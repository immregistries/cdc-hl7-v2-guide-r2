What was asked

Questions in this section cover how IIS respond to QBP queries: which query/response profiles (Z34/Z44, Z31/Z32/Z33/Z42) to support and when each applies, how to handle multiple matches, consent restrictions and "not found" outcomes, what history and forecast content belongs in the RSP, and how to manage query volume and EHR query workflows. A large group of questions came from AART testing where vaccinations or patients the IIS had accepted were not returned in later queries, usually because of vendor or test-environment processing. Other recurring themes are not filtering the consolidated history, returning one forecast per vaccine group, and building robust single-query capacity instead of batch queries.

IG clarifications suggested when the TA records were consolidated (8)
  • Define which demographics should be returned in a possible-match (Z31) candidate list.
  • Define how to signal that additional matching records exist but cannot be returned due to consent/data-sharing restrictions (e.g., a QAK-2 status or ERR code), and reconcile the "no candidates found" vs explicit "data sharing set to No" messaging.
  • Expand guidance on which vaccination details (route, site, administrator, expiration, eligibility) belong in RSPs, and how historical vs administered affects that.
  • State that only one forecast per vaccine group/disease should be returned, including age-based transitions such as DTaP to Tdap/Td.
  • State whether forecast recommendations should be grouped under a single placeholder ORC/RXA and that empty CVX 998 groups should not be sent.
  • Define how school exemptions are returned (existing Z32/Z42 vs new query/response profiles) and their content.
  • Provide guidance on appropriate query volume/frequency for bidirectional interfaces.
  • Possible additions from unanswered questions: representing completed series, evaluation OBX grouping (including for combination vaccines), adjuvanted vaccine forecasts, and maximum Z31 candidate counts.

Multiple Matches and Candidate Lists (Z31, Z33, NF, TM)

What criteria must match for an IIS to return a potential match (Z31)? What distinguishes a single potential match from an exact match, and where is the line between a potential match and no match?

Asked 1× · 2023 · QBP/RSP · Answered · Related: QAK-2, RCP-2, Patient Matching & Deduplication

Answer given

HL7 does not define patient matching or query search logic. That is internal to each IIS and also shaped by policy and law. With populations in the millions, many IIS use probabilistic or machine-learning matching rather than a deterministic decision tree, so there is no simple line. Querying systems should be ready to receive any of these outcomes: - Single high-confidence match: single patient found (Z32 with the record). - Multiple high-confidence matches (e.g., twins): depending on local policy and/or the RCP-2 quantity limit, a list of patients (Z31), no patients found (NF), or too many found (TM). - One or more low-confidence matches: depending on policy and/or RCP-2, a list of patients (Z31, possibly just one), NF, or TM. - No high- or low-confidence matches: not found (NF).

An IIS may have a single low-confidence match that policy does not let it share. It would then return NF rather than a Z31 exposing that patient's PID. How often each outcome occurs, and the criteria behind them, is not available to AIRA.

When should an IIS return a Z31 (List of Candidates), and how can it be tested? Why does a provider testing the Z31 scenario receive a Z42 instead?

Asked 2× · 2025 · QBP/RSP · Answered · Related: QPD, QPD-3, RCP

Answer given

The Z31 supports cases where a patient search results in two or more possible patients. For example, if two unique patients exist with the exact same name and date of birth, a query with only that name and DOB would logically find both, and the Z31 returns both candidates' demographics with no immunizations. To test it, the IIS needs two such identically or near-identically matching patient records set up so a query can return both.

It is often difficult to get an IIS to return a Z31 instead of a Z42. A Z42 means the IIS believes it found a single good match. Troubleshooting steps: get a copy of the query being run, run it yourself and confirm you get a Z42; identify the two records you believe should be returned; ensure the MRN in the query is not on one of the patient records (a matching MRN can be strong enough to produce an exact match); ensure no State Registry (SR) identifier is sent, which can also force a strong match; and make sure the query parameters are a good match for both records. AIRA tests this in its Query Assessment (Measure 5) using two twin patients with very similar demographics (same mother, address, DOB, different first names and multiple birth order), submitted via VXU, followed by a QBP containing an MRN not associated with either record and only the shared demographics; those AART test patients remain in the IIS test environment and can be re-queried to elicit a Z31.

What are the use cases for returning a Z33 when a query results in more matches than the quantity requested in RCP-2?

Asked 2× · 2022 · QBP/RSP · Answered · Related: RCP-2, Patient Matching & Deduplication

Answer given

The AIRA IIS Functional Guide for query (https://repository.immregistries.org/resource/iis-functional-guide/, page 43) covers this. The responding system must be prepared to handle a situation where too many patients are found and returning even limited patient data is not valuable. This happens when the responding system finds more patients than the maximum requested in the query (RCP-2) or the maximum allowed by its own policies. General requirement: the responding system SHALL HAVE THE ABILITY TO properly respond based on patient matching results and patient consent wishes. Functional requirement: per jurisdictional policy, the responding system SHALL return either a response indicating too many patients were found (Z33) or a response indicating no patients were found (Section 7.3).

Is there a standard for how much demographic data an IIS should return for possible matches (Z31)? An IIS returns limited demographics on the candidate list and full demographics on re-query by IIS ID, which an EHR has trouble reconciling.

Asked 1× · 2025 · QBP/RSP · Answered · Related: PID, QPD-3, RSP Z31

Answer given

There is no current AIRA or HL7 guidance that explicitly defines how much demographic information must be returned at each step, and AIRA had not heard of other IIS limiting demographics on the first query and expanding them on re-query. The 2017 Security Guidance Considerations for IIS says an IIS should return only what is minimally necessary, but does not prescribe a specific pattern; limiting demographics on potential matches to reduce exposure aligns with that principle. From a standards and practical standpoint there is no problem with this practice; reconciliation difficulties are likely a data-mapping or assumption issue on the EHR side (in this case the limitation was confirmed to be on the EHR side, with a fix dependent on EHR version).

When an IIS finds an exact match but other potentially matching records cannot be returned (data-sharing/consent No or Unknown, or possible duplicates), how can the RSP indicate more records exist? Can multiple patients' histories be returned?

Asked 1× · 2021 · QBP/RSP · Answered · Related: ERR-4, QAK-2, RSP Z31, RSP Z32, RSP Z42

Answer given

There is no RSP profile that returns shot history for multiple patients. Only the Z32 and Z42 profiles return immunization history, and both are limited to one PID. The Z31 can return multiple patients but only demographics (PID, PD1, NK1) for each; the Z33 returns no patients. The recommended approach within the current standard is to return the good match with all the consented records and add an ERR segment with Informational severity (ERR-4 = I) indicating that there may be more records associated with the patient if consent or merging could be resolved. (If returning demographics for multiple candidates, the best option is a Z31 with an ERR segment.) The caveat is that this informational ERR is likely to be invisible to end users, since EHR systems are not built to expect or display it; the scenario was not anticipated in the standard. SISC has published guidance on query responses and patient protection for the single-patient case, which describes a similar ERR-based approach and also a forward-looking option using an expanded QAK-2 value set to be more explicit.

Immunization History Content in the RSP

Should an IIS return all immunizations in an RSP, or filter out immunization data originally sent by the querying system?

Asked 2× · 2016–2019 · RSP · Answered · Related: RXA

Answer given

The IIS should return the full history and not filter it. AIRA's recommendation (also given to another IIS and presented in SISC Recent Support Activity presentations) is that IIS should not filter the patient history. The role of an IIS is to create a consolidated view of the patient's record and provide an evaluation and recommendation. An IIS that does not report back the entire history is not giving the whole picture, and its forecast will appear inconsistent with the record returned. Filtering also requires the IIS to make assumptions about what the external system knows or doesn't know about the patient. While filtering may be a challenge for the external system, having the IIS do it would negatively affect the IIS's core mission, so IIS should not filter data as a general course of action. (The 2019 asking has no separate recorded answer.)

Should an RSP return all vaccination detail the IIS holds (route, site, administrator, expiration date, VFC eligibility) or only the minimum (vaccine type, date, lot) as a historical record?

Asked 1× · 2021 · RSP · Answered · Related: RXA-9, RXR, RXA-10, RXA-16, OBX-5

Answer given

The functional-guide text being cited concerns the value in RXA-9 and whether the vaccination is represented as historical vs. administered. There is no expectation that a historical vaccination cannot include additional information; historical vaccinations can include route, site, administrator, etc., and you may want to include them.

For the Z42 RSP in the current guide: RXR is RE, so route and site should be sent if known; vaccine administrator is O (optional) for historical vaccinations; expiration date is O; VFC eligibility is not clearly specified but certainly not R, probably O.

Guidance on RSP content is not well developed in the current guide, so it is largely the IIS's decision how much detail to return. EHR systems are prepared to accept or ignore whatever is sent. A good rule of thumb: whatever the IIS shows clinical users in its UI could be made available via HL7, and consult the clinical/EHR community about what they want from the IIS.

Forecast and Evaluation Content in the RSP

Which forecast dates should an IIS return in the RSP? Are "latest date next dose should be given" and "date dose is overdue" required in addition to earliest and recommended dates?

Asked 2× · 2024–2026 · RSP · Answered · Related: OBX-3, OBX-5

Answer given

2024: The IIS was returning the recommended date but not the others. The only other date AIRA tests in its CDS assessment is the Earliest date. If all of them are available, returning them all is worthwhile because provider systems may find them valuable.

2026: Neither latest nor overdue is required in the RSP; the latest CDS in RSP TAB defines them as MAY return. Certified EHRs that use the IIS forecast are not required to support the overdue date but are required to support the latest date, although no certification test case appears to explicitly use the latest date, so an EHR may have passed without supporting it. The latest date is only relevant for a limited set of recommendations; some have an explicit maximum age (e.g., rotavirus) but many do not. Return the latest date only when an actual maximum age exists, and do not default it to a placeholder like 12/31/2999. Check with providers whether they want it and with EHRs whether they consume and display it.

The later answer refines the earlier "return them all if available": return latest date only when a real maximum age exists.

For a 7-year-old with no DTaP, an IIS's Z42 returns both a DTaP forecast (CVX 107) with status COMPLETE (LA13421-5) and a Td forecast (CVX 139) with correct due dates; testing tools pick the DTaP forecast and fail. How should forecasts for DTaP vs Tdap/Td be returned?

Asked 1× · 2025 · RSP · Answered · Related: OBX-3, OBX-5, RXA-5

Answer given

General guidance is not to return multiple forecasts for the same vaccine-preventable disease in the HL7 response, since it causes confusion (for testing tools, EHRs, and providers alike); similarly, forecasting all remaining doses in a series is discouraged. Only one forecast should be returned for the DTaP/Tdap/Td group: under age 7, forecast DTaP; at 7 years and older, forecast Tdap or Td (not both) and drop the DTaP forecast. Reporting DTaP as COMPLETE for a patient who aged out without completing it is misleading; hiding or filtering the DTaP forecast once the patient turns 7 resolves the HL7 issue. The age-7 cutoff has been stable for decades based on licensure and ACIP recommendations. A better CVX for this patient would be Tdap since the patient needs Tdap first.

This applies to forecasting only; for evaluation, doses given before age 7 should still be evaluated against DTaP even if the patient is now older. On the internal split of the CDSi series, AIRA suggested splitting at target dose 7 rather than 6, noting that among doses 7-11 at least one should be Tdap (preferably the first), and that Tdap can be used for any of them.

For a patient with no vaccine administrations, an IIS's Z42 returns an ORC/RXA (CVX 998, no vaccine administered) with no OBX segments, followed by forecast recommendations in additional ORC/RXA/OBX groups. Is this correct, or should the empty ORC/RXA be dropped?

Asked 1× · 2022 · RSP · Answered · Related: RXA-5, ORC, OBX

Answer given

Technically the message structure is acceptable. The NIST IZ Tool flagged two issues: it did not recognize the new CVX 206 (JYNNEOS) as a valid code to recommend, which is a tooling lag and not a conformance concern; and it reported that the ORC/RXA groups without OBX are missing a forecast. The latter is most likely a NIST limitation from checking every ORC/RXA for forecast content; the Z42 requirement to send a forecast is met by the other ORC/RXA groups. AART did not test the Z42 format for patients with no immunizations at that time, so it does not affect assessment results.

Recommended changes to align with other IIS: (1) do not send an ORC/RXA with CVX 998 that has no associated OBX segments; receivers should ignore it but it could cause problems for systems not expecting it; (2) group all forecast recommendations under a single ORC/RXA. This is not a requirement, but since the ORC/RXA is merely a placeholder carrying no additional information, use the minimum number of them.

Query Volume, Capacity and Batch Queries

How common is it for IIS to support batch HL7 2.5.1 QBP queries for many individuals? Should a batch query interface be built, and what are best practices given concerns about being swamped?

Asked 2× · 2022–2023 · QBP/RSP · Answered · Related: Transport/Connectivity

Answer given

Too many queries is a big concern for IIS. Some IIS may support some type of bulk query, but this has not been standardized. EHR systems can and do send large numbers of queries in "batches" by simply calling the submit-single-message operation over and over. This is surprisingly efficient and, if well supported, can be faster than a classic batch operation; the challenge is that it can overwhelm IIS capacity. The general recommendation is to build a robust, resilient single-query function: (1) the IIS can process a high number of concurrent queries, at least 10x the rate at which it receives updates; (2) the IIS has automated safeguards preventing partners from initiating too many queries in a given time frame, ideally customizable so high-volume providers can have a different threshold; (3) the IIS has an automated system limiting total queries to a level the system has been tested to support. The IIS can then advise partners on its capacity and leave it to them to manage large query volumes. (The 2023 asking has no separate recorded answer.)

EHR Query Workflow and Use of Query Results

An EHR only queries the IIS when a patient has a scheduled appointment and is checked in; practices want to query at any time (e.g., to document COVID vaccines for school forms). Is there a requirement or guidance on how/when EHRs trigger queries, and can an IIS require on-demand queries?

Asked 3× · 2022 · QBP/RSP · Answered · Related: Bidirectional Exchange

Answer given

Neither the ONC certified EHR requirements nor AIRA's Immunization Integration Program specify whether queries must be triggered manually or automatically; the only expectation is that the EHR can query for and consume an immunization history and forecast (IIP: query and reconcile records). Out-of-the-box EHR configurations meet most customers' needs, and locally required changes are customary but may add cost. Automatic queries streamline workflow but may not support resolving inexact or multiple matches and may miss vaccinations given between the query and the visit. Manual queries let providers see the most current record while the patient is present but take staff time. Some EHRs support both. The practice should check with the IIS whether there is a requirement to look up patients before administering, and whether they may use the IIS web portal for manual lookups in the meantime. AIRA planned to contact the vendor about options. (Two other askings, 2022-07 and 2022-09, have no separate recorded answers; whether an IIS can require on-demand queries was not directly answered.)

Asked 2× · 2021 · QBP/RSP · Partly answered · Related: Patient Matching & Deduplication

Answer given

The IIS Functional Guide, Vol 1: Query and Response has relevant information, though it was written for EHR and IIS implementers rather than end users. AIRA's work on multiple/inexact match guidance (including "Query Response Aggregate Measures for Multiple Matches", describing how an IIS can measure how well multiple-match handling works for a provider) includes introductory language that could be adapted. The Immunization Integration Program (IIP) developed query-response guidance (near-final draft) that began with multiple matches and expanded to inexact matches and all query responses. One recommended approach is regular creation and review of aggregate query-response outcome metrics by IIS and provider organizations, which helps clinicians understand what happens with the queries they initiate. SAS code from another IIS for pulling similar metrics from its vendor platform was available, and IIP offered tailored TA to IIS and EHRs. It was also suggested the IIS look closely at actual queries to see exactly what problems users encounter, including vendor product idiosyncrasies affecting matching, and then create a jurisdiction-specific statement.

A hospital updates its legal patient record from IIS query results and turned off queries after IIS patient mismatches (records merged on first/last name and DOB). Are there restrictions on how query results may be used?

Answer given

There is no national guidance restricting how an entity uses information received from the IIS or what can go in a legal medical record; IIS information can be saved with the patient record. Some IIS have tried to restrict use based on local policy, but the purpose of QBP/RSP is to make the patient's vaccine history available for clinician use and records, and restrictions make the interface problematic for EHRs. The core issue here is patient matching (e.g., matching on name/DOB alone), an area AIRA planned to examine.

Other Query Partners and Uses

Should insurance companies query the IIS the same way providers do (QBP/RSP), or should there be a separate specification?

Asked 1× · 2021 · QBP/RSP · Answered · Related: Local Profiles & Jurisdictional Constraints

Answer given

Technically nothing prevents using the same QBP/RSP profiles. The questions are mostly about policy, such as whether there's demographic or other data returned to providers that can't be returned to insurers. If so, there are two main options: (1) Create a new local query profile (a "Zxx" profile instead of Z34/Z44). This has advantages, but it can be a problem if insurers' software is IG-aware and natively speaks Z34/Z44. (2) Filter the response based on the type of organization querying, removing restricted elements before returning the RSP. Also consider whether insurers can handle receiving the full consolidated history on every query (for example, nearly the same history six months apart plus one new flu shot) and deduplicating vaccinations on their side.
