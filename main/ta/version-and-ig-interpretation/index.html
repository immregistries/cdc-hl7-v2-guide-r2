What was asked

Questions in this section are about which version of HL7 and of the immunization IG applies, and how to read and apply the IG. They cover retiring HL7 2.3.1/2.4, the status of v2.8.2, and whether FHIR will replace v2. Others concern reading conventions: data type components, R versus RE usage, CE versus CWE, and the difference between message conformance and required receiving functionality. Others ask where newer guidance lives (SISC TABs) when the IG is silent, for example on VXU trigger events, SOGI and disability data, or regulatory changes (Meaningful Use, ONC HTI-1).

IG clarifications suggested when the TA records were consolidated (4)
  • Explain how receivers should handle CE-formatted data where CWE is specified.
  • Provide a functional guide (or functional requirements) that defines how receiving systems must support the data in each field, beyond message conformance.
  • Define required and prohibited VXU trigger events, including demographic-only changes.
  • Incorporate SOGI messaging guidance, unknown/declined race and ethnicity, and possibly disability observations.

HL7 Versions: Older Versions and Future Direction

Should an IIS keep supporting HL7 v2.3.1 and/or v2.4 immunization messages alongside v2.5.1, or phase them out? Is that decision left to each jurisdiction or made by AIRA/CDC?

Asked 3× · 2016–2024 · general · Answered

Answer given

AIRA published a document in 2017 (the SISC statement on the sunset of HL7 2.3.1) supporting the retirement of HL7 2.3.1 and proposing June 30, 2018 as the sunset date for old interfaces. It does not require ending support, but says systems SHOULD end support for 2.3.1. SISC has not revisited the topic since. HL7 2.4 was never an immunization standard, so there is no official community position on discontinuing it, and the decision is effectively left to each IIS.

The earliest instance (2016, asking whether an IIS should support both 2.3.1 and 2.5.1) has no recorded answer. The 2017 instance about v2.4 was answered only by a reference to the SISC 2.3.1 sunset statement.

Is there a plan or recommendation for IIS to move to an HL7 version newer than v2.5.1, and why is HL7 v3 not being followed (e.g., by a non-US jurisdiction)?

Asked 1× · 2021 · general · Answered

Answer given

Nothing is official yet, but given the overall US trend, any move will likely be to FHIR rather than HL7 v3. It is not yet known when or which interoperability functions will move to FHIR, or how long that will take. FHIR also opens possibilities beyond today's v2 exchange (e.g., querying for an official school report, inventory management/decrementing, bulk queries). For non-US jurisdictions, HL7 v3 is a dead end for new installations and is not recommended. FHIR was created partly to address difficulties implementing v3 in Canada and the UK, is much simpler than v3, and is better suited to international use.

Will FHIR replace HL7 v2 VXU and QBP messaging for IIS, and how should an interoperability team prepare for FHIR?

Asked 1× · 2023 · VXU, QBP, general · Answered

Answer given

HL7 v2 is not going away soon. A revised HL7 v2 guide was being written to fix documentation problems in the current one, and v2 is expected to be supported for years and likely decades. FHIR is being used for problems VXU and QBP cannot handle, such as FHIR Bulk Query for standardized bulk extraction from an IIS. It complements HL7 v2 rather than replacing it, which is why there is no roadmap away from v2. To prepare, software developers on new interoperability projects should know FHIR or related technologies (JSON, REST). For interoperability staff generally, look for interest in new technologies including FHIR, and consider "interest or experience in working with FHIR" as a hiring qualification.

Reading and Applying the IG

How do you use the CDC IG to find the requirements for a specific component of a field, such as ORC-3.2 or NK1-5.2?

Asked 1× · 2020 · general · Answered · Related: ORC-3, NK1-5

Answer given

Each HL7 field has a defined data type, shown in the segment table in the IG. Data types are reusable and are defined in detail in the data types chapter (Chapter 4). The "dot" parts are formally called components, and their requirements come from the data type definition. ORC-3 is an EI (Entity Identifier), so its components are described under EI. NK1-5 (phone number) is an XTN, so its components are described under XTN.

What is the difference between R and RE usage?

Asked 1× · 2016 · general · Answered · Related: RXA-15, RXA-9, Conformance Testing & Validation Tools

Answer given

A conformant system must support both R and RE elements. Operationally, RE elements can be empty, while R elements are expected to be populated 100% of the time. For example, date of birth has usage R and must always be populated to be conformant. Race has usage RE: both systems must be able to exchange it, but it is conformant to leave it empty if the sending system does not know it. For assessment, all R elements should be included in test cases, but only some test cases may include RE elements. For receiving systems, it is important to confirm they handle an unpopulated RE element gracefully.

It is also important to distinguish "conformant" from "usable". Per Release 1.5, an administered dose (RXA-9 = 00) must contain a lot number (usage R). Omitting it is a technical conformance error, but the IIS might still keep the vaccination event because the rest of the information is usable, or it might not. That decision is up to the local IIS.

Is the CDC Immunization IG (Release 1.5) the right reference for the data types an IIS should accept and send, given that the IIS still accepts older data types such as CE where the guide specifies CWE?

Asked 1× · 2020 · general · Answered · Related: Code Sets & Vocabulary

Answer given

Yes, the CDC IG is the right document. Technically CE and CWE are very similar, especially in Release 1.5, and some providers will probably still submit CE. It can be hard to tell CE from CWE even when a message declares one or the other, because the last three components of CWE are optional. The IIS should build in flexibility to accept both.

Which fields and related functionality is an IIS required to implement? (A client believed the standard required certain functionality supporting an HL7 field; the vendor thought otherwise.)

Asked 1× · 2017 · general · Answered · Related: Conformance Testing & Validation Tools

Answer given

The IG defines the conformance of messages, but it does not define exactly how the receiving system supports the data in a given field. That would belong in a functional guide, which did not exist. The question was therefore a grey area: the functionality could be described neither as absolutely required nor as clearly optional. AIRA then reviewed current test results and pointed out areas that should be improved under current standards.

VXU Triggers and Scope of Submitted Content

What events should trigger an EHR to send a VXU, and how can an IIS make sure vendors send demographic updates only for patients previously reported (rather than for every patient regardless of immunization status)?

Asked 2× · 2021 · VXU · Partly answered · Related: Data Quality & Validation; Message Structure & Cardinality (demographic-only VXU updates)

Answer given

The IG leaves triggers broad: "The sender sends an immunization record in a VXU message. The trigger may be an update or new record in the sending system records or may be triggered by some other event" (p. 67), and "Some event triggers the sending system to create and send a VXU" (p. 68). For the Z22 profile (Appendix B, p. 43), the goal is to send up-to-date information about a vaccination event and the patient. A conformant message may contain the entire vaccination history known to the sender but is not required to, and may contain only the vaccination events added, updated or deleted as part of the triggering event. For certification, EHRs must show they send a VXU when an administered vaccination is given, a historical vaccination is recorded, a vaccination is deleted, and a vaccination is updated. Beyond this, there are no national standards for additional triggers that require a submitter to send, and no guidance on when a submitter must not send. An IIS can add such requirements to its local guide as long as they do not contradict the national guidance. (The part of the question about limiting demographic updates to previously reported patients is not directly answered.)

Can an EHR submit its own dose validity flag for a dose in a VXU, or is dose validity determined only by the IIS?

Asked 1× · 2025 · VXU, RSP · Answered · Related: OBX-3

Answer given

Dose validity is not part of the standard HL7 VXU submission from an EHR to an IIS. The IIS returns evaluation and forecasting information in response to a query, typically in a Z42 and sometimes in a Z32 RSP. This information is produced by the IIS's immunization clinical decision support engine, based on the patient's history and current ACIP recommendations. AIRA is also working with its Standards and Interoperability Steering Committee on specifications to further standardize how IIS message this information.

What do the ONC HTI-1 regulations for 2026 change for immunization reporting to IIS, and what resources should a provider organization consult?

Asked 1× · 2025 · VXU, general · Answered · Related: Onboarding & Interface Testing

Answer given

For immunization reporting to IIS under certification criterion 170.315(f)(1) (Transmission to immunization registries), there are no notable changes for 2026. Provider systems can keep exchanging with IIS as they always have, in line with certification/re-certification requirements. There is a Standards Version Advancement Process (SVAP) option for immunization exchange, but it is not required, and no IIS is known to require it or plan to. Separately, 2026 introduces Insights Condition requirements related to immunizations: data collection begins in 2026 and reporting happens later (no later than July 2027). ASTP has issued several enforcement discretion notices that affect these timelines. Resources: the ONC SVAP standards document, Insights Condition measure education materials (including the Immunization Administered measure), and the ASTP enforcement discretion page.

A state law requires the IIS to collect sexual orientation and gender identity (SOGI), updated race/ethnicity, and disability information. What national discussions are under way on HL7 v2 changes to support these concepts, and what are the expected timelines?

Asked 1× · 2024 · VXU · Answered · Related: PID-10, PID-22, OBX-3, OBX-5

Answer given

Do not wait for the next national IG. The next version is at least a year away from HL7 ballot, and not every topic will be in it (disability will not be in the next round). Look instead at SISC Technical Advisory Bulletins (TABs) and older SISC guidance documents, which will be rolled into the next version of the standard. Some IIS vendors have historically treated published SISC guidance as enough to start development.

Race/ethnicity: HL7 v2 already supports these concepts. A TAB is planned on how to send "unknown" race and ethnicity, including "declined to answer". National efforts to revise and expand race/ethnicity codes are under way, but for now the community is keeping the standard value sets until there is clearer national direction.

SOGI: SISC published a guidance document about two years earlier (a predecessor to the TABs) that describes how to send sexual orientation and gender identity in HL7 v2. It was adapted from HL7 interim guidance for both lab and immunization messaging, so it matches national practice.

Disability: There is no guidance yet. It can be done in HL7 v2, but no IIS had asked for it. AIRA offered to convene a SISC subgroup to design a technical solution and publish a TAB, with the requesting IIS bringing its requirements.
