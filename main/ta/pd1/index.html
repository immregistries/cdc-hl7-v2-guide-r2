What was asked

Questions about PD1 cluster around three fields: PD1-11 (publicity code / reminder-recall contact preference), PD1-12 (protection indicator) and PD1-16 (immunization registry status). PD1-12 dominates: what it means, whether it is tied to consent, how strict an IIS may be about it (requiring, forbidding, repeating it) and what ACK severity is appropriate. PD1-11 questions concern the outdated HL7 Table 0215 values and NIST/AART value-set validation; PD1-16 questions concern mapping registry status codes to IIS patient statuses (MIROW) and their relationship to the PID-30 death indicator.

IG clarifications suggested when the TA records were consolidated (3)
  • Update Table 0215 (publicity code) with modern contact methods such as text and email, via a community code-set exercise.
  • Clarify the semantics of PD1-16 code P (permanently inactive) and whether it implies death in the absence of PID-29/PID-30; document the mapping to MIROW statuses.
  • Clarify PD1-12 meaning (stated preference, local policy, no default) and guidance for jurisdictions that need multiple consent types (with PD1-13 alignment).
  • PD1-11 Publicity Code 2

NIST rejects PD1-11.1 values (e.g., `F^Family Only^HL70215`) as "not a member of the value set HL70215 / HL70215_IZ". What values are valid in PD1-11, and can an IIS send the base HL7 values (F, N, O, U)?

Asked 2× · 2023–2026 · RSP · Answered · Fields: PD1-11 · Related: Code Sets & Vocabulary; Conformance Testing & Validation Tools

Answer given

The values F, N, O and U are the suggested values in the HL7 base standard, but they were replaced in the IZ implementation guide. AART (and the NIST tool) test against the IZ IG, not the base standard, so the national IG requirements must be followed to pass validation. Specifically: (1) PD1-11 should contain only values supported in the IG; (2) F, N, O and U are not supported by the current IG; only the values in the IG table for PD1-11 (the 0X codes, e.g., `02^^HL70215`, which passed a 2023 assessment) are acceptable; (3) because F/N/O/U are not directly mappable to the IG's codes, an IIS that crosswalks its internal codes to the base values cannot simply map them back to the outbound 0X codes.

An earlier (2023) report of the same NIST error, where the IIS believed it was sending a valid code from the PHIN VADS Publicity Code value set, had no answer recorded.

PD1-12 Protection Indicator

What does PD1-12 (protection indicator) mean and how should it be sent? Some vendors treat it as opt-in/opt-out; others use it only for special situations (witness protection, domestic violence, adoption). How does it apply in a state with opt-in consent?

Asked 3× · 2018–2024 · VXU/RSP · Answered · Fields: PD1-12 · Related: PD1-13; Local Profiles & Jurisdictional Constraints

Answer given

PD1-12 reports the patient's or guardian's stated preference about protecting (not sharing) the patient's record. It is not a flag that should be set automatically, although the patient or guardian may choose protection for any of those reasons. If the patient or guardian has not stated a preference, leave the field empty. No default value should be set, because the field records their wishes.

The actual meaning is governed by local jurisdiction law and policy. A value of Y means the patient or guardian wants the local protection law or policy applied, whatever that is locally. The exact meaning does not carry over between jurisdictions.

The earlier general question about "standards for sending the protection indicator" (2019) and a question about use under a state's opt-in consent status (2018) had no answer recorded; the 2024 answer above covers them.

Because PD1-12 is an HL7 field, does an IIS need to collect patient consent in order to populate it?

Asked 1× · 2024 · VXU · Partly answered · Fields: PD1-12 · Related: PD1-13

Answer given

No. The IIS does not need to collect consent just because the field exists in the HL7 message; whether to collect and use the protection indicator is a jurisdictional policy decision, and the field only needs to be handled properly if the jurisdiction uses it.

The IG says PD1-12 is not required and empty implies consent, but an IIS returns MSA-1 = AE with ERR-4 = E when PD1-12 is missing, while ERR-8 says it is "informational" and the patient is actually stored. Can the severity be lowered to W or I?

Asked 1× · 2022 · VXU/ACK · Answered · Fields: PD1-12 · Related: ERR-4, ERR-8, MSA-1; Acknowledgement & Error Handling

Answer given

The IIS agreed and updated the error severity (ERR-4) and descriptions (ERR-8) across its acknowledgements for an upcoming release. The underlying principle is that ACK severity should match what actually happened: a condition that does not prevent the record from being stored should be reported as a warning or informational, not as an error.

An IIS rejects messages with PD1-12 populated (ERR-4 = E, "patient consent is unwanted - Segment Rejected"), effectively making an RE field X. Would changing it back to RE but limiting allowed values meet the standard?

Asked 1× · 2024 · VXU/ACK · Answered · Fields: PD1-12 · Related: ERR-4; Local Profiles & Jurisdictional Constraints

Answer given

AIRA prefers that the usage of PD1-12 not be changed and that the national value set (Y, N) be honored, because it is an uphill battle to keep providers from sending values in a national value set. However, the IIS does not have to save or act on the data if policy prohibits it. A suggested approach is to change the ERR-4 severity for this condition from E to I (informational): the patient data continues to be saved, and the ACK tells the sender the PD1-12 value is not being stored.

In HL7 Table 0441, what is the intended use of code P "Inactive-Permanently inactive"? Is it meant only for deceased patients, and should an IIS map it to "Inactive-Deceased" only when a date of death is sent in PID?

Asked 1× · 2022 · VXU · Partly answered · Fields: PD1-16

Answer given

There is no definitive answer. The AIRA/MIROW document Patient Status in Immunization Information Systems (page 28, Functionality Challenge 2) indicates IIS should consider "permanently inactive" to be mappable to "deceased", as long as local terminology can be mapped to the minimum recommended statuses (active, inactive-outside jurisdiction, deceased). However, that document does not describe how submitting systems define the field, and there is little national information on how EHRs have implemented it. Recommendation: investigate a random sample of affected records to determine their actual status, and consider following up with providers on how they use the code.
