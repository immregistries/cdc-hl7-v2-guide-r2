Acknowledgement & Error Handling

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

23 questions. Findings: none
Not yet assessed

What was asked

Questions in this section concern how an IIS should build and populate ACK (Z23) messages: overall ACK formatting, how MSA-1 and ERR-4 severity should signal rejection versus acceptance, and how to handle partially valid messages. Recurring themes are the meaning of ERR-4 = E (the submitter must correct and resubmit), not rejecting valid-but-unused data, how much to "nag" with warnings, AART assessment findings about ACKs, and which response (ACK vs RSP) to use for problem queries. Several questions were logged without answers.

IG clarifications suggested when the TA records were consolidated (4)
  • State explicitly that receivers must not reject or raise errors on optional/unsupported OBX observations (e.g., dose-level funding source) and should ignore data they do not use.
  • Clarify when a Z23 ACK versus a Z33 RSP is expected for query parsing and validation failures.
  • Document expected IIS response time for synchronous VXU/QBP exchanges.
  • Consider documenting partial-acceptance semantics (keep good data vs. all-or-none) and ACK retention expectations, which were asked about but not covered.

AART Assessment Findings on ACKs

Why does an IIS fail AART Submission Assessment Measure 13 when the test message was not accepted, and how does its ACK differ from one that passed?

Asked 1× · 2021 · ACK · Answered · Related: MSA-1, ERR-4, Conformance Testing & Validation Tools

Answer given

Measure 13 has two components: (1) the ACK must indicate there is a problem with the message and must conform to the implementation guide (validated with NIST), and (2) the ACK must have MSA-1 = AE and at least one ERR segment with ERR-4 (severity) = E. In this case both test case ACKs did not conform to the standard according to NIST. The test details screen in AART shows, at the bottom, why the ACK did not meet standards, which can be used to improve the acknowledgement.

Error Severity and When to Reject

What do R and RE usage mean for a receiving system? Must an IIS reject all messages with R (required) violations?

Asked 1× · 2017 · VXU/ACK · Answered · Related: ERR-4, Version & IG Interpretation

Answer given

No. The IIS must raise an error, but it can declare how severe the error is through ERR-4 (and need not reject the message).

When part of a VXU is invalid (e.g., a bad RXA-3 administration date or RXA-5 CVX/NDC, or one of several immunizations is bad) but the patient is valid, should the IIS reject the whole message or accept the good data, and should it return AE with W or E severity?

Asked 3× · 2020–2024 · VXU/ACK · Answered · Related: RXA-3, RXA-5, RXA, MSA-1, ERR-4

Answer given

Earlier guidance (2020): You can store whatever information in the message is good while still rejecting the bad part for correction and resubmission: map the patient and return AE with E-severity ERR for the RXA errors. AE plus E tells the EHR the errors must be corrected and resubmitted. On resubmission the patient will come again, but this approach stores as much good data as possible and IIS should be deduplicating anyway. For example, if a message has five vaccination events and one is bad, store the patient and the four good immunizations, and reject the bad one with AE + E; the EHR may resubmit all five, which should not be a problem for the IIS.

Later guidance (2024): If the IIS receives a vaccination it cannot accept, it should return ERR-4 = E identifying the specific problem. E means the submitter must correct the problem and resubmit the entire message. The IIS may accept all or none of the data in the original message according to its own processing rules and operational needs. Even if the IIS keeps some of the data, the submitter should assume none was accepted and resubmit the whole corrected message so nothing is lost. This is documented in AIRA's "Guidance for HL7 Acknowledgement Messages to Support Interoperability".

The two answers are consistent on AE + E severity; the later answer adds that keeping partial data is at the IIS's discretion and that the submitter should resubmit everything.

Vendors ask an IIS to return ACK errors when COVID-19 data elements that CDC requires (e.g., sex, race) are missing, even though the IIS doesn't normally require them. Is an IIS expected to return ACK errors for these elements?

Asked 1× · 2020 · ACK/VXU · Answered · Related: MSA-1, ERR

Answer given

No. IIS shouldn't change their ACK behavior for COVID vaccination events compared with non-COVID events. Every element the IIS reports to CDC has an option for Unknown (or blank), so the IIS can still report to CDC when a submitter leaves those elements empty.

An IIS returns MSA-1 = AE with ERR-3 = 207^Application internal error^HL70357 ("Internal error prevented the completion of this request - Message Rejected") for a fully populated administered-vaccine VXU. What causes it and how should it be handled?

Asked 1× · 2021 · VXU/ACK · Partly answered · Related: OBX-3, OBX-5, ERR-3

Answer given

Through trial and error AIRA found that removing the OBX segment that reports the dose-level vaccine funding source caused the message to be accepted, so that OBX appeared to trigger the internal error. An IIS should be able to accept a message with this OBX present even if it does not use that data; unwanted data should simply be ignored rather than causing the message to be rejected. Because the same OBX is used in many test cases, this defect affected results across several assessment content areas (Submission and Data Quality Incoming). The IIS forwarded the finding to its vendor, but a fix had not been confirmed at the time of the record.

When RXA-5 is an NDC the IIS does not recognize, the IIS returns only warning-level ERRs (e.g., "vaccination cvx code is missing", "ndc code is unrecognized"; no ERR-4 = E), so the message appears accepted, but a later query shows the vaccination was not stored (only a CVX 999 unknown dose). Is this correct?

Asked 1× · 2024 · VXU/ACK/RSP · Answered · Related: RXA-5, ERR-4

Answer given

No. If vaccination events are being lost while the EHR is told the message was accepted, the ACK is misleading; an IIS that cannot store a vaccination event should indicate that with an error-level (ERR-4 = E) response so the sender corrects and resubmits. AIRA found this behavior came from a configuration of the vendor's test endpoint that did not match how any of its IIS clients are configured, and asked the vendor to reconfigure the endpoint to behave like an IIS would. After reconfiguration, the false-positive test results were resolved.

The IIS accepts serology observations but not a particular (valid) serology code it received. How should it respond? Is it valid to acknowledge the message was understood but not store the data?

Asked 1× · 2024 · VXU/ACK · Answered · Related: ERR-4, ERR-5, OBX-5

Answer given

Do not tell a site that sent a valid code to correct and resend its message. To stay conformant, the most the IIS should do is return an informational result (severity I) saying the serology is good information but will not be saved. It is valid for the IIS to acknowledge it understood the message and not store that data.

Warnings and Informational Messages

Should an IIS return informational warnings in the ACK telling submitters which fields of a demographic-only update (ADT or VXU) were or were not applied, given that most submitters ignore informational warnings?

Asked 1× · 2022 · ACK/ADT/VXU · Partly answered · Related: ERR, ERR-4

Answer given

Informational ERR segments are indeed likely not to be read, though that doesn't mean you shouldn't send them. Current best practices for both patient and vaccination data require the IIS to decide how received data is integrated into the official patient record, so a submitter cannot be assured that any accepted update will change the official record (e.g., historical vaccinations may be ignored, or the IIS may prefer a name spelling from vital records over the EHR's). Furthermore, ADT is a "broadcast all, take what you need" exchange: the default expectation is that receivers take what is useful and silently ignore everything else. AIRA asked for a concrete example of a field the IIS would not update to give more specific direction.

An IIS silently ignores data sent in fields it has constrained to X (not supported) rather than returning a warning in the ACK. Are there scenarios where a warning would be helpful?

Asked 1× · 2021 · ACK · Answered · Related: Local Profiles & Jurisdictional Constraints

Answer given

In general it would be rare to warn about this. A site should only nag when it matters for data quality and the IIS's business functions. Too much nagging about unimportant things trains people to ignore warnings, and that applies to HL7 ACKs too. HL7 doesn't require an ACK to document every difference in expectations.

Errors for Query Messages

When an IIS receives a QBP with problems, should it return a Z23 ACK or a Z33 RSP? (Options: (1) Z23 for parsing/validation issues, Z33 for IIS-side errors and no results; (2) Z23 only when the query cannot be parsed, Z33 for everything else; (3) Z33 for everything.)

Asked 1× · 2022 · QBP/RSP/ACK · Answered · Related: MSH-21, ERR, Query & Response Behavior

Answer given

Figure 40 of the CDC IG (query response decision flow) corresponds to option 1. Option 3 is not correct per that diagram. However the decision is not very critical: either option 1 or 2 should work, as long as the ERR segment clearly explains why a matching result cannot be returned. EHRs generally do not distinguish much between a Z23 and a Z33; they treat both as a negative match indication.

An IIS improving response time is considering skipping address validation, which adds about 200 ms per VXU. Is that tradeoff worthwhile?

Asked 1× · 2021 · VXU/ACK · Answered · Related: Transport/Connectivity, PID-11

Answer given

Once response time is around 1-2 seconds, optimization should shift from reducing response time to (1) maximizing total throughput (e.g., multiple servers), even if individual responses are slightly slower, and (2) returning as much information as possible in the ACK. It is better to return the final disposition and any problems found after 2 seconds than to respond in 0.5 seconds saying the message was received but not fully processed. For this IIS, a 200 ms wait was worth it if address quality issues can be reported back in the ACK. (AIRA testing checks that IIS respond in under 5 seconds; formal documented guidance was not identified.)
