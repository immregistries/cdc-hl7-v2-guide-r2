MSH Message Header

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

39 questions. Findings: 6 warnings 13 notes
Gap 5 · Partly answers 9 · Differs 4 · By appeal 1 · Answers 19 · Out of scope 1

How well the guide answers these

The guide answers the organization questions well: section 2.7 defines MSH-4 and MSH-22, and their roles in queries, more clearly than any past TA answer. The IGAMT profiles answer most of the fixed-value questions (MSH-2, MSH-9, MSH-15, MSH-16, MSH-21, SFT). The narrative says nothing about the other MSH fields. MSH-3, MSH-5, MSH-6 and MSH-23 (how values are agreed, and whether intermediaries change them), MSH-10 uniqueness and duplicate messages, MSH-11 test data, and the plausibility of MSH-7 are all asked about repeatedly and left to the reader. A short Message Header section in chapter 2 would answer most of them. Two past answers differ from the guide: queries with header errors now get a Z23 ACK rather than a Z33 RSP, and MSH-4 is now required on queries.

Assessed 2026-11-17 against the narrative draft of 4 Nov 2026 and IGAMT export of 6 Nov 2026.

What was asked

Other recurring themes are timestamp handling in MSH-7 (time zones, precision), acknowledgement mode fields (MSH-15/MSH-16), message type and profile identifiers (MSH-9, MSH-21) for ACK and RSP messages, and the use of MSH-8 for security credentials versus moving credentials to the CDC WSDL transport.

MSH-2 Encoding Characters

A submitter sends `MSH|^~\%26|` (URL-encoded `&`) instead of `MSH|^~\&|`. Is MSH-2 valued `^~\%26` acceptable?

Asked 1× · 2024 · VXU/general · Answered · Fields: MSH-2 · Related: Transport/Connectivity

Answer given

No. The IG (and the NIST validator) requires conformance statement IZ-13: MSH-2 (Encoding Characters) SHALL be valued `^~\&`. There is no reason to URL-encode HL7 content when it is not being delivered via a URL (for example, when sent via the CDC WSDL SOAP transport), and the submitter is inconsistent anyway since it did not URL-encode the `` (%5C) or `^` (%5E). The IIS should push back on the submitter to send the correct encoding characters rather than taking responsibility for correcting an unnecessary encoding.

Can the guide answer it?

Answers

IGAMT conformance statement IZ-13 says MSH-2 SHALL be '^~\&'. The narrative does not mention MSH-2.

Is there a maximum length for MSH-3 (Sending Application)? A local IG lists 20 characters but the CDC IG does not; where did the limit come from, and what maximum is recommended?

Asked 1× · 2026 · VXU · Answered · Fields: MSH-3 · Related: Version & IG Interpretation, Data Quality & Validation

Answer given

The current CDC IG does not specify a maximum length for MSH-3; it has generally moved away from specifying field lengths unless there is a clear interoperability need. The 20-character limit likely came from older HL7 versions, where base-standard lengths were commonly copied into IGs. HL7 conformance has since clarified that those lengths are not normative; explicit mechanisms exist when min/max lengths must be specified, and otherwise historical lengths are general guidance. IIS are not required to enforce a 20-character maximum and should not validate it solely for conformance. Validate lengths only when needed for the IIS's own storage or processing; unnecessary length checks create avoidable interoperability problems.

Can the guide answer it?

By appeal Note

IGAMT gives no length for MSH-3, and the guide says not to enforce arbitrary rules or reject for minor conformance preferences. But it never says what the lengths that IGAMT does carry (MSH-8 up to 40, MSH-10 up to 199) mean, or that base-standard lengths are not normative.

Recommendation: In 5.11 (compatibility with the base standard) or 4.1, say what a length in the profiles means, and that IIS should not reject a value only because it is longer than a base-standard length.

In the guide: 6.1.4 Focus on Data Quality and Program Goals, 3.3.5 s2

Should practices send MSH-4 on QBP messages?

Asked 1× · 2017 · QBP · Answered · Fields: MSH-4 · Related: Onboarding & Interface Testing

Answer given

MSH-4 works similarly on QBP and VXU. ONC guidance: the IIS must track the onboarding process for each provider organization from registration of intent through production, including communications. Once in production, however, there is no requirement that the IIS track submissions or queries by provider organization. So if the IIS can manage onboarding for each provider organization by some other mechanism (e.g., non-HL7 methods) and it doesn't need MSH-4 to operate, there is no reason to require the field. If MSH-4 isn't required for submission, it likely isn't needed for queries either, unless the IIS has different business rules or policy for record access during queries.

Can the guide answer it?

Differs Note

The 2017 answer said an IIS need not require MSH-4 on queries if it does not use it. The guide now makes MSH-4 required (R) and says query messages SHALL include it. A deliberate change.

A site with several facilities sending through one interface (e.g., one clinic submitting for multiple locations) needs the right facility in MSH-4. How should multi-facility sites be represented, and can a message mover map the administered-at location (RXA-11.4) into MSH-4?

Asked 2× · 2019–2022 · VXU · Answered · Fields: MSH-4 · Related: MSH-22, RXA-11, Transport/Connectivity

Answer given

The guidance explained how to use MSH-4, MSH-22 and RXA-11.4 (administered-at location) to represent the sender and the individual facilities; details were not recorded (2019).

For the Simple Message Mover (SMM) specifically (2022): yes. SMM has a `smm.config.txt` file where transformations can be added that change messages before they are sent to the IIS. The catch is that the transformation applies to every message sent through. If the facility ID is sent in RXA-11.4 and should be sent in MSH-4, add the transformation `MSH-4=RXA-11.4`. This sets MSH-4 to the facility value in the first RXA-11.4 it finds, ignoring additional RXA segments that may have the same or different RXA-11.4 values. Do not email the `smm.config.txt` file unencrypted because it contains encoded credentials.

Can the guide answer it?

Differs Note

The guide answers how to represent several facilities: MSH-4 is the submitting organization operating the interface, and child facilities go in RXA-11.4 or ORC-17. The 2022 answer suggested copying RXA-11.4 into MSH-4, which the guide no longer allows.

MSH-5 Receiving Application

An IIS has a hard stop when MSH-5 or MSH-6 is blank or not the expected value, but neighboring IIS it will exchange with may not populate them. Is that the standard, and will the IZ Gateway populate them?

Asked 1× · 2021 · VXU/QBP/general · Answered · Fields: MSH-5 · Related: MSH-6, Transport/Connectivity

Answer given

MSH-5 and MSH-6 are RE in the IG, meaning if there is a value it must be transmitted. The guide does not say whether sender or receiver defines the values; it leaves that to local negotiation. The IZ Gateway does not modify the message, so the sender must populate correct MSH-5/MSH-6 values. It is reasonable to expect sending systems to configure MSH-5 and MSH-6 according to the receiver's requirements, since they are addressing the message and want it routed properly.

Can the guide answer it?

Partly answers Note

MSH-5 and MSH-6 are RE in IGAMT, and the guide says intermediaries must be transparent. It does not say who defines their values, whether an IIS may reject a message when they are empty, or that the IZ Gateway does not change them (the IZ Gateway is out of scope).

MSH-6 Receiving Facility

Submitters send their IIS-assigned numeric ID in VXU MSH-4, MSH-22 and RXA-11.4, but the IIS returns the ACK with the parent organization's alphanumeric org code in MSH-6 (and MSH-22). Should the ACK return the same ID received in the VXU?

Asked 1× · 2022 · ACK/VXU · Answered · Fields: MSH-6 · Related: MSH-4, MSH-22, MSH-5

Answer given

There are no constraints in the current IG requiring that ACK MSH-6 equal VXU MSH-4, although it is reasonable to expect they would usually be the same since they identify the same organization. It may be best to have them match, especially if EHRs are asking questions about the returned values, but it is not required by current standards, and most if not all receiving systems should be able to process the response even if they do not match.

Answers

2.7.7 says MSH-4 and MSH-22 are "typically mirrored back" in acknowledgements. Like the past answer, this is not a requirement. It sits in the query section, though it applies to the VXU ACK too.

In the guide: 2.7.7 Use in Query Transactions (QBP/RSP)

When an HIE is a pass-through for immunization queries, should senders put the HIE or the IIS (the ultimate destination) in MSH-6?

Asked 1× · 2022 · QBP/VXU · Answered · Fields: MSH-6 · Related: MSH-3, MSH-4, MSH-5, Transport/Connectivity

Answer given

The current guide gives no guidance on what values go in MSH-3, MSH-4, MSH-5 and MSH-6; they are intended to be negotiated between sender and receiver. Either the HIE or the IIS in MSH-6 is acceptable. Most IIS do not require specific values here and will process messages with MSH-6 empty. You could require a specific value, but only do so if it is needed to properly route and process the message.

Can the guide answer it?

Gap Warning

The guide says nothing about MSH-3, MSH-5 or MSH-6 values: that they are agreed between trading partners, that an IIS should require specific values only when it needs them for routing, or which party to name when an HIE passes a message through. TA has answered this the same way several times.

Recommendation: Add a short Message Header section to chapter 2 covering MSH-3, MSH-5, MSH-6 and MSH-23: agreed during onboarding, required by an IIS only when needed for routing or processing, not changed by intermediaries, and in an ACK or RSP normally echoing the sender's MSH-3 and MSH-4.

VXU doesn't support patient management workflows such as merging, linking and unlinking patients. Is there an HL7 v2 standard for these events?

Asked 1× · 2025 · ADT · Answered · Fields: MSH-9 · Related: PID, PD1

Answer given

Yes, ADT (Admit Discharge Transfer) messages, widely used in health systems for patient management. ADT is a fairly basic message with patient segments (PID, PD1, etc.), and the trigger event in MSH-9 tells sender and receiver which workflow is intended (e.g., register new patient (A04), merge patients). There is no immunization-specific IG for ADT, but HL7 v2.5.1 references for ADT_A04 and the full list of ADT trigger events are available online. For internal use (UI to HL7 processing) the system can decide which segments, fields and trigger events to support. A couple of IIS accept ADTs today to establish a relationship between a provider organization and a patient.

Can the guide answer it?

Answers

ADT is out of scope, and 3.2.5.6 points to ADT for routine demographic updates.

How commonly do EHRs populate the query tag (QPD-2) and message control ID (MSH-10) with unique IDs versus static values, and how should a receiving IIS treat them?

Asked 1× · 2022 · QBP/VXU/RSP · Answered · Fields: MSH-10 · Related: QPD-2, Query & Response Behavior

Answer given

MSH-10 is required to be unique at least for the date of the message and for the sender in MSH-4, so it should not be hard-coded and reused, although a sender could reuse an ID on a different day. In practice some systems rely on the message ID heavily, even refusing to process the same ID twice, and it is commonly used to look up failed messages, so most mature systems are expected to use strongly unique IDs. Similar strategies are expected for the query tag; using the same value for both is fine. The query tag is only critical for deferred queries (request now, check progress later), and the national guide supports only immediate queries, so it is not really needed. As a receiver, it is easiest to simply echo back what was sent and not tie any other critical business rules to these values.

Can the guide answer it?

Gap Warning

MSH-10 is required, but the guide never says it must be unique (the past answer says per sender, at least per day) or that MSA-2 echoes it. The query tag in QPD-2 is not discussed either.

Recommendation: In a Message Header section, say MSH-10 SHALL be unique for the sender and is echoed in MSA-2.

If a QBP arrives without MSH-21, what should the IIS return in the RSP's MSH-21 and QAK-3?

Asked 1× · 2024 · QBP/RSP · Answered · Fields: MSH-21 · Related: QAK-3, ERR, MSA-1, QPD

Answer given

The IIS can still run the query, particularly because QPD-1 also carries the query profile. It can return a warning (W) ERR segment along with its normal reply (not found, single patient, list, or too many), depending on the result.

If the IIS wants to reject the query, the proper way is a Z33 RSP with MSA-1 = AE, an ERR segment pointing to `MSH^1^21` with code 101 (Required field missing) and severity E, QAK-2 = AE, QAK-3 holding the query profile (for example `Z34^Request Immunization History^CDCPHINVS`), and QPD echoed back. The IIS should send back QAK and QPD even if it cannot fill them in completely.

Differs Note

The 2024 answer: run the query anyway with a Warning, or reject with a Z33 RSP (MSA-1 'AE', ERR on MSH-21). Under the guide, missing required header information gets a Z23 ACK, and 'AE' no longer means rejected. See ta-q03-107.

MSH-22 Sending Responsible Organization

Is there national guidance on how an IIS should respond when the MSH-22 value in a VXU has no relationship to the submitter's SOAP credentials or the MSH-4 sending facility? Should this be an error or warning, and how should MSH-4, MSH-22, ORC-17 and RXA-11 relate?

Asked 1× · 2025 · VXU/ACK · Answered · Fields: MSH-22 · Related: MSH-4, ORC-17, RXA-11, MSA-1, Local Profiles & Jurisdictional Constraints

Answer given

There is currently no national guidance on this and no national requirement to validate MSH-22 against the authenticated sender; the IG defines MSH-22 as the business organization accountable for the message content, which may or may not be the same as the MSH-4 facility. In practice MSH-4 aligns with the SOAP wrapper credentials and is used by IIS as the authoritative sender; IIS may choose to validate MSH-22 per local policy, and during onboarding should define what MSH-22 values are expected for each authorized sender.

Recommendations: if the IIS cannot accept and store the data because MSH-4 is invalid or unrecognized, return an E-level error on MSH-4 with MSA-1 = AE so the sender knows to correct and resend. Relying on MSH-4 as the authoritative source is a good default. ORC-17 (entering organization) is far less standardized and many EHRs do not populate it meaningfully, so validating it is difficult unless coordinated during onboarding. MSH-22 exists for cases where one organization submits on behalf of another (e.g., a cloud EHR or HIE) and MSH-4 alone does not identify the accountable entity; in those cases an IIS can require MSH-22 to contain a recognized, registered value, but for most sites MSH-4 suffices and MSH-22 can be ignored. RXA-11 identifies the clinic/site that administered the vaccine and is critical for inventory tracking. The proposed approach of accepting the data, attributing ownership to MSH-4, and returning a warning or informational message about the unrelated MSH-22/ORC-17 value is consistent with this. An older CDC document on identifying provider entities and mapping them to HL7 fields (MSH-4, MSH-22, ORC-17, RXA-11) was shared, and the topic was to be raised with CDC, IGEG and SISC for a future TAB or IG update.

Can the guide answer it?

Partly answers Warning

The guide ties transport credentials to MSH-4 and says authorization to submit for another organization is set up at onboarding. It does not say whether an IIS should check MSH-22 against that authorization, or what severity to give a mismatch.

Recommendation: Add a statement on MSH-22 that is not authorized for the submitting organization: for example, IIS MAY validate it against onboarding records, and report a mismatch as an Error or Warning by local policy.

MSH-23 Receiving Responsible Organization

An IIS plans to populate response MSH-23 with MSH-23.6 = a local assigning authority, MSH-23.7 = a local identifier type code (e.g., `VACMANPIN`), and MSH-23.10 = an ID echoed from query MSH-22.10. NIST reports the MSH-23.7 value is not a member of value set HL70203_IZ. Since base HL7 table 0203 has "suggested values", is a local value acceptable?

Asked 1× · 2022 · RSP/QBP/VXU · Answered · Fields: MSH-23 · Related: MSH-22, Conformance Testing & Validation Tools, Local Profiles & Jurisdictional Constraints

Answer given

The NIST tool is working correctly. The identifier type code (component 7) must come from HL7 table 0203 to pass the national guide and NIST validation. Possible table 0203 values that could fit such a provider PIN include FI (Facility ID), PRN (Provider Number), RI (Resource identifier), and XX (Organization identifier). However, be cautious about requiring submitters to use components 6-10 of MSH-22: although supported in the guide, few IIS implement them and NIST has not certified EHR systems to support these components, so requiring them would likely cause some systems to struggle to connect. More typically IIS expect a value in MSH-22.1 (Organization Name); while it is a string not tied to a table, it is where IIS commonly ask submitters to put an IIS-assigned value. Accepting the PIN in MSH-22.1 would work with certified systems today.

Can the guide answer it?

Partly answers Note

The IGAMT binding answers the identifier type question (HL70203). The narrative never mentions MSH-23, and 2.7.1 says the components after HD.1 are optional. The past advice not to require MSH-22 components 6 to 10 is not in the guide.
