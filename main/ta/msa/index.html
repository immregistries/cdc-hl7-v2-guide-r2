MSA Message Acknowledgment

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

14 questions. Findings: none
Not yet assessed

What was asked

Nearly all MSA questions concern MSA-1 (Acknowledgment Code): when to return AA, AE or AR, and how MSA-1 must agree with the severities in ERR-4. The dominant theme is that AR is reserved by the base HL7 v2 standard for a small set of message-level conditions, so content rejections are signaled with AE plus an ERR-4 = E, while AA is used only when there are no ERR segments or only informational ones. Later questions (2024-2026) track draft guidance expanding the use of AR and concern about EHR interfaces that shut down when they receive AR. A few questions address MSA-3 and MSA-6.

IG clarifications suggested when the TA records were consolidated (3)
  • State explicitly that receiving AR must not cause a sender to shut down its interface; clarify sender reactions to AR vs CR.
  • Publish the MSA-1 / ERR-4 combination table (AIRA ACK guidance Table 5) as normative guidance.
  • Document the planned expansion of AR use and its relationship to the base-standard AR conditions.

MSA-1 Acknowledgment Code

In the AART Submission/Acknowledgement assessment, several test cases fail with "IIS did not accept message," but the IIS actually processed those messages. What is expected, and how can these test cases pass?

Asked 1× · 2024 · VXU/ACK · Answered · Fields: MSA-1 · Related: ERR-4, Acknowledgement & Error Handling, Conformance Testing & Validation Tools

Answer given

For the failed test cases AART is submitting VXUs that are conformant to the standard, but the IIS acknowledgements indicate the system does not like what was submitted: they return an "E" (error), indicating something needs to be corrected. Since the VXUs are conformant, it is the acknowledgements that need to be corrected so they do not report errors for valid content. Other users of the same IIS product have faced similar issues and may be able to share the ACK updates they made to pass.

An IIS business rule prevents deleting an immunization linked to an inventory lot. When a well-formed delete is not processed for this reason, should MSA-1 be AE or AR?

Asked 1× · 2021 · ACK/VXU · Answered · Fields: MSA-1 · Related: ERR-4, ERR-8

Answer given

It should be AE, not AR; AR is not appropriate since the message was processed. The more important question is ERR-4: severity E means the sender is expected to correct the information and resend, which is probably the best code here, assuming the IIS wants the sender to take further steps (fix data on their side and/or contact the IIS to fix the record). Consider stating those next steps in the error text, e.g., adding "Please contact the IIS help desk to resolve this issue."

When an IIS rejects a VXU (does not store it), for example because patient first name, last name or DOB is missing or invalid, should it return MSA-1 = AR? Some EHR interfaces treat AE as "processed with errors" and act only on AR.

Asked 3× · 2020–2024 · ACK · Answered · Fields: MSA-1 · Related: ERR-4, Acknowledgement & Error Handling

Answer given

No. These should be AE with ERR severity E. The base HL7 v2 standard is very specific that AR can only be used in very limited situations (four specific situations, which are rare in practice). If the IIS must reject for other reasons (for example, a future-dated administration or a missing address when required), it cannot use AR; it must return AE in MSA-1 with ERR-4 = E. Senders therefore need to look at ERR-4: AE with an E-severity ERR indicates rejection. The table of MSA and ERR-4 combinations and their expected meaning in AIRA's "Guidance for HL7 Acknowledgement Messages to Support Interoperability" (Table 5) is the best description.

What MSA-1 should be returned when the message is accepted but has only warnings or only informational issues (e.g., the IIS accepts the message even though RXA is missing fields it deems necessary)?

Asked 4× · 2020–2023 · ACK · Answered · Fields: MSA-1 · Related: ERR-4, Acknowledgement & Error Handling

Answer given

If you are satisfied enough with the message that you would not expect the provider or EHR to take action and resubmit, the ACK should be AA with no ERR segments, AA with only I-severity ERR segments, or AE with W-severity ERR segments, with no E-severity ERR segments. Messages with only I-severity issues return AA, provided there are no W or E severity errors. Confirmed again in 2023: if the only ERR segments are informational, MSA-1 should be AA (consistent with the AIRA ACK guidance). A 2023 question asking whether an ACK with MSA-1 = AE and only informational errors is acceptable has no separate answer recorded; the guidance above indicates AA.

Can an ACK use MSA-1 = AA together with an ERR of severity I (e.g., `ERR|||0^Message Accepted^HL70357|I||||Incoming immunization already exists...`)? How should an IIS decide between E, W and I in ERR-4 when some conditions currently returned as AE with a warning are not really errors?

Asked 1× · 2022 · ACK · Answered · Fields: MSA-1 · Related: ERR-4, ERR-3, Acknowledgement & Error Handling

Answer given

Follow AIRA's Guidance for HL7 Acknowledgement Messages to Support Interoperability (https://repository.immregistries.org/resource/guidance-for-hl7-acknowledgement-messages-to-support-interoperability/). MSA-1 should be AA if there are no ERR segments or all ERR segments are severity I; if at least one ERR is W or E then MSA-1 should be AE (or AR in a few corner cases). The proposed AA with an informational ERR for a duplicate immunization is good, since resubmitting a vaccination is not a problem. IIS decide what are true errors but must flag them consistently: E means the issue must be fixed and resubmitted, W means the data needs fixing but need not be resubmitted, and I conveys information without requesting action. There is no firm national stance on which specific issues are E, W or I; it rests on IIS policy. Nationally the priority is that E is used correctly and not for issues that do not need fixing or resubmission. W can drive data quality, including for issues that may be correct as reported (e.g., an unexpected dose amount), as long as the message says something like "The dose amount may be incorrect, please verify."

An IIS returns MSA-1 = AA for every message, including submissions containing errors that it reports in ERR segments. Is that appropriate, and how do other IIS handle ACKs?

Asked 2× · 2016–2024 · ACK · Answered · Fields: MSA-1 · Related: ERR-4, ERR, Acknowledgement & Error Handling

Answer given

No. Provider organizations will likely read AA as "accepted without error" and will not review or aggregate the ERR segments. The IIS should return AE in MSA-1, which means the message was processed and errors are being reported. Send AE whenever the IIS detects an error more severe than informational (warnings and errors), from data ignored because it is not wanted up to rejection of the whole message. See AIRA's "Guidance for HL7 Acknowledgement Messages to Support Interoperability" for MSA-1 values (2024). In an earlier case (2016), after discussing how other IIS handle acknowledgements, the IIS agreed to update its ACKs to be more meaningful (reflecting actual processing results and errors) for providers submitting via the CDC WSDL rather than always returning AA.

What is the proper use and purpose of the AR acknowledgement code, if rejected data is indicated with AE plus ERR-4 = E?

Asked 3× · 2019–2024 · ACK · Partly answered · Fields: MSA-1 · Related: Acknowledgement & Error Handling

Answer given

AR has a quite limited purpose defined by the base HL7 v2 standard, reserved for a small set of specific conditions (such as an unsupported message type) rather than for rejecting message content. Changing this would be far larger than a national IG change because the AR definitions apply to all HL7 v2 ACK messages, not just immunizations (2024). An earlier (2020) answer gave an overview of the ACK Guidance document recommendations (details not recorded); a 2019 question has no answer recorded.

Note: later questions (2026, below) refer to draft guidance expanding the use of AR.

Is there documentation on the expanded use of AR, and is it a problem that some EHR interfaces shut down when they receive an AR?

Asked 2× · 2026 · ACK · Answered · Fields: MSA-1 · Related: Acknowledgement & Error Handling

Answer given

Draft guidance expanding AR use was to be presented to SISC with a vote the following month (early 2026). Nothing in the base HL7 v2 standard, the current IG (2015), the current ACK guidance (2015), or the new document suggests shutting down an interface when an AR is received, and AIRA was not aware of other EHRs that do this. A few IIS have issued AR for years despite the AE/E guidance because migrating their provider community to AE was difficult. The concern about interfaces shutting down is warranted, and AIRA asked which IIS were causing the most shutdowns.

AIRA then met with the EHR vendor's interface team, which was not concerned about the movement toward IIS returning AR. The vendor suggested some intermediary language around use of CR (Commit Reject), and that language was added to the appendix of the ACK guidance.

MSA-3 Text Message

Should an IIS leave MSA-3 empty in its ACK to resolve a conformance finding?

Asked 1× · 2025 · ACK · Answered · Fields: MSA-3 · Related: Acknowledgement & Error Handling

Answer given

AIRA's M&I testing ignores MSA-3 being populated, because some IIS send it and some receiving systems depend on finding it there. AIRA would not recommend removing MSA-3 from a production system without first talking with downstream systems (trading partners) to make sure they are not relying on it.
