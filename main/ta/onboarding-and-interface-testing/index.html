Onboarding & Interface Testing

Working analysis for the authors, from questions asked of AIRA's technical assistance service. Not part of the guide.

26 questions. Findings: none
Not yet assessed

What was asked

Questions in this section cover how IIS onboard submitting and querying partners, how they design and modernize their onboarding processes and documentation, and how interfaces are tested (including by AIRA's AART assessment tool and through intermediaries such as HIEs and the IZ Gateway). Recurring themes include onboarding VXU and QBP together versus separately, legacy (historical) data loads, security hygiene for test and inactive interfaces, the need for automated (not manual) processing during testing, and where to find sample test messages and training. Several questions come from non-HL7 senders (spreadsheets/CSV, employee health, school districts, NHSN) asking how to get data into an IIS.

IG clarifications suggested when the TA records were consolidated (3)
  • The IG does not address identification of individual querying sites in QBP (only MSH-level identifiers) or registration expectations for query-only facilities; site-level tracking is recommended by Security Guidance but not specified (raised for SISC/IGEG).
  • Consider clarifying standard terminology for historical/legacy data submission methods (single-patient protocol vs. HL7 batch file vs. full history per VXU).
  • Consider guidance on implementing delete/update messaging (MSH-10, ORC-3, RXA-21, RXA-22) for senders moving from flat files.

Query (QBP/RSP) Onboarding

When an IIS adds bidirectional query, is onboarding needed again for all senders who already submit VXUs? Is the middle of the COVID response a good time to implement?

Asked 1× · 2021 · QBP/RSP · Answered · Related: Bidirectional Exchange

Answer given

Some IIS have an additional onboarding testing step for organizations using query, but it is very different from VXU onboarding: there is a large need to check data coming into the IIS and much less need to check data going out. AIRA can provide more detail as the IIS progresses. As for timing, query will be useful as soon as it is available; it may not be critical in a given month for people to get their vaccination history out, but it will be valuable going forward.

Does AIRA have a query-specific (QBP) onboarding form or questionnaire, similar to its VXU Onboarding Questionnaire?

Asked 1× · 2023 · QBP/general · Answered · Related: Query & Response Behavior

Answer given

AIRA has not developed query-specific onboarding documentation. Onboarding best practice is to onboard VXU and QBP messaging at the same time, and when that practice is followed, all of the questions a provider needs to answer are already contained in the AIRA Onboarding Questionnaire. The templated Onboarding Questionnaire does not include all of the query-related questions an IIS might ask on a separate query form, but it is designed to be customized by each IIS, so adding useful query-related questions to it is consistent with best practice. If the IIS onboards VXU and QBP interfaces separately, merging the questions may make less sense and the IIS can instead adapt questions from the questionnaire to its own query form.

Some IIS do not require facilities that only send QBP queries to register individually; large organizations register one facility ID and any number of sub-locations query under it without tracking. Is this common, should it be discouraged, and should onboarding track individual facilities even for QBP-only access?

Asked 1× · 2025 · QBP · Answered · Related: MSH-4; Query & Response Behavior

Answer given

There is no national requirement in the IG that QBP-only facilities be registered individually, but the Security Guidance recommends tracking queries to the site level for audit and breach response. HL7 v2 makes this difficult for QBP because identifiers are limited to MSH fields, and keeping them consistent with VXU practice is messy. In practice state policy and information sharing agreements govern this; some states require facility-level identification while others allow parent-level credentials if the parent assumes responsibility, which is beyond what the IG specifies. The practice creates a governance blind spot when no one knows who is querying under a shared ID, and should be addressed. AIRA planned to raise it at SISC and flag it to IGEG as a gap (as part of an open work item on identifying organizations).

An IIS tests VXU interfaces first in production (with data held/queued until validation), and only after go-live tests query using real data. Is it possible to test VXU and query together during the testing phase, and if so how is that set up?

Asked 1× · 2023 · VXU/QBP/RSP · Answered · Related: Query & Response Behavior

Answer given

The usual approach to testing simultaneously is for the provider to query for patients previously submitted via VXU. Whether that works depends on how the IIS's pre-production (queued) setting handles a QBP: will it error, or return an RSP, and if so from queued data or all stored data?

If the pre-production setting returns an RSP, identify a set of patients for providers to query during testing: test patients (if test data can be stored in production and the provider is willing to query them), patients previously entered manually in the IIS, or, if the IIS answers queries from queued VXU data, the patients the provider just submitted.

If the pre-production setting does not return a valid RSP, query cannot be tested alongside VXU, and testing query after VXU go-live is a good practice. It is common to add query to a live interface and test it in production, which also allows clinical staff to confirm the RSP returns accurate data. Consider collecting query setup information up front during onboarding/registration so query testing can begin right after VXU go-live.

Legacy (Historical) Data Loads

Why does the onboarding SOP template include legacy (historical) data submission as a requirement, and how do IIS get legacy data from EHRs (e.g., beyond a 90-day retrigger window) without receiving full histories with every new VXU?

Asked 1× · 2023 · VXU · Answered · Related: Transport/Connectivity

Answer given

Legacy data loads improve IIS data saturation, and an IIS is most valuable when fully populated. Some jurisdictions (e.g., opt-in states) have policies that prevent legacy loads and should remove the step from their customized SOP. AIRA's guide "Importing Legacy Data to Improve IIS Saturation" (based on a survey of 35 jurisdictions and interviews with IIS and EHR vendors) recommends offering several submission methods to fit different EHR capabilities. Sending a full history with each new VXU is one form of the HL7 single-patient approach. Others include a batch HL7 flat file, which one large EHR vendor prefers for moving large volumes of patient and vaccination data. For the 90-day limitation, the IIS could submit a community information request.

During onboarding an IIS asks providers how they will send historical data: (a) HL7 real-time batch (single-patient protocol using the real-time interface), (b) HL7 batch file (2.5.1 batch specification), or (c) full immunization history with each new VXU. Is this terminology accurate/standard, and which option would a provider choose if sending real-time via the SOAP service?

Asked 1× · 2023 · VXU · Answered · Related: Transport/Connectivity

Answer given

See AIRA's guide "Importing Legacy Data to Improve IIS Saturation", which covers all three methods. For (a), page 5 describes HL7 single-patient protocol and three approaches to it; if the intent is sending legacy data as individual messages through the interface, the word "batch" should be removed, whereas if it means loading an HL7 batch file of single-patient messages, clarify that. For (b), "HL7 batch" is accurate, but page 8 describes several working definitions of "batch", so describe exactly what the IIS supports. For (c), the phrasing is correct (see page 7). Transport (e.g., SOAP) is separate from these methods and varies by IIS; a provider sending via its existing live SOAP interface would be using HL7 single-patient protocol, most closely option (a).

Interface Lifecycle & Security (Test Credentials, Inactive Interfaces)

The AIRA onboarding SOP template says to disable test interface credentials after a provider goes live in production. Why, when keeping a dual test/production connection makes later upgrades, new vaccine testing, and retesting easier?

Asked 1× · 2023 · general · Answered · Related: Transport/Connectivity

Answer given

It is a general security practice: IIS should not keep open access points with no immediate use. Most providers stay live and do not use the test connection again, and interface accounts are often exempt from password expiration or inactivity deactivation policies, so test interfaces that are never disabled can be a security risk. The SOP is a template. Jurisdictions should follow their own security policies, and if those support keeping test connections (with monitoring and credentials separated by environment), the SOP should be customized.

Is there guidance on production HL7 interfaces that are not sending any data? Should there be a policy for checking that connected sites are sending data, and a timeline for disabling an interface when a provider stops sending?

Asked 1× · 2023 · general · Answered

Answer given

No formal guidance exists, but there are several considerations. First, find the root cause. Is something blocking messages from reaching the IIS, has the facility closed or changed its practice, or does it only use the interface occasionally (e.g., yearly flu clinics)? Collecting expected volume and vaccine types at onboarding gives a baseline for these decisions. Second, check jurisdictional security policies (e.g., the state privacy/security office) that govern access, inactive accounts and credential expiration, and see whether they cover interface accounts or should be extended to them. Third, use available levers to get the provider sending again, such as state reporting requirements, and warn the provider that the connection may be disabled, which would leave direct data entry as the only way to meet reporting requirements.

AIRA AART / Measurement & Improvement Testing

What does connecting (or reconnecting) an IIS test environment to AIRA's AART assessment tool involve, and what information and level of effort are required from the program and IT?

Asked 1× · 2024 · VXU/QBP · Answered · Related: MSH-4, MSH-6, MSH-11, MSH-22, RXA-11

Answer given

Step 1 is providing connection information for the IIS test environment: the web services endpoint URL; web services credentials (username, password and facility ID); and the HL7 identifier values the jurisdiction requires in test messages for MSH-4, MSH-6, MSH-11, MSH-22 and RXA-11.4. Typically the IIS creates a fake organization/provider in its test environment (e.g., "AIRA AART") and generates credentials for it, much like onboarding a new provider, except no real data is sent and the connection is used only for Measurement and Improvement testing. Step 2 is a connectivity test in which AIRA configures AART and attempts to connect; troubleshooting may require IIS, IT or vendor staff and can take minutes to a couple of hours. Note that AART assessment relies on the ACK: an interface that always returns a positive ACK (e.g., through an HIE) cannot be meaningfully assessed for submission, and when queries go to a separate interface, VXUs must be processed before the queries are run.

AART test VXUs sent different patients (different name, DOB, etc.) with the same PID-3 patient ID from the same organization, which sends them to the IIS's ambiguous-ID queue for manual resolution. Is this intentional, and should IIS staff resolve these records?

Asked 1× · 2022 · VXU/QBP · Answered · Related: PID-3; Patient Matching & Deduplication

Answer given

AART test messages are contrived and normally try not to reuse MRNs, but sometimes the same MRN is used for two different patients intentionally to see how the IIS reacts. AART is not trying to get its data accepted; it is probing system behavior, and some test messages contain problems that are not critical for passing the functional tests. IIS staff should not spend resources on these; it is fine if such records stay in the ambiguous-ID queue indefinitely.

During AART HL7 testing (including CDS testing), an IIS accepted a VXU with a historical HepA dose but the dose did not appear in the subsequent Z44 query response. Is manually adding the vaccination so the query response can be tested acceptable?

Asked 1× · 2024 · VXU/QBP/RSP · Answered · Related: Query & Response Behavior

Answer given

No. For all HL7 testing, including CDS testing, the IIS is expected to add records automatically from the submitted VXU messages; manual intervention to add or modify a record does not meet the testing requirements. Some flexibility is allowed for the IIS to run normal automated processes such as overnight jobs (e.g., deduplication) before the query is sent, but not manual entry. Practically, CDS testing involves around 900 test cases, so manual entry would not be feasible anyway. A small set of "sanity check" test cases can be run first to confirm the IIS is returning submitted doses before re-running the full CDS test set.

Intermediaries & Multi-Jurisdiction Connections (HIE, IZ Gateway)

When an HIE sits between EHRs and the IIS, what does AIRA validation test, and can the HIE continue to handle onboarding (validating messages, working with EHR vendors, distributing site IDs) as long as it does not modify messages?

Asked 1× · 2022 · VXU/QBP · Answered · Related: Transport/Connectivity; Conformance Testing & Validation Tools

Answer given

AIRA validation is conducted on whatever endpoint/interface the IIS designates as the official location for submitting updates and queries. AIRA has no requirements on the IIS architecture or how an HIE integrates with the IIS; it only validates that the state (or an HIE on the state's behalf) offers an HL7 endpoint that follows national standards. In practice this usually means the HIE passes messages through to the IIS as-is, but other arrangements may be acceptable as long as submitting systems can connect using current standards and interact normally without modification. AIRA has best practice guidance on streamlining onboarding, but how onboarding tasks and staff are organized is for the HIE and state to negotiate.

IZ Gateway began flagging messages in its onboarding (test) environment that appeared to contain PHI/PII, including a long-used obviously fake vendor test patient. Why is IZ Gateway inspecting test message content, and what can a vendor do when its test patient is flagged?

Asked 1× · 2024 · general · Answered · Related: Transport/Connectivity

Answer given

Policy documents IIS have signed prohibit PHI/PII from passing through the IZ Gateway onboarding environment, yet several IIS were pushing real data through it (for example, pre-production environments with live provider connections that trigger IIS-to-IIS exchange). That exposed both the IZ Gateway team and receiving IIS, whose test environments are not secured like production, to PHI. The onboarding environment, unlike production, allows staff to view messages to support testing and HL7 standardization during go-live. CDC therefore instituted detection and eventually rejection of apparent PHI/PII in onboarding. Determining test data versus real data is imperfect; vendors whose fabricated test patients are flagged can ask the IZ Gateway team to declare those patients known test patients, and should consider making test data look less like real PHI. AIRA would pass the feedback on communication and timing to the IZ Gateway team.

Non-HL7 and Non-Traditional Senders

Organizations whose employee-health vaccinations are recorded in non-HL7 applications ask to send COVID-19 doses by spreadsheet. Should the IIS require HL7, and what are other states doing?

Asked 1× · 2020 · VXU · Answered

Answer given

Other jurisdictions face the same issue. Prioritized options: (1) employee health enters data into the hospital EHR, which likely already feeds the IIS; (2) employee health enters doses in the IIS user interface; (3) employee health builds and tests an HL7 interface, though this is likely unreasonable given their time/expertise and IIS onboarding capacity; (4) explore a locally installed tool that converts an extracted tab-delimited file of identified data (using the CVRS identified specification for a uniform extract) into HL7.
