Query Responses and Patient Protection

How to structure an RSP^K11 response when the query matches a patient who has asked that their data be protected: when to send a full Z32 or Z42 response, and when to send a Z33 instead.

Summary

The guide agrees with the FAQ's basic approach: each IIS applies its own consent rules, a patient whose data may be shared gets a normal Z32 or Z42, and a protected patient gets a Z33 (that part is also checked in the Returning Record in RSP TAB comparison, tab-rr-01). What the guide leaves out is everything that lets a querying system tell "protected patient found" apart from "no patient found": the FAQ's modified Z33 (MSA-1 'AA', an informational ERR, QAK-2 'NF'), and the two codes the FAQ planned for this release. One of those now exists as national ERR-5 code 2700, but the guide does not use it. The other, a QAK-2 value 'PD', was never added. The guide also does not carry over the rule against returning a partial history.

Guidance when implementing Release 1.5 p. 1

should If local laws, regulations, and IIS policy allow data to be returned even though the patient asked for protection, the IIS should respond with a standard Z32 or Z42.		In narrative only Note

The guide leaves consent enforcement to each IIS ("IIS are responsible for enforcing their own consent rules based on local authority") and uses a Z33 only when a record "cannot be disclosed". A normal Z32 or Z42 for a protected patient whose data may be shared follows from that, but is not said.

4.5.6 Consent and Privacy, 3.5.2.4 Z33 - Return a Response with No Person Records, 4.5.6.1 s7

Guidance when implementing Release 1.5 p. 1-2

strongly recommend A partial patient history is not recommended. In the absence of widespread support for dose-level protection, all doses should be returned if any doses are returned: a provider who takes a partial history for a full one may make an inappropriate clinical decision, and confidence in the IIS suffers.		Missing Warning

The guide says a Z32 or Z42 returns "the complete immunization history", but never addresses withholding some doses for privacy, or the clinical risk of a history that looks complete but is not.

Recommendation: In the consent sections or the Z32/Z42 sections, state that an IIS SHOULD NOT return a partial history to protect some doses: it returns either the whole history or a Z33.

3.5.2.4 Z33 - Return a Response with No Person Records

Guidance when implementing Release 1.5 p. 2

Where law and policy do not strictly prohibit indicating that the patient exists, send a modified Z33: MSA-1 'AA'; ERR-3 populated (207, Application Internal Error, suggested); ERR-4 'I' (the querying system is not expected to fix or resend anything); ERR-5 empty; ERR-8 text saying a patient was found but is protected (for example, "A match was found in the IIS but no value is returned since Data Sharing for the record is set to No"); QAK-2 'NF'.		Missing Warning

The guide has a single Z33 for every case and no way to tell a querying system that a protected patient was found. The FAQ records why that matters: EHR systems may need to distinguish a protected patient from no patient (for example, so staff do not create a duplicate record or keep re-querying).

Recommendation: Describe the "protected patient found" Z33 in the Z33 section, updated for this guide: MSA-1 'AA', one ERR segment with ERR-4 'I' and ERR-5 2700 (see sisc-qrpp-05), ERR-8 text for the user, and QAK-2 'NF' (or 'PD'; see sisc-qrpp-06). State that an IIS uses it only where law and policy allow it to reveal that the patient exists.

Action: Narrative

3.5.2.4 Z33 - Return a Response with No Person Records, 4.5.6 Consent and Privacy, 3.3.3.6 ERR-8: User Message

Guidance for incorporation into a future release p. 2

In the next release, ERR-5 in the modified Z33 carries a new error code for a protected patient found.		Missing Warning

The code now exists in the national set of ERR-5 codes: 2700 "Protected Patient Found" (and 2701 "Potentially Protected Patient Found"), both noted as applying to a single high-threshold match. The guide publishes that code set (Appendix D) but does not mention either code in its consent or Z33 sections.

Recommendation: Name ERR-5 codes 2700 and 2701 in the Z33 section, as the way to tell a querying system that a protected patient was found.

Action: Narrative

3.3.3.4 ERR-5: Application Error Code, 3.5.2.4 Z33 - Return a Response with No Person Records

Guidance for incorporation into a future release p. 2

In the next release, QAK-2 is 'PD' (Protected Data), a new code used when a protected patient is found.		Missing Warning

Neither the guide nor IGAMT has 'PD': QAK-2 is bound to HL70208_IZ01 with OK, NF, TM, AE, and AR. 'PD' is not an HL7 v2.5.1 code, so adding it would extend an HL7 table. With ERR-5 2700 available, 'PD' may no longer be needed, but the FAQ said it would be added, so its omission should be a decision rather than an oversight.

Recommendation: CDC to decide whether to add QAK-2 'PD' or rely on QAK-2 'NF' with ERR-5 2700. Record the decision in the change history.

Action: CDC decision
