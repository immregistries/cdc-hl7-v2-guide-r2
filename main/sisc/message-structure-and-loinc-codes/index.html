Guidance on Detailed Message Structure and the Use of Specific LOINC Codes

How to structure whole VXU and RSP messages that carry observations (immunity, refusals, indications and contraindications, adverse reactions, VIS), and which LOINC codes belong in which order segment group.

Published document · Copy in this repository

Version 1.1, published as a Word document. The repository also has an earlier PDF (2017). The CDS in RSP TAB (September 2026) builds on this guidance for evaluations and forecasts.

Summary

The guide has folded this guidance in closely: its section 4.4 says it "consolidates and replaces prior LOINC guidance", uses the same six Order Segment Group flavors, and lists the same LOINC codes for each, almost word for word. The CDS in RSP TAB has since replaced the evaluation and forecast rules, and the guide follows the TAB. Three things need attention. First, the guide's section on condition date semantics (4.8.6.3) treats contraindications as patient-level observations that are never linked to a vaccine, which reverses this guidance's v1.1 change and contradicts the guide's own flavor definitions and IGAMT (already a finding, qf-igamt-condition-loinc). Second, the rule that event groups come before the Patient Observations group, and the per-profile summary of which groups each message uses, were dropped. Third, the co-constraint tables differ from IGAMT in small ways that are mostly already recorded in the IGAMT review.

Types of Order Segment Groups p. 2

Six flavors of Order Segment Group are used in immunization messages: Immunization Event, Immunization Event (Contraindicated), Immunization Event (Refused), Immunization Event with Evaluation, Forecast, and Patient Observations.		Covered

The guide defines the same six flavors with the same names, and adds that the names are conceptual only.

should Local codes used by trading partners are out of scope. IIS should document any additional codes used in the jurisdiction and the context for using them.		In narrative only Note

The guide says observations outside the defined flavors "must be interpreted based on local or bilateral agreements", and that IIS may support additional LOINC codes, but does not say an IIS should document them.

4.4.3 Order Segment Groups and LOINC/OBX Grouping, 4.4.1 Overview of LOINC and OBX Usage in Immunization Messaging

Structure of the VXU (Z22) message p. 3

A Z22 may contain zero or more Immunization Event groups (administered, contraindicated, or refused) and up to one Patient Observations group.		Covered

The guide goes further and requires a single Patient Observations group (SHALL).

4.4.4.4 Patient Observations, 4.4.4.1 Immunization Event, 4.4.4 Order Segment Group Flavors

Structure of the VXU (Z22) message p. 3

should All Immunization Event groups, of any type, should come before the Patient Observations group (if present).		Missing Note

The guide sets an order only for the RSP (the Forecast group comes last). It says nothing about where the Patient Observations group goes in a VXU or an RSP.

Recommendation: State that the Patient Observations group, when present, follows all immunization event groups (and, in an RSP, comes before the Forecast group), or decide that order does not matter and say so.

4.4.4.4 Patient Observations, 4.4.3 Order Segment Groups and LOINC/OBX Grouping

Structure of the VXU (Z22) message p. 3

A VXU is not expected to contain Immunization Event with Evaluation or Forecast groups, since submitters do not usually evaluate or forecast doses.		In narrative only Note

The guide describes both flavors as produced by a CDS engine and returned in RSP messages, and the Z22 co-constraint tables have no evaluation or forecast rows, so this holds in practice. It is not stated for the VXU.

4.4.1 Overview of LOINC and OBX Usage in Immunization Messaging, 4.4.4.4 Patient Observations

Structure of the Z32 and Z42 messages; Table 4 p. 5-9

Which groups each profile uses (Table 4): Z22 uses Immunization Event (0..*), Patient Observations (0..1), Refused and Contraindicated (0..*). Z32 uses either Immunization Event or Immunization Event with Evaluation (the latter if a Forecast is present), an optional Forecast (0..1), and the rest as for Z22. Z42 uses Immunization Event with Evaluation (0..*), exactly one Forecast (1..1), and the rest as for Z22. Each forecast set in the Forecast group has its own OBX-4 sub-ID.		Partly covered Note

The guide's CDS rules match for any RSP with CDS content (evaluation in each history group, exactly one Forecast group, placed last), and the Forecast section requires a shared OBX-4 per set. But the guide has no summary of which flavors each profile uses, and does not say whether a Z32 may carry evaluation or a forecast. Figure 20 is organized by flavor, not by profile.

Recommendation: Add a short table like this guidance's Table 4 to section 4.4.4: each flavor against Z22, Z32, and Z42, with its cardinality.

Action: Narrative

4.7.4 s1, 4.7.4 s2, 3.5.2.5 Z42 - Return Evaluated Immunization History and Forecast, 4.4.4.6 Forecast

must Related OBX segments must be linked with the same sub-ID in OBX-4: the observations about one VIS, and the observations in one evaluation or one forecast set.		Reworded Note

4.4.2.4 OBX-4 Observation Sub-ID, 4.6.6.3 s9, 4.4.4.6 Forecast

Change History (version 1.1) p. 9

Contraindication observations were removed from the RSP Patient Observations group, because it is important to show the contraindicated vaccine in RXA-5. Contraindications should be sent in an Immunization Event (Contraindicated) group.		Conflict Warning

The guide's flavor sections follow this (30945-0 only in the Contraindicated group, which "links contraindication observations to a specific vaccine that was not given"), and so does IGAMT. But section 4.8.6.3 says conditions may be sent as standalone patient-level observations or in a not-administered group, that IIS process both "identically", and that RXA-20 = NA "does not create standardized meaning linking the condition to a specific non-administered vaccine". That reverses the reason for the v1.1 change. The representation conflict is already a finding (qf-igamt-condition-loinc); this adds the history CDC should weigh when deciding it.

Recommendation: When deciding qf-igamt-condition-loinc, note that SISC moved contraindications into the Contraindicated group in 2018 precisely so the vaccine is identified. If the guide keeps 4.8.6.3, record the reversal in the change history.

Action: CDC decision

4.8.6.3 Date Semantics, 4.8.6.3 s1, 4.8.6.3 s4, 4.4.4.2 Immunization Event (Contraindicated), 4.4.4.4 Patient Observations

Structure of the Z32 and Z42 messages (evaluation) p. 5, 7

required; must In each evaluation set, vaccine type (30956-7) is required and must be the first OBX, and dose validity (59781-5) is required and must be the second. Reason for validity, series name, number of doses, dose number, and schedule used may follow.		Conflict Note

The vaccine type comes first in the guide too. But the guide says dose validity SHALL be omitted when it cannot be determined, where this guidance (and the CDS in RSP TAB, and IGAMT) require it. This is already a finding from the TAB comparison (tab-cds-08).

Recommendation: Resolve with tab-cds-08.

Action: CDC decision

4.7.7.2 Vaccine Type and Component Identification, 4.7.7.4 s3, 4.4.4.5 Immunization Event with Evaluation

Structure of the Z32 and Z42 messages (forecast) p. 5, 7

required; must In each forecast set, vaccine type (30956-7) is required and first; status in series (59783-1) is required; reason for recommendation (30982-3) is required when the status is contraindicated or not recommended; earliest and recommended dates (30981-5, 30980-7) are required for doses on schedule or overdue; overdue and latest dates, schedule, series name, number of doses, and dose number are optional.		Reworded Note

The guide follows the CDS in RSP TAB, which replaced these rules. One change: the reason for recommendation is now MAY, even when a series is contraindicated or not recommended. The TAB comparison found the guide matches the TAB (tab-cds-17).

Recommendation: Record in the change history that the reason for recommendation is no longer required.
