Consolidating Demographic Records and Vaccination Event Records

How an IIS builds a single best record for a patient and for each vaccination event from multiple reports, and how it chooses among conflicting values.

Published PDF · Copy in this repository · Repository page

Summary

The guide and this MIROW guide share the model of one consolidated patient record and one consolidated vaccination event, assembled from many reports and used for everything the IIS does, including query responses; the guide's statements that returned data may differ from what was submitted, that each source keeps its own ORC-3, and that administered records are generally preferred all follow from it. Three connections need attention. MIROW asks IIS to keep every past IIS patient ID, so a submitter holding an old ID can still be answered, but the guide makes that history optional and does not say what happens when a query names a retired ID. MIROW treats the lot number as a single value, while the administered RXA lets RXA-15 repeat without saying what a second lot means. And the guide never mentions the multiple birth indicator and birth order (PID-24, PID-25), which are what keep twins from being merged.

Where the guide connects

The best practice saysResultIn the guide

P01, P02, P05 - One consolidated record, used for all IIS functions

An IIS creates a single consolidated demographic record for each patient and a single consolidated vaccination event record for each vaccination event, built from the best value for each data element, and uses it for all IIS functions, including clinical decision support and query responses.		Covered

The guide tells querying systems to expect the consolidated history, with names that may differ from what they sent, rather than an echo of their own submissions.

2.3.3 Record Consolidation and Deduplication, 4.5.2.10 Name Consistency and Matching Expectations, 4.6.1.5 s1, 4.6.3 Vaccination Record Identity and ORC-3

P03 - Make original information accessible

The originally submitted values should remain accessible to the IIS.		Reworded Note

The guide recommends keeping the link between each source record and the consolidated event, and allows keeping both the submitted and the cleansed address, but leaves retention of submitted values to the IIS.

4.5.3.6 s3, 4.6.3 s1, 4.6.1 Administered versus Historical Vaccinations

BR202, BR203 - Retain all past IIS patient IDs; use the current one

All past IIS patient IDs associated with a consolidated record should be retained. The current IIS patient ID should be used in all IIS-originated communications, and in response to a query the IIS should let the submitter know that the IIS patient ID has changed.		Partly covered Warning

The guide requires the current SR or LR in every RSP (as BR203 asks), but says retired identifiers "may be retained as aliases, but a complete identifier history is not required". Submitters are told they can store the IIS identifier (from code 5044 or an RSP) and use it in later queries; after a merge, the one they hold may be retired. The guide does not say whether a query naming a retired SR or LR finds the merged record.

Recommendation: CDC to decide whether an IIS SHOULD resolve a retired SR or LR in QPD-3 to the current record (which MIROW BR202 makes possible), and to say so in Identifier Changes, Merges, and Retirement.

Action: CDC decision

4.5.1.5 Identifier Changes, Merges, and Retirement, 4.5.1.7 s1, 3.3.3.5 s4

BR5103 to BR5105 - IIS vaccination event IDs and alternate vaccination event IDs

All past IIS vaccination event IDs should be retained, the current one used in all IIS-originated communications, and the submitters' own vaccination event IDs (alternate IDs, with their assigning authority) kept accessible, to reduce problems in bidirectional exchange.		Covered

The guide's ORC-3 model is this rule in message form: keep the source-assigned ORC-3 with its assigning authority, return it to the same source when possible, and otherwise return the IIS identifier for the consolidated event.

4.6.3 s1, 4.6.3 s2, 4.6.3 s3

BR204, BR702 - Retain past and multiple values

Past values of alternate patient IDs, addresses, alias names, telephones, and email addresses should remain accessible (they help matching and unmerging), and all unique current values of multi-valued elements should be retained.		Reworded Note

The guide accepts repeated addresses, names, and contact methods and lets the IIS decide how many to keep; it does not recommend retaining past values. That is a reasonable split (retention is IIS policy), but the guide could point to MIROW for the reasons to retain them.

4.5.3.1 s4, 4.5.1.5 s2, 4.5.1.10 Other Patient Identifiers

BR201, BR5101, BR5102 - What the IIS needs to know about each value

For each data element, the IIS needs the data source type, the specific data source, the most recent submission date, and a confidence level, and for vaccination events the administered/historical indicator, which the submitter should provide.		Covered

The message carries each of these: the source in MSH-4, MSH-22, and RXA-11; the date in MSH-7; the record type in RXA-9 (required). The RXA-9 historical source codes, which feed the confidence level, are not explained in the narrative (see the deduplication comparison, mirow-vd-08).

2.7.2 Submitting Organization (MSH-4 Sending Facility), 2.7.3 Responsible Organization (MSH-22), 3.2.5.2 s2, 4.6.1.6 IIS Processing and Reconciliation

BR301 to BR304, BR5202 to BR5205 - Data groups

Some elements form groups that must come from the same source, be kept together, and be consistent: telephone and its type, an alternate patient ID with its assigning authority and type, multiple birth indicator and birth order, a responsible person's name and relationship, dose volume and unit, a contraindication and its date, and an alternate vaccination event ID with its assigning authority.		Covered

The HL7 structure keeps each group together (XTN, CX, and EI components; NK1-2 with NK1-3; RXA-6 with RXA-7; an OBX with its date), and the guide's insistence on an assigning authority for PID-3 and ORC-3 is what lets an IIS keep identifiers grouped with their source.

4.5.1.2 s2, 4.6.3 Vaccination Record Identity and ORC-3, 4.5.4.1 s3

BR701, BR5301 - Elements with a single value

Some elements must have a single value: for the patient, date of birth, multiple birth indicator, birth order, birthing facility, and birth state; for a vaccination event, the administration date, product, manufacturer, lot number, expiration date, dose volume and unit, site, route, and ordering and administering providers.		Partly covered Warning

The profiles allow one value for each of these except the lot number: RXA-15 is required and repeats (1..*) in the administered RXA, and the guide does not say what a second lot number means. The SISC comparison found the same gap (sisc-lot-01).

Recommendation: State that RXA-15 carries the lot number of the unit administered, and either limit it to one repetition or define what further repetitions carry (for example, a diluent or a separately supplied adjuvant).

Action: Narrative and IGAMT

2.8.2 s5, 3.2.4.2 Non-Identifying Vaccination Fields

BR1201, BR6001, P10 - Unmerge, and prevent re-merging (twins)

An IIS should be able to unmerge a consolidated record and should prevent re-merging records it has unmerged, which happens often with twins.		Missing Warning

Unmerging is IIS processing, but the message is where twins are told apart: the multiple birth indicator (PID-24, RE) and birth order (PID-25, conditional). The narrative never mentions them, so submitters have no reason to send them. MIROW also treats them as values from Vital Records, the definitive source (BR601).

Recommendation: Add a short section on multiple births to Patient Information: send PID-24 and PID-25 whenever known, because they are what keeps an IIS from merging twins, and query with them when known.

Action: Narrative

4.5 Patient Information, 3.4.6 Selecting a Candidate Match

P07 to P09, BR801, BR802, BR901, BR902, BR5401 to BR5403, BR5601, BR5602, BR5701, BR5702 - Choosing the best value

Accurate information is preferred over more complete information; then more complete over less, more specific over less, higher confidence over lower, and more recent over older. For a vaccination event, the administered record's values are preferred over a historical record's; two administered records from different sources are investigated; and between two records from the same source, the most recent submission wins.		Covered

The guide's preference for the administering organization's record, and its update model (a later report from the same source replaces the earlier one), match these rules.

4.6.1.6 IIS Processing and Reconciliation, 4.6.1.1 s1, 3.2.5.3 Modifying Non-Identifying Vaccination Fields

BR1002, BR5802, P12 - Do not overwrite validated data

Consolidation should not overwrite data the IIS has validated. If an IIS corrected a value and the same source submits the same wrong value again, the validated value is kept; the general rule of using the most recent value gives way.		Partly covered Note

The guide says IIS "are expected to apply these updates to the existing vaccination record", without the MIROW exception, although it also says returned values may differ from those submitted and that IIS must not require submitters to "correct" names. A submitter whose update is not applied has no way to know.

Recommendation: CDC to decide whether the guide acknowledges that an IIS may keep a validated value instead of applying a resubmitted one (MIROW BR1002 and BR5802), and if so whether the ACK should report it as a warning.

Action: CDC decision

3.2.5.3 Modifying Non-Identifying Vaccination Fields, 4.5.2.10 s3

BR1101, BR5901, P11 - Local laws control

Local laws, regulations, and policies on opt-out, foster care, protective custody, and adoption supersede all other rules; information they prohibit using is not used in a consolidated record.		Covered4.5.6 Consent and Privacy, 3.5.3 Information Disclosure Constraints, 4.5.6.2 Jurisdictional Consent Models

BR601 - Supremacy of vital statistics

Vital statistics is the definitive source for date of birth, gender, multiple birth indicator, birth order, birthing facility, birth state, mother's maiden name, and birth certificate number.		Reworded Note

Consistent with the guide's use of official documentation for the date of birth; the guide does not single out Vital Records or cover the other birth elements (see mirow-cr-09).
